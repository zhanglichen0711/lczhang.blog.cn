Agent 的 demo 人人都能跑出来：一个模型 + 两个工具 + 一段循环，就能演示"AI 自己完成任务"。但把这个 demo 推到生产，速度会突然慢下来——慢不在模型能力，而在三件 demo 阶段看不到的事。

## 状态：多轮之后它还记得自己干到哪了吗

Demo 是一轮任务，生产是几十轮的真实对话。Agent 做着做着会忘掉目标、重复调用、在一个错误结果上继续往下走。**会话状态的管理——什么该记住、什么该忘、超时和中断怎么恢复——是生产 Agent 的第一道坎。** 模型上下文再长，也代替不了明确的状态机。

## 工具：模型提议得再好，工具也得接得住

Demo 里的工具是假的、一次只调一个。生产里工具会超时、会返回脏数据、会被并发调用、会有权限边界。模型建议调 `search_docs`，但参数格式错了怎么办？工具返回异常怎么办？动作涉及敏感操作谁来批准？**这些不是模型问题，是系统问题**——而且每一个都能让 Agent 从"聪明"变成"不可信"。

## 退化：模型升级一次，Agent 可能坏一批

Agent 比单轮 RAG 脆弱得多：改一个模型、调一句 prompt、换个工具返回格式，都可能让整条任务链在某一步悄悄坏掉，而且是隔几天才被用户发现的那种坏。单轮应用有个坏案例集就够，Agent 需要的是**按任务路径组织的回归测试**——每个典型任务跑一遍完整流程，而不是只看单步输出。

## 谁在真正落地 Agent

观察下来，真正跑起来的 Agent 都收敛到同一个模式：**把任务切成边界清晰的小步，每步用一个高可靠的模型或规则完成，步与步之间用明确的输入输出契约衔接，全程可观测可回滚。** 它不是"让模型自由发挥"，而是"让模型在约束里发挥"。

## 慢是正常的

Agent 落地慢，不是谁做得不好，是这个形态本身就要求把工程做扎实。Demo 到生产之间缺的那段路，恰好就是应用工程师的价值所在——**模型负责聪明，系统负责可靠。**
