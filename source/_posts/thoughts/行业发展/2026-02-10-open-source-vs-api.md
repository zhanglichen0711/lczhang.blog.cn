选开源模型还是闭源 API，很多讨论都停在"谁分数高、谁便宜"。做了几年应用之后，我的判断标准已经收敛成一个更本质的问题：**数据最终留在哪一边。**

## 闭源 API 的隐性成本是数据

API 调起来确实省事：不用管 GPU、不用管部署、模型厂商帮你维护。但每一次调用，你的 prompt、你的文档片段、你的业务数据，都要发到对方的服务器上。

如果只是公开信息的问答，这无所谓。一旦知识库里混着合同条款、客户信息、内部流程——数据出境就不是技术问题而是商业问题。**模型厂商的服务条款写得很清楚，你输入的东西会被用来做什么，决定权不在你。**

## 开源模型的隐性成本是运维

开源模型把数据留在了自己这边，但它不负责帮你跑起来。权重下载、显存规划、推理引擎、高可用、版本升级——这些以前厂商替你扛的事，全部变成你的运维负担。

而且开源不等于免费：算力是成本，人也是成本。小团队自托管一个大模型，省下的 API 费可能还不够付 GPU 和运维的时间。

## 用一张表代替站队

| 维度 | 闭源 API | 开源自托管 |
|---|---|---|
| 数据归属 | 出境到厂商 | 留在自己这边 |
| 接入成本 | 低，几行代码 | 高，部署 + 运维 |
| 单次成本 | 按 token 付费 | 固定算力成本 |
| 升级维护 | 厂商负责 | 自己跟进 |
| 定制能力 | 弱 | 可微调、可私有化 |

## 实际的选择逻辑

我的经验是分场景，不站队：

- **数据敏感、合规要求高**（政企、金融、内部知识库）→ 开源 + 私有化部署，把"数据不出域"作为硬前提；
- **公开信息、追求迭代速度**（C 端助手、内容工具）→ 直接调 API，把精力省下来做业务；
- **混合是常态** → 公开部分走 API、敏感部分走本地小模型，中间用路由层切分。

## 结论

模型能力会快速拉平，但**数据归属的约束不会随模型升级消失**。所以选型的第一问不是"哪个模型更强"，而是"这份数据允不允许离开我的服务器"——答案定了，选项往往就只剩一个。
