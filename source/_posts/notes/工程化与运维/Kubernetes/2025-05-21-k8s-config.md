镜像里最不该写死的东西有两类：**普通配置**（模型名、超时时间、日志级别——各环境不一样）和**敏感信息**（API Key、数据库密码——写进镜像等于泄露给所有能拉镜像的人）。Docker 时代我们用环境变量注入，但那是在启动命令里一条条传，规模一大就乱。K8s 用两个专门的对象管理这件事：**ConfigMap 管普通配置，Secret 管敏感信息**。核心原则一句话：**镜像和环境解耦——同一个镜像，配上不同的 ConfigMap/Secret，就能跑出测试、预发、生产三种行为。**

## ConfigMap：普通配置

ConfigMap 就是一组键值对（或配置文件），用来存不敏感的配置：

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: rag-config
data:
  MODEL_NAME: "Qwen/Qwen2.5-7B-Instruct"
  MAX_TOKENS: "2048"
  LOG_LEVEL: "info"
  # 也可以直接放一段配置文件
  config.yaml: |
    retrieval:
      top_k: 5
      rerank: true
```

创建并注入到 Pod：

```bash
kubectl apply -f configmap.yaml
```

**方式一：作为环境变量注入**

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      containers:
        - name: api
          image: registry.example.com/rag-api:1.0
          envFrom:
            - configMapRef:
                name: rag-config
```

`envFrom` 会把 ConfigMap 里所有键变成环境变量。也可以只挑几个键用 `env` + `valueFrom` 注入。

**方式二：作为文件挂载**

```yaml
containers:
  - name: api
    volumeMounts:
      - name: config
        mountPath: /app/config
volumes:
  - name: config
    configMap:
      name: rag-config
```

ConfigMap 挂成文件后，应用照常读文件——很多框架支持"配置热更新"，ConfigMap 更新后文件会同步变化（有秒级延迟），应用可以感知而不需要重启。

## Secret：敏感信息

Secret 的用法和 ConfigMap 几乎一样，唯一的区别是**内容要加密存储、访问要受控**：

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: rag-secrets
type: Opaque
data:
  OPENAI_API_KEY: c2stZXhhbXBsZQ==    # base64 编码
stringData:
  DB_PASSWORD: "MyP@ssw0rd"          # 明文写，自动转 base64
```

注意：**YAML 里的 `data` 字段要求 base64 编码**，写起来麻烦；用 `stringData` 可以直接写明文，K8s 会自动转码。创建后注入方式和 ConfigMap 相同：

```yaml
containers:
  - name: api
    env:
      - name: OPENAI_API_KEY
        valueFrom:
          secretKeyRef:
            name: rag-secrets
            key: OPENAI_API_KEY
```

几个必须知道的认知：

- **base64 不是加密**。`c2stZXhhbXBsZQ==` 只是编码，谁都能解码。Secret 的安全依赖集群本身的权限控制和加密机制（etcd 加密、RBAC），**不要因为"写了 Secret"就以为安全了**。
- **Secret 也不该进 Git 仓库**。ConfigMap 和 Secret 的 YAML 如果明文提交到仓库，Secret 照样泄露。正确做法是 Secret 的 YAML 只存在于集群（或存在 Git 里但用 Sealed Secrets、External Secrets 加密，后面 CI/CD 篇会涉及）。
- 应用层能拿到 Secret 明文（环境变量里就是明文），所以**最小权限**很重要：只给需要的容器注入它需要的 Secret。

## 环境隔离：一份镜像，三套配置

理解了 ConfigMap 和 Secret，就能理解 K8s 里"环境"是怎么隔离的。同一个镜像 `rag-api:1.0`：

- 测试环境：注入 `rag-config-test`（连测试库、模型用小的）和测试 Secret；
- 生产环境：注入 `rag-config-prod`（连生产库、模型用正式的）和生产 Secret。

**镜像本身一个字节都不变**，变的只是挂上去的配置对象。这带来的好处是决定性的：

- 发布流程里"测试过的镜像 = 生产的镜像"，不存在"测试用的配置泄漏到生产"的风险；
- 环境之间的差异全部显式可见（diff 两个 ConfigMap 就知道差别在哪）；
- 敏感信息不进镜像，拉镜像的人拿不到密钥。

## 两个常见坑

**坑一：改了 ConfigMap 没生效。** 环境变量方式注入的配置，**Pod 不重建不会更新**——ConfigMap 改了但旧 Pod 还在跑旧值。要么滚动重启 Deployment（`kubectl rollout restart deployment/rag-api`），要么把配置走文件挂载（这个方式可以热更新）。

**坑二：密钥当 ConfigMap 存。** 有人图省事把 API Key 放进 ConfigMap。ConfigMap 没有加密机制、到处可见，密钥必须走 Secret。区分标准很简单：**能不能让所有拉镜像/看集群的人知道——能，放 ConfigMap；不能，放 Secret。**

## 小结

ConfigMap 和 Secret 把配置从镜像里抽出来，让"一份镜像多环境复用"成为可能：普通配置进 ConfigMap，敏感信息进 Secret（记住 base64 不是加密，密钥不进 Git），环境差异靠不同配置对象隔离。到这，一个应用在 K8s 里的完整形态已经拼齐——Deployment 管副本、Service/Ingress 管入口、ConfigMap/Secret 管配置。但还差关键一环：**K8s 怎么判断 Pod 里的服务是死是活、什么时候该重启？** 下一篇讲探针。
