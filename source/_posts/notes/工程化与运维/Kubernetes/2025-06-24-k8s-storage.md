前面讲的 Deployment 场景里，Pod 都是"无状态"的——删了重建，丢点缓存无所谓。但集群里总有真正需要持久化数据的服务：MySQL、Redis、Milvus、MinIO。这些服务的 Pod 也是"会死"的，数据却不能跟着死。K8s 怎么给这些"有状态"的服务提供可靠的存储？答案分两层：**PVC 解决"数据存哪、怎么申请"**，**StatefulSet 解决"有状态服务的身份和顺序怎么保证"**。

## PV 与 PVC：存储的"声明式"用法

延续 K8s 的声明式哲学，存储也是"描述需求，而不是指定细节"。K8s 把存储抽象成两个对象：

- **PV（PersistentVolume）**：集群里的存储资源——一块云盘、一个 NFS 共享、本地磁盘目录。它是"供应方"，由管理员或云厂商（动态供给）创建。
- **PVC（PersistentVolumeClaim）**：应用对存储的"需求声明"——我要 10GB、读写模式、访问速度。它是"需求方"，应用只跟 PVC 打交道，不关心背后是哪种存储。

```yaml
# 应用侧：声明存储需求
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: rag-data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

Pod 里挂载 PVC：

```yaml
containers:
  - name: api
    volumeMounts:
      - name: data
        mountPath: /data
volumes:
  - name: data
    persistentVolumeClaim:
      claimName: rag-data
```

**PVC 和 Pod 解耦**是这套设计的关键：Pod 不知道数据存在哪块盘上，只知道挂载点叫 `/data`。底层存储换掉（云盘换成 NFS），Pod 的 YAML 一个字节都不用改。云环境里通常配**动态供给**——PVC 一创建，云厂商自动分配一块云盘绑定上，连 PV 都不用手写。

## Pod 重建后数据还在

没有卷的 Pod 重建后，数据随旧容器一起消失。挂上 PVC 的 Pod 则不同：

1. Pod 被杀、被调度到另一台节点；
2. K8s 在新节点重新创建 Pod；
3. 新 Pod 挂上**同一个 PVC**，读到的是旧 Pod 写的数据。

这正是数据库上 K8s 的前提。但这里有个微妙之处：PVC 的访问模式决定了它能不能被多节点同时挂载：

- **ReadWriteOnce**：只能被一个节点挂载（单副本数据库用这个）；
- **ReadWriteMany**：可被多个节点同时挂载（共享文件存储，多副本读场景用这个）。

云盘（云厂商块存储）通常是 ReadWriteOnce，多副本共享要选 ReadWriteMany 的文件存储（NFS、CephFS）。**选错访问模式，多副本的 Pod 会调度失败**，这是有状态服务部署最常见的报错之一。

## StatefulSet：有状态服务的"稳定身份"

Deployment 管无状态服务很合适，但管数据库这类有状态服务有个问题：**Deployment 的 Pod 名字是随机的**（`rag-api-abc123`），重建后名字会变。对需要"稳定身份"的服务（数据库节点间要互相认领、要按序号分片），名字变了就乱了。

StatefulSet 就是为有状态服务设计的控制器，它保证三件事：

**1. Pod 有稳定的名字和网络身份。** 每个副本按序号命名（`milvus-0`、`milvus-1`、`milvus-2`），序号不变，重建后还是同一个名字。

**2. 每个副本绑定独立的 PVC。** 序号为 N 的 Pod 永远挂它自己的卷（`data-milvus-0`），Pod 重建数据不丢、身份不变。

**3. 按顺序启动和终止。** 下一个副本要等上一个就绪才启动，保证有主从关系的服务（如 etcd、ZooKeeper）启动顺序正确。

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: milvus
spec:
  serviceName: milvus
  replicas: 3
  selector:
    matchLabels:
      app: milvus
  template:
    metadata:
      labels:
        app: milvus
    spec:
      containers:
        - name: milvus
          image: milvusdb/milvus:v2.4.0
          volumeMounts:
            - name: data
              mountPath: /var/lib/milvus
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 100Gi
```

注意最后一段 `volumeClaimTemplates`——StatefulSet 用它给**每个副本自动生成一个独立的 PVC**（`data-milvus-0`、`data-milvus-1`、`data-milvus-2`）。删掉 StatefulSet 里的一个 Pod，重建后新 Pod 会认领回自己的卷，数据完好。

## 有状态服务上 K8s：到什么程度

要把 MySQL、Milvus 这类服务真正跑好，还需要主从复制、备份恢复、故障切换等一大堆能力。业界有两条路：

- **Operator 模式**：用专门的"服务算子"（如 ZALO Postgres Operator、Milvus Operator）管理有状态服务——它知道数据库该怎么做主从、怎么备份、怎么处理故障，把运维经验编码成控制器。**生产环境部署数据库类服务优先考虑 Operator，而不是自己手搓 StatefulSet。**
- **用云托管服务**：能用云厂商的托管数据库（云数据库、托管向量库）就用托管的，把"数据可靠性"这种高风险高成本的活外包出去，集群里只跑无状态应用。对大多数团队，这往往是最优解——**K8s 里少一个要你半夜爬起来处理的数据服务，就多一分安稳。**

## 小结

存储的 K8s 化分两层理解：PVC 让应用用"声明需求"的方式拿存储，跟底层解耦，Pod 重建数据不丢；StatefulSet 给有状态服务稳定名字、稳定卷、稳定顺序。但真正的数据库上集群，建议走 Operator 或云托管，别自己从零维护。下一篇把整个 Kubernetes 系列收口——用一篇实战把前面所有概念串起来：一个完整的 RAG 服务怎么部署到 K8s。
