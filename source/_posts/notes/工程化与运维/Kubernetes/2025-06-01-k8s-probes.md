Docker 篇讲过健康检查——让编排系统知道容器是死是活。到了 K8s 里，这件事被拆得更细：**一个"活着"的进程，不等于"可以接流量"**。模型还在加载、数据库还没连上、缓存正在预热——这些时刻进程是活的，但接了流量就会报错。K8s 用两类探针分别回答两个不同的问题，用错了会导致"服务一直在重启"或"流量打到没就绪的 Pod"这类诡异故障。

## 两类探针：就绪与存活

**存活探针（livenessProbe）**回答"进程还活着吗"——死了就重启容器。它查的是**不可恢复的故障**：死锁、OOM 后的僵尸状态、goroutine 泄漏导致的假死。

**就绪探针（readinessProbe）**回答"现在能接流量吗"——没就绪就把这个 Pod 从 Service 的负载均衡池里摘掉，等就绪了再接回来。它查的是**可恢复的临时状态**：启动加载中、依赖下游还没通。

```yaml
containers:
  - name: api
    image: registry.example.com/rag-api:1.0
    ports:
      - containerPort: 8000
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8000
      initialDelaySeconds: 30   # 启动后等 30 秒再开始查
      periodSeconds: 10         # 每 10 秒查一次
      timeoutSeconds: 3
      failureThreshold: 3       # 连续失败 3 次才判定存活失败
    readinessProbe:
      httpGet:
        path: /ready
        port: 8000
      initialDelaySeconds: 5
      periodSeconds: 5
```

注意这里有个**新手几乎必踩的坑：把两个探针指向同一个接口**。假如 `/healthz` 在模型没加载完时返回 503：

- 就绪探针失败 → Pod 被摘出流量池，这是对的；
- 存活探针也失败 → **K8s 认为容器死了，直接杀掉重启**。

结果就是：模型加载要 40 秒，容器每 30 秒被杀一次，**永远加载不完**——一个经典的"启动即崩溃循环"。正确设计是：

- 存活探针查一个**轻量、稳定**的接口（进程活着就 200）；
- 就绪探针查**真正代表可服务**的状态（依赖就绪、模型加载完）。

## 探针的三种探测方式

探针支持三种探测动作：

- **httpGet**：HTTP GET 请求，2xx/3xx 视为健康。Web 服务最常用，注意**路径别用需要鉴权的接口**，否则探针会因为 401/403 把健康服务误判成不健康。
- **tcpSocket**：TCP 连接成功即健康。适合没有 HTTP 接口的服务（如 Redis、MySQL），但只能证明端口在听，证明不了服务真能用。
- **exec**：容器内执行命令，退出码 0 即健康。适合没有网络接口的进程（如批量任务 worker）。

```yaml
readinessProbe:
  exec:
    command:
      - python
      - -c
      - "import urllib.request; urllib.request.urlopen('http://localhost:8000/ready')"
```

## Startup 探针：慢启动服务的救星

大模型推理服务有个特殊性：**加载几个 GB 的模型权重可能要 1-3 分钟**。如果用存活探针且 `initialDelaySeconds` 设得不够，容器会在加载期间被反复杀掉。把 `initialDelaySeconds` 调到足够大又会让真出问题时发现得太慢。

K8s 提供了第三个探针——**startupProbe（启动探针）**：只在启动阶段探测，成功后**存活/就绪探针才开始工作**：

```yaml
startupProbe:
  httpGet:
    path: /healthz
    port: 8000
  initialDelaySeconds: 0
  periodSeconds: 5
  failureThreshold: 60        # 最多给 60×5=300 秒启动时间
```

配置后启动阶段由 startupProbe 兜底（最多等 5 分钟），启动完成后存活探针接管日常健康监控，`initialDelaySeconds` 就不用再纠结设多大。**推理服务部署强烈建议配 startupProbe。**

## 优雅退出：摘流量在前，杀进程在后

Pod 被删除（发布、缩容、驱逐）时，K8s 的执行顺序是：

1. Pod 状态变为 Terminating，**从 Service 摘除**（新流量不再进来）；
2. 给主进程发 SIGTERM，**宽限期默认 30 秒**（`terminationGracePeriodSeconds` 可配）；
3. 宽限期结束还没退出，发 SIGKILL 强制杀。

应用要配合的是：**收到 SIGTERM 后，停止接收新请求、把手头请求处理完、释放资源，然后自己退出**。对 uvicorn/gunicorn 这类成熟服务器，这是内置行为——前提是**进程别被包裹得收不到信号**。

```yaml
containers:
  - name: api
    terminationMessagePath: /dev/termination-log
spec:
  terminationGracePeriodSeconds: 60   # LLM 流式请求可能较长，给足收尾时间
```

LLM 服务有个特殊点：**单个流式请求可能持续几十秒**。如果宽限期太短，正在生成回答的请求会被掐断。所以推理服务的 `terminationGracePeriodSeconds` 往往要调大，配合前面的就绪探针（把 Pod 摘出流量池后，新请求不再进来，存量请求有时间吐完）。

## 小结

探针是 K8s 自我修复的"感官"：存活探针决定要不要重启（查不可恢复故障），就绪探针决定要不要接流量（查可恢复状态），启动探针给慢启动服务一个不受打扰的加载期——**三个探针各管一件事，别混用同一接口**。配合优雅退出（摘流量 → SIGTERM → 超时强杀），Pod 的整个生命周期才算闭环。下一篇讲这闭环里最常见的一个操作：滚动更新——新版本怎么无声无息地替换旧版本，出事了又怎么一键回滚。
