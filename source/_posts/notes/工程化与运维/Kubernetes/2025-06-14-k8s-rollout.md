上线新版本是运维里最高频也最紧张的动作。传统方式里"停服更新"已经不可接受——用户正在用你的服务，你不能让他们等。K8s 的 Deployment 把发布做成了内置能力：**滚动更新（Rolling Update）**——不中断服务地逐个替换旧副本，过程中随时可以暂停、恢复、回滚。这篇把滚动更新的机制讲透，重点是控制发布节奏的两个参数，以及出问题时怎么快速回到安全状态。

## 滚动更新的过程

对 Deployment 执行更新（换镜像 tag、改配置）后，K8s 会创建一个新的 ReplicaSet，然后**渐进式地**把流量从旧 Pod 切到新 Pod：

```bash
kubectl set image deployment/rag-api api=registry.example.com/rag-api:1.1
```

默认策略下，K8s 的节奏是：先起一个新的（新 ReplicaSet 从 0 到 1），等它就绪后，停一个旧的（旧 ReplicaSet 从 3 到 2），再起第二个新的……直到全部替换完成。

整个过程由两个参数控制节奏：

- **maxSurge**：更新期间允许超出期望副本数的最大数量。默认 25%（`replicas: 4` 时最多 5 个），决定"一次最多新起几个"。
- **maxUnavailable**：更新期间允许不可用的最大数量。默认 25%，决定"一次最多停几个旧的"。

```yaml
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # 一次最多多起 1 个新 Pod
      maxUnavailable: 0    # 更新期间不允许有 Pod 不可用（先起新的，就绪了再停旧的）
```

`maxUnavailable: 0` 加 `maxSurge: 1` 是**零停服**的保守配置：永远先确认新 Pod 健康，才停一个旧 Pod。代价是更新期间资源占用会短暂超过副本数，集群要有余量。反过来，想快速更新（能容忍短暂少量不可用）就调大 maxUnavailable。

关键点：**滚动更新依赖就绪探针**。K8s 每起一个新 Pod，都要等它就绪（readinessProbe 通过）才继续下一步。如果新版本有 bug、就绪探针一直失败，滚动更新会卡住——不会继续停旧 Pod，服务整体不受影响（这正是前面把探针讲透的原因，探针不灵，滚动更新就瞎）。

## 发布过程的观察与控制

```bash
kubectl rollout status deployment/rag-api      # 阻塞查看更新进度
kubectl rollout history deployment/rag-api      # 查看发布历史
kubectl rollout pause deployment/rag-api        # 暂停更新（灰度观察）
kubectl rollout resume deployment/rag-api       # 恢复更新
```

实践里很有用的一个组合：**发布后先 pause，观察新 Pod 的日志和指标，确认没问题再 resume**——相当于手动灰度：

```bash
kubectl set image deployment/rag-api api=...:1.1
kubectl rollout pause deployment/rag-api    # 起 1 个新的就停住
# ... 观察新 Pod 表现 ...
kubectl rollout resume deployment/rag-api   # 确认没问题，放行剩余替换
```

## 回滚：一键回到上一个版本

新版本上线后发现问题（错误率上升、响应变慢、用户投诉），第一时间不是查 bug，而是**先回滚止血**：

```bash
kubectl rollout undo deployment/rag-api
```

回滚到上一个版本：

```bash
kubectl rollout undo deployment/rag-api --to-revision=2   # 回滚到指定版本
```

回滚同样走滚动更新的流程——先起旧版本的 Pod，确认就绪再停新版本的，服务不中断。这就是 Deployment 相比"手动管理 Pod"的决定性优势：**每一次发布都留了后路，出问题永远有安全出口。**

一个常见的运维心法：**先回滚、再排查**。线上事故的第一要务是恢复服务，不是定位根因。回滚到已知良好的版本让服务先恢复，再从容地在新版本上排查问题——而不是让用户陪着你在坏版本上等修复。

## 不可变更新与蓝绿发布的取舍

滚动更新适合绝大多数场景，但有两种情况要额外考虑：

**情况一：数据库结构变更（migration）。** 滚动更新时新旧版本会短暂共存——如果新版本要改数据库表结构，而旧版本还在用旧结构，可能出现兼容问题。这类发布要先用 migration 作业把库迁好，或采用先扩容后切换的方式，避免新旧版本同时打一个库。

**情况二：推理服务版本切换。** 模型推理服务加载权重慢，滚动更新时新旧模型短暂并存、显存翻倍，小集群可能扛不住。这时可以考虑**蓝绿发布**（一次性起整套新版本，验证后切流量）——它不属于 Deployment 的默认能力，需要借助 Service 切换标签或 Argo Rollouts 这类工具实现，属于进阶话题，这里先留个印象。

## 小结

滚动更新让"发布不中断、出事能回滚"成为默认能力：maxSurge 和 maxUnavailable 控制发布节奏，就绪探针是每步推进的安全闸门，`rollout pause` 支持手动灰度，`rollout undo` 一键止血。运维心法是先回滚再排查，别让用户在坏版本上等。到这里，无状态应用的发布闭环已经完整——下一篇补上有状态的那块：数据库这类数据要持久化的服务，在 K8s 里怎么管理存储。
