第一次把本地跑得好好的服务部署到服务器，结果在别人机器上一启动就崩，是最常见也最让人崩溃的经历。查来查去，多半是环境不一致：本地 Python 3.11，服务器是 3.8；本地装了系统库，服务器没有；本地用的依赖版本和 lock 文件对不上。**Docker 解决的就是这个问题——把应用和它依赖的整个环境打包在一起交付，让"在我机器上能跑"变成"在任何机器上都能跑"。**

## 容器和虚拟机的本质区别

要理解 Docker，先分清"容器"和"虚拟机"这对容易混淆的概念。虚拟机在物理机上虚拟出一整套硬件，每个虚拟机里跑一个完整的操作系统（Guest OS），启动一个虚拟机要几十秒，占用几个 GB 内存。

容器则完全不同：**它不虚拟硬件，只隔离进程**。所有容器共享宿主机同一个 Linux 内核，容器里的"操作系统"只是应用运行所需的最小文件集合（依赖库、配置文件、可执行文件）。所以：

- 启动一个容器是秒级，虚拟机是分钟级；
- 一个容器只占几十 MB，虚拟机动辄几个 GB；
- 一台机器能同时跑几百个容器，虚拟机可能十几个就顶满了。

代价是隔离性比虚拟机弱——容器共享内核，内核一旦被攻破，所有容器都受影响。所以生产环境里"安全要求极高"和"需要跑 Windows 应用"的场景仍用虚拟机，其余大部分服务都可以容器化。

## 镜像与容器：类与实例

Docker 里最核心的一对概念是**镜像（Image）**和**容器（Container）**。打个比方：镜像是"类"，容器是"类的实例"。

- **镜像**是只读的模板，里面装着应用代码、运行时、依赖、配置，由一层层文件系统叠加而成。镜像是静态的，可以被复制、分发、版本化。
- **容器**是镜像运行起来后的进程实例，有自己可写的一层文件系统。同一个镜像可以启动任意多个容器，互不影响。

```bash
docker pull python:3.11-slim    # 拉取镜像
docker run -it python:3.11-slim bash   # 用镜像启动一个容器并进入 shell
```

`run` 的时候如果本地没有这个镜像，Docker 会自动去仓库（默认 Docker Hub）拉取。这也是 Docker 好用的地方——**一条命令就把别人的镜像拿过来直接用**，不用自己从头搭环境。

## 为什么 AI 应用团队更需要 Docker

对做大模型应用的人来说，容器化的需求比传统后端更迫切，原因有三个：

**第一，模型服务的依赖极其挑剔。** CUDA、cuDNN、PyTorch 的版本互相咬合，装错一个版本推理就报错。把 vLLM、向量库、推理引擎各自容器化，版本冲突被隔离在不同容器里，互不干扰。

**第二，交付链路长。** 你本地调好的 RAG 服务要经测试环境、预发环境最后上生产，每个环节环境一致，才不会有"测试没问题上线就挂"。镜像在哪个环节构建，就在哪个环节运行，从源头消灭环境漂移。

**第三，弹性扩缩容的前提。** 无论用 Docker Compose 在单机编排，还是上 Kubernetes 做集群调度，第一步都是"服务能被镜像化、能被一键拉起"。容器是后面所有自动化操作的最小单元。

## 一次构建，处处运行

把整个流程串起来看，Docker 的工作流是：

```bash
# 1. 写 Dockerfile 描述环境怎么构建
# 2. 构建镜像
docker build -t myapp:1.0 .
# 3. 推送镜像到仓库（团队共享 / 部署用）
docker push registry.example.com/myapp:1.0
# 4. 在任意装了 Docker 的机器上运行
docker run -d -p 8000:8000 registry.example.com/myapp:1.0
```

镜像带标签（`1.0`）管理版本，环境从开发到生产完全一致。出问题时还能用同一个镜像在本地复现——这是排查线上问题最有力的手段之一：**"线上跑的是哪个镜像，本地就拉哪个镜像来跑。"**

## 小结

这一篇解决了"是什么、为什么"：容器是共享内核的进程隔离，镜像与容器是模板与实例的关系，AI 应用的挑剔依赖让它格外需要容器。下一篇进入实操，讲 Docker 的核心概念和日常使用频率最高的命令——镜像管理、容器生命周期、日志与进入容器调试，把这套命令练熟，后面的 Dockerfile 和编排才有基础。
