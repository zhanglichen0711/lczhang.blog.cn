大模型应用有个传统软件没有的运营难题：**每一笔"收入"背后都有真实的"成本"，而且成本随用量线性增长**——用户每问一次，你都要付模型厂商一次 token 费。请求量上去之后，如果成本不可见、不可控，月底账单会给你"惊喜"。更隐蔽的是，**成本不是均匀分布的**：一个重度用户、一个写坏的循环 Agent、一个被爬虫狂刷的接口，可能烧掉整体成本的一大半。这篇讲清楚 token 成本怎么监控、怎么分析、怎么设配额治理。

## 为什么必须单独做成本监控

成本问题有三个特征，决定了它不能靠"事后看账单"：

**第一，成本是实时的、逐 token 累积的。** 传统 SaaS 的成本主要是固定的服务器开销，用多用少差别不大。LLM 应用的成本直接绑定在每次调用上，一个异常（循环 Agent、被刷接口）可能在几小时内烧掉平时一个月的量。**等月底账单出来再发现，钱已经花了。**

**第二，成本藏在链路深处。** 一次 RAG 回答可能产生多次模型调用：查询改写一次、Embedding 一次、生成一次、如果接了个质量评估模型又加一次。每个环节用的模型不同、单价不同。不逐环节记录，根本不知道钱花在哪一步。

**第三，成本和质量有冲突，需要数据说话。** 用贵的大模型效果确实好，但贵多少、好多少，没有数据就无法决策。成本监控提供的不只是"花了多少"，还有"花在哪、值不值"。

## 成本数据的来源与记录

成本数据从哪来？**每一次模型调用的 usage 字段**——OpenAI 兼容 API 的响应里都带 token 计数：

```json
{
  "usage": {
    "prompt_tokens": 1520,
    "completion_tokens": 380,
    "total_tokens": 1900
  }
}
```

要把它变成"成本"，还需要**单价表**——每个模型每百万 token 多少钱（输入/输出分开计价）。这部分可以交给追踪平台（Langfuse 内置各家模型的计价表，自动算成本），也可以自己在代码里按 `model + usage` 折算。

埋点记录时，成本数据要带够维度标签，才能回答"钱花哪了"：

```python
# 记录成本时带上维度
langfuse_context.update_current_observation(
    usage={"input": usage.prompt_tokens, "output": usage.completion_tokens},
    metadata={
        "model": model_name,        # 按模型看：哪个模型最烧钱
        "feature": "rag_generate",  # 按功能看：检索还是生成占大头
        "user_id": user_id,         # 按用户看：谁用量异常
        "session_id": session_id,
    },
)
```

三个必带的维度是 **model / feature / user_id**：按模型看单价影响，按功能看流程设计问题，按用户看滥用与大户。

## 成本看什么：三张关键的账

**账一：总成本趋势。** 每天/每周总 token 消耗和成本的曲线。看的是整体——是不是随着用户增长线性涨？有没有突然的台阶（可能某次发布改了模型或逻辑）？

**账二：成本分布。** 按功能、按模型拆解。RAG 服务里"模型生成"和"Embedding"各占多少？如果 Embedding 占比异常高，可能是缓存没生效、重复向量化。**分布比总额更能暴露问题。**

**账三：Top 用户/会话。** 单用户成本排行、单会话 token 排行。**Top 1% 的用户可能消耗 20% 的成本**——要么是正常的大客户（该考虑阶梯计价），要么是异常（循环、滥用、爬虫）。发现"单会话 token 突然暴涨"，多半是有 Agent 在循环空转。

## 配额与熔断：成本失控的最后防线

监控只是"看得见"，治理才是"控得住"。成本治理的手段按干预强度排列：

**第一层：按用户/租户设配额。** 给每个用户或租户配置额度（每日/每月 token 上限或金额上限），超了限速或降级（改用便宜的小模型）：

```python
class QuotaError(Exception): pass

async def check_quota(user_id: str):
    used = await redis.get(f"quota:{user_id}:{today}")
    if int(used or 0) > USER_DAILY_LIMIT:
        raise QuotaError("今日额度已用完")

async def track_usage(user_id: str, tokens: int):
    pipe = redis.pipeline()
    pipe.incrby(f"quota:{user_id}:{today}", tokens)
    pipe.expire(f"quota:{user_id}:{today}", 86400)
    await pipe.execute()
```

**第二层：单请求/单会话上限。** 单个请求设置最大 token 数（`max_tokens` 本身就是预算）；单会话设置最大轮次和总 token 上限——**这是防循环 Agent 空转烧钱的关键阀门**，超过就强制结束会话。

**第三层：熔断与告警。** 全局成本异常时自动熔断：某模型调用错误率飙升（可能配置写错导致疯狂重试）、某接口成本半小时内超阈值——触发告警甚至自动降级（把模型从大模型切到小模型，保住服务不断）。

**第四层：缓存兜底。** 前面 Redis 系列讲过的语义缓存在这里是降本利器——相似问题命中缓存，直接省掉一次模型调用。**成本治理里最有效的往往不是限制，而是别让重复的调用发生。**

## 成本监控与告警的指标设计

落到指标上，Prometheus 里值得长期跟踪的几组：

```promql
# 每日总成本（按模型拆）
sum by (model) (increase(llm_cost_total[24h]))

# 单次请求 token 的 P95（异常高的尾巴 = 潜在循环）
histogram_quantile(0.95, sum(rate(llm_tokens_per_request_bucket[5m])) by (le))

# 成本增速（环比突增告警）
sum(increase(llm_cost_total[1h])) / sum(increase(llm_cost_total[1h] offset 24h))
```

告警规则的心法：**成本告警的阈值要按"绝对值 + 增速"双维度**——绝对值防单次大额，增速防缓慢失控。成本异常通常不是瞬间发生的，增速告警能早几天发现问题。

## 小结

成本治理四件事：埋点记录（usage + model/feature/user 维度）→ 三张账分析（趋势、分布、大户）→ 配额熔断（用户额度、单会话上限、异常熔断、缓存兜底）→ 指标告警（绝对值 + 增速）。大模型应用的成本是实时流动的，**看不见就失控，看见了才有治理的前提**。整个可观测系列的方法论都齐了——最后一篇实战收口：给一个真实的 RAG 服务从零搭一套完整观测体系。
