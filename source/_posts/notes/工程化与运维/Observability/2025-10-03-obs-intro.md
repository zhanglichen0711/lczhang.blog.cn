服务上线只是开始，真正考验人的是**它跑起来之后出了事你能不能快速定位**。传统后端靠监控（monitoring）就够了——CPU 高不高、接口慢不慢。但 LLM 应用把问题的复杂度抬升了一个量级：回答变差了，是检索没召回相关内容，还是模型没遵循指令？回答变贵了，是哪一步吞掉了大部分 token？请求超时了，是向量库慢还是模型慢？**这类"黑盒里的白盒问题"，靠单一手段说不清，需要日志、指标、追踪三件套配合——这就是可观测性（Observability）。**

## 三大支柱：日志、指标、追踪

可观测性有个经典框架叫"三大支柱"，各回答一个问题：

**日志（Logs）**回答"发生了什么"。一条条带时间戳的事件记录：谁在什么时间请求了什么、报了什么错、返回了什么。日志最细、最全，但也是三样里最"散"的——出问题时要靠关键字搜索。

**指标（Metrics）**回答"有多少/多快/多差"。聚合后的数值：QPS、P95 延迟、错误率、token 消耗量。指标是"仪表盘"，一眼看出整体健康度，但它不告诉你"具体哪个请求出了问题"。

**追踪（Traces）**回答"一个请求内部，时间花在了哪一环"。把一次请求拆成一棵树：检索花了 300ms、重排花了 50ms、模型生成花了 2s——每一环的耗时和结果都清晰可见。

三者关系可以这样记：**指标告诉你有病，日志告诉你症状，追踪告诉你病灶。** 只用其中任何一个都会抓瞎——指标报警了但不知道哪个请求有问题，日志刷屏了但不知道影响面多大，追踪很精细但你不盯着看就发现不了异常。

## LLM 应用的可观测性：普通监控不够了

传统监控对 LLM 应用有个盲区：**它只能看到"服务层"的动静（请求数、延迟、错误码），看不到"智能层"发生了什么**。LLM 应用的独特问题在于：

**第一，输出是"质量"问题，不是"错误"问题。** 接口返回 200、延迟正常、没有报错——但回答是错的、是幻觉、是答非所问。传统监控完全感知不到，因为没有"异常"信号。要对齐的是**回答质量**，需要把每次调用的输入输出记录下来供复盘。

**第二，成本是逐 token 累积的。** 一次调用贵不贵、一个用户一个月烧掉多少钱，传统监控不统计 token。成本问题需要按模型、按功能、按用户维度统计 token 消耗。

**第三，链路是多环节的。** RAG 一次回答要经过查询改写 → 向量检索 → 重排 → 拼 prompt → 模型生成。任何一环出问题都影响最终结果，可传统监控只看到"接口总耗时 3 秒"，不知道 2.5 秒花在了模型生成上。

所以 LLM 应用的可观测性 = 传统三件套（日志/指标/追踪）+ **LLM 专属的调用追踪**（每次调用的 prompt、输出、token、成本、模型参数）+ **质量评估**（回答好不好）。这也是 Langfuse、LangSmith 这类 LLMOps 工具存在的理由——它们把"追踪"这一支柱延伸到了智能层。

## 可观测性的分层落地

对一个 RAG 服务，完整的可观测体系大致分层：

```
服务层（传统手段）
 ├── 日志：访问日志、错误日志（结构化、带 request_id）
 ├── 指标：QPS、P95 延迟、错误率、CPU/内存（Prometheus + Grafana）
 └── 追踪：跨服务调用链（可选，服务多了再上）
智能层（LLM 手段）
 ├── 调用追踪：每次 LLM 调用的输入/输出/token/成本/延迟
 ├── 检索追踪：query 是什么、召回了几条、每条相关性
 └── 质量评估：回答评分、用户反馈、幻觉检测
```

这个系列接下来会按这个框架逐层展开：先讲日志怎么记录才可查，再讲指标监控怎么搭，然后用几篇讲 LLM 调用追踪（Langfuse 接入、Agent 追踪、成本监控），最后用一篇实战把整个体系串起来。

## 小结

可观测性是"服务上线后的生存能力"：日志回答发生了什么，指标回答有多少，追踪回答在哪一环——三者配合才能快速定位问题。LLM 应用在这个基础上还要多一层：追踪智能层的调用（prompt、token、成本、质量），因为它的"故障"常常不是报错，而是"回答变差"。下一篇从最基础也最重要的日志讲起：什么样的日志才是能帮你排查问题的日志。
