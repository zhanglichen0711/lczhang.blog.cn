用缓存最怕的不是"缓存没生效"，而是"缓存失效引发连锁灾难"。面试必问、生产必踩的三座大山：**穿透、击穿、雪崩**。名字像绕口令，成因和防线完全不同。这一篇逐个拆开。

## 先画一张访问链路

```text
用户请求 → Redis 有缓存？
   ├─ 命中 → 直接返回
   └─ 未命中 → 查 MySQL / 调 LLM → 结果写回缓存 → 返回
```

三个灾难都发生在"**缓存未命中，请求打到后端**"这条支路上，只是触发的方式和规模不同。

## 穿透：查了一个"根本不存在"的东西

**成因**：请求查的数据在缓存和数据库里**都不存在**。比如恶意脚本用不存在的 doc_id 疯狂刷接口——缓存永远不命中，每次请求都穿透到 MySQL，把数据库打挂。

```text
请求 doc:99999（不存在）
→ 缓存 miss → 查库 miss → 不写缓存？→ 下次又来…… 数据库被无效查询打垮
```

**防线**（三层，按成本从低到高）：

1. **参数校验前置**：接口层直接拦掉明显非法的请求（id 格式不对、超出范围）；
2. **缓存空值**：查库也不存在时，把一个"空结果 + 短过期"写进缓存（如 60 秒），挡住同一无效 key 的重复穿透：

```python
def get_doc(doc_id: int):
    cached = r.get(f"doc:{doc_id}")
    if cached is not None:
        return None if cached == "EMPTY" else json.loads(cached)

    doc = db.query(doc_id)
    if doc is None:
        r.set(f"doc:{doc_id}", "EMPTY", ex=60)   # 空值也缓存，只挡 60 秒
        return None
    r.set(f"doc:{doc_id}", json.dumps(doc), ex=3600)
    return doc
```

3. **布隆过滤器**（可选）：key 太多、想彻底挡无效 key 时，启动时把全量合法 id 灌进布隆过滤器，请求先过过滤器——不在集合里直接拒绝，不进缓存也不进库。

## 击穿：一个热 key 在过期瞬间被打爆

**成因**：某个**特别热**的 key（比如全网都在搜的"拆模强度要求"）刚好过期，一瞬间大量请求同时 miss，全部涌向后端。打的是"单点压力"。

**防线**：

1. **互斥锁（最常用）**：缓存失效时，只放一个请求去重建缓存，其他请求等它建好再读：

```python
def get_hot(key: str, rebuild):
    cached = r.get(key)
    if cached:
        return cached
    # 只有一个线程能拿到锁去重建，其余短暂自旋等待
    if r.set(f"lock:{key}", "1", nx=True, ex=10):
        try:
            value = rebuild()          # 查库/调 LLM
            r.set(key, value, ex=3600)
            return value
        finally:
            r.delete(f"lock:{key}")    # 建完释放锁
    else:
        time.sleep(0.05)
        return get_hot(key, rebuild)   # 递归等别人建好
```

2. **逻辑过期**：缓存永不过期（物理上），但在 value 里带一个逻辑过期时间；读到过期就异步去刷新，请求先返回旧值——用户永远不 miss。

## 雪崩：大批 key 同时过期 / 缓存整体宕机

**成因**：不是单个 key，而是**一大批 key 在同一时间过期**（比如统一设了 3600 秒、同一时刻上线），或 Redis 整个宕了。所有请求同时 miss → 数据库被瞬时洪峰打垮。

**防线**：

1. **过期时间加随机抖动**——避免"集体过期"：

```python
import random
expire = 3600 + random.randint(0, 600)   # 3600~4200 随机
r.set(key, value, ex=expire)
```

2. **热点数据分散过期**——同类 key 分几个批次设不同过期时刻；
3. **多级缓存兜底**——Redis 之上加一层本地缓存（如进程内 LRU），Redis 挂了还有本地挡一阵；
4. **后端限流降级**——数据库扛不住时直接返回降级结果（旧缓存、提示稍后），别硬扛。

## 三个问题的对比记忆

| | 穿透 | 击穿 | 雪崩 |
| --- | --- | --- | --- |
| 查的东西 | 缓存和库都不存在 | 热 key 过期瞬间 | 大量 key 同时过期 / 实例宕机 |
| 压力点 | 无效流量打库 | 单个热 key 打库 | 洪峰全量打库 |
| 关键防线 | 空值缓存 / 参数校验 | 互斥锁重建 | 过期加抖动 / 多级缓存 |

**一句话串记**：穿透是"打一个不存在的东西"，击穿是"一个热的过期了"，雪崩是"一批同时过期或整个挂了"。各自防线分别是：空值缓存、互斥锁、过期加随机。

## 小结

三个灾难本质都是"缓存 miss 的流量没人兜住"。工程上的通用心法是：**让 miss 的成本可控**——要么缓存空值挡无效流量（穿透），要么锁住重建（击穿），要么错开过期时间、留好降级预案（雪崩）。缓存方案设计的重点从来不是"加一层缓存"，而是"缓存失效时系统还站得住"。
