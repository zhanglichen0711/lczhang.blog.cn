缓存能扛读流量，但引入它就有个绕不开的问题：**数据库更新了，缓存还是旧的**——用户看到的数据不一致。这一篇从根源讲起，给出工程上最常用的 Cache Aside 方案，以及"先删缓存还是先更新数据库"的经典争论。

## 不一致是怎么来的

缓存和数据库是两份数据，任何更新都有先后顺序。只要不是原子操作，就存在"中间态"：某一步做完、另一步没做时，读请求可能读到旧缓存或旧库。**一致性问题的本质：更新链路里有两步，两步之间有人插队读了旧数据。**

## 主流方案：Cache Aside（旁路缓存）

Cache Aside 是目前工程上最主流的缓存模式，四条规则：

- **读**：先读缓存，命中直接返回；miss 则读库、写回缓存；
- **写**：先更新数据库，再**删除缓存**（不是更新缓存）；
- **为什么删除而不是更新**：更新缓存要先算好新值（可能要经过复杂计算），而删除只需一条命令；下次读 miss 时自然重建。删除更简单也更不容易出错。

```python
def update_doc(doc_id: int, new_title: str):
    # 1. 先更新数据库（事务内）
    db.update(Doc, doc_id, title=new_title)
    # 2. 再删缓存
    r.delete(f"doc:{doc_id}")
```

读路径：

```python
def get_doc(doc_id: int):
    cached = r.get(f"doc:{doc_id}")
    if cached:
        return json.loads(cached)
    doc = db.query(doc_id)              # 缓存 miss → 读库
    r.set(f"doc:{doc_id}", json.dumps(doc), ex=3600)
    return doc
```

## 遗留问题：两个经典竞态

Cache Aside 简单，但有两个竞态窗口，要心里有数：

### 竞态一：先删缓存，后更新库失败

```python
# 错误顺序：先删缓存
r.delete(key)
db.update(...)      # ← 这步失败，库没更新，缓存却没了
```

下次请求读库还是旧值，写回缓存——**旧值被重新缓存**，问题被放大。

**正确顺序是先更新库再删缓存**：库更新成功了缓存才被删；如果删缓存失败，大不了多一次旧缓存读取，等 TTL 过期后自然修正——**数据库为准，缓存最终一致**。

### 竞态二：删缓存瞬间，读请求把旧值写回

即使顺序正确（先更库、再删缓存），仍有一个极窄窗口：

```text
线程 A：更新库 → 删除缓存
线程 B：                此刻读缓存 miss → 读库（读到的是……）
```

如果线程 B 在 A 更新库**之前**发起读库、在 A 删缓存**之后**写回缓存，B 写回的是旧值——旧值又被缓存了。这就是所谓的"脏缓存"窗口。

**缓解手段**：

1. **延迟双删**：更新库后，删一次缓存，**睡几百毫秒再删一次**——给读请求留出把旧值写回的时间窗，第二删把它清掉：

```python
def update_doc(doc_id: int, payload):
    db.update(Doc, doc_id, payload)
    r.delete(f"doc:{doc_id}")
    time.sleep(0.5)                  # 等可能的旧值写回窗口过去
    r.delete(f"doc:{doc_id}")        # 再删一次，清掉被写回的旧值
```

2. **缓存带短 TTL 兜底**：就算脏值被写回，短过期（如 60 秒）也能自动修正，把"不一致时长"限制在可控范围内。

## 什么时候不能只用缓存删除

**计数类**数据（文档被引用次数、阅读量）不适合"删缓存"模式——它们高频累加，删了缓存等于每次都要重建。这种情况用**直接更新缓存 + 原子操作**（`INCR`）更合适，而且 Redis 的原子命令本身没有竞态：

```python
# 阅读量：库里的计数最终落库，缓存里先原子累加
r.incr(f"doc:{doc_id}:hits")
# 定期把缓存计数刷进 MySQL（异步批量）
```

计数一致性是"最终一致"的典型：缓存即时累计、定期落库，短期不一致可以接受。

## 一致性级别要选对

没有银弹，先想清楚你的业务**能容忍多久的不一致**：

| 业务 | 可容忍不一致 | 方案 |
| --- | --- | --- |
| 文档标题/内容 | 秒级可接受 | Cache Aside + 双删 + TTL |
| 计数（阅读量/热度） | 分钟级 | 缓存原子累加，定期落库 |
| 权限/价格/库存 | 尽量为零 | 别用缓存承载，或加锁/事务 |
| 会话状态 | 会话级 | TTL + 直接读写缓存为主 |

**权限这类"错了就出事"的数据，不要放进普通缓存**——宁可每次查库，也不要为省一次查询冒越权风险。这是数据与存储设计里最重要的一条红线。

## 小结

缓存一致性的工程共识：**Cache Aside（更新库 + 删缓存）打底，延迟双删 + 短 TTL 收窄竞态窗口，计数类走原子累加，敏感数据不缓存**。理解一致性不是"消除"，而是"把不一致窗口压到业务能接受的程度"。
