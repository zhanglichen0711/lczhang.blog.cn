Redis 默认把数据放内存，但内存一断电就清空。如果你的 Redis 里存着"重建成本高"的数据（缓存能重建无所谓，会话、计数丢了就麻烦），就得开持久化——让数据在重启后还能回来。Redis 提供两套持久化机制：**RDB**（快照）和 **AOF**（日志），这一篇把原理、取舍和组合策略讲清楚。

## RDB：定期打快照

RDB 是"按时间点把内存里所有数据**压缩存成一份文件**"（dump.rdb）。类似给数据库拍快照：

```conf
# redis.conf
save 900 1       # 900 秒内至少 1 次写 → 触发快照
save 300 10      # 300 秒内至少 10 次写 → 触发快照
save 60 10000    # 60 秒内至少 1 万次写 → 触发快照
```

**优点**：

- 恢复极快——把快照文件 load 进内存即可，适合重启恢复和备份迁移；
- 文件紧凑——一份压缩二进制，做灾备、迁移都很方便。

**缺点**：**有丢失窗口**。快照是"某个时间点"的状态，两次快照之间的写操作如果发生宕机，全部丢失。`save 300 10` 意味着最坏可能丢最近 5 分钟的数据。

## AOF：追加写日志

AOF 把**每一条写命令**追加到一个日志文件里，重启时把日志重放一遍就恢复了数据。它解决了 RDB 的丢失窗口问题：

```conf
# redis.conf
appendonly yes
appendfsync everysec   # 每秒把缓冲区的日志刷到磁盘（默认）
```

`appendfsync` 决定"多久刷一次盘"，是**性能 vs 数据安全**的旋钮：

| appendfsync | 行为 | 最坏丢数据 | 性能影响 |
| --- | --- | --- | --- |
| always | 每条命令都刷盘 | 不丢（只丢正在写的一条） | 慢，吞吐下降明显 |
| everysec | 每秒批量刷一次 | 最多丢 1 秒 | 小（默认推荐） |
| no | 交给操作系统 | 不定（可能丢几秒~几十秒） | 最快 |

**优点**：数据更安全（everysec 最多丢 1 秒），日志可读可审计。

**缺点**：

- 文件比 RDB 大（命令文本），恢复比 RDB 慢（要重放全部日志）；
- 日志无限增长需要**重写（rewrite）**机制压缩——Redis 会把日志压缩成"当前状态的紧凑命令"，周期性自动做。

## 直接对比

| | RDB | AOF |
| --- | --- | --- |
| 数据形态 | 二进制快照文件 | 追加的写命令日志 |
| 丢失窗口 | 两次快照之间（可能分钟级） | everysec 最多 1 秒 |
| 恢复速度 | 快（直接加载） | 慢（重放日志） |
| 文件大小 | 小、紧凑 | 大、需定期 rewrite |
| 适合 | 备份、迁移、快速恢复 | 数据安全要求高的主实例 |

## 工程上的组合策略

**生产环境两者一起开**，Redis 默认配置正是如此：AOF 保证"重启少丢数据"，RDB 提供"快速恢复 + 备份文件"。恢复时 Redis 优先用 AOF（数据更全）。

按数据性质定方案：

```text
缓存类（可重建）：可不开持久化 / 开 RDB 做兜底 —— 丢了重新攒即可
会话/计数（短期有价值）：开 AOF everysec —— 最多丢 1 秒
订单/核心业务：不该只靠 Redis 持久化 —— 数据最终要在 MySQL
```

判断口诀还是那条：**"丢了能不能重建"决定要不要持久化、用多强的持久化**。纯缓存 Redis 开持久化反而拖累性能还浪费磁盘，不需要。

## 一个真实的坑：fork 阻塞

RDB 快照和 AOF rewrite 都依赖 **fork 子进程**来做（主进程继续服务）。数据量大时 fork 瞬间会短暂阻塞主进程（毫秒到百毫秒级）。所以：

- 别把大实例的 RDB 存盘频率设得太高；
- 监控 `latest_fork_usec`，fork 耗时异常要警惕；
- 内存占用太高的实例，快照写盘期间 I/O 压力大，注意错峰。

## 小结

RDB 管"快速恢复与备份"，AOF 管"少丢数据"，生产默认双开各取所长。真正要动脑的不是"开哪个"，而是**结合数据性质决定持久化级别**——纯缓存不开、会话类 AOF、核心数据不进 Redis。Redis 是内存数据库，持久化只是它的"保险"，不该当主存储用。
