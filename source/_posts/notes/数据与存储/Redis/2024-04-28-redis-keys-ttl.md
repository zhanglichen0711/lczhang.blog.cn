数据类型是 Redis 的"工具箱"，键则是"标签"。键设计得好不好，直接决定代码可读性、排查便利性和缓存正确性。这一篇把键操作的几个关键动作讲透：命名规范、条件写入、过期时间。

## 键命名规范：用冒号分层

Redis 的键是字符串，但**不要随手乱写**。社区通行规范是"用冒号把实体和属性串起来"，像文件的目录层级：

```bash
# 反例：语义模糊，无法归类
SET doc42          "数据"
SET user1          "张三"

# 正例：实体:ID:属性，清晰可读
SET doc:42:title    "GB50204-2015"
SET user:1:name     "张三"
SET user:1:role     "quality"
```

冒号分层的两个直接收益：

1. **可读性与可推断性**——`doc:42:title` 一眼看出"文档 42 的标题"；排查线上数据时，`KEYS doc:*` 就能浏览某一类键（下面会说 KEYS 的坑）；
2. **按前缀管理**——想给某类键统一加过期、统一删除（比如用户下线清掉他所有会话键），前缀就是分组依据。

统一规范建议：**`实体:主键:属性`**，如 `session:{user_id}`、`cache:faq:{question_hash}`。

## SET 的条件选项：NX 与 XX

`SET` 不只是赋值，带选项能表达"只在某种条件下写"，这是实现锁和防覆盖的基础：

```bash
SET lock:doc:42 "job-1" NX EX 10
# NX：键不存在才写成功（返回 OK）；已存在则失败（返回 nil）
# EX 10：10 秒后自动过期

SET cache:key "value" XX
# XX：键已存在才更新（防止把还没建好的缓存写坏）
```

`NX` 的典型用途就是**分布式锁**：多个进程同时 `SET lock NX`，只有一个能成功——拿到锁的人才算抢到。这个在第 9 篇展开。

## 过期时间：缓存的"保质期"

Redis 键可以设过期时间，到期自动删除——**这是它当缓存的核心能力**：

```bash
SET cache:faq:ab12 "答案内容" EX 3600
# 1 小时后自动消失

EXPIRE cache:faq:ab12 7200    # 对已有键重新设过期
TTL cache:faq:ab12            # 查看剩余秒数（-1 永久，-2 不存在）
```

过期的三种实用场景：

1. **缓存结果**——FAQ 答案缓存 1 小时，命中期内免 LLM 调用；
2. **临时状态**——验证码 5 分钟有效、限流窗口 1 分钟重置，到期自动清理不用人删；
3. **锁的自动释放**——`SET NX EX` 里的 EX 就是防"拿到锁的进程挂了，锁永远不释放"。

一个细节：**要"写入即带过期"，一定用 `SET key val EX n` 一步完成**，不要先 SET 再 EXPIRE——两条命令之间有窗口，进程崩在中间就留下了永不过期的键。

## 别在生产用 KEYS

新手查数据习惯 `KEYS cache:*`——它会**遍历全库所有键**，在键多的实例上会阻塞 Redis 数秒，生产环境直接拖垮服务。替代方案：

```bash
# 大批量安全扫描（cursor 游标分批，不阻塞）
SCAN 0 MATCH cache:faq:* COUNT 100
```

或者更好——**键设计好前缀后，靠业务访问而不是扫描**。需要"查一类数据"说明当初没设计好查询键。

## 过期 vs 删除：谁负责清理

过期键真正被删除有三种时机：访问时惰性删除、定期抽样删除、内存不够时按淘汰策略清理（`maxmemory-policy`）。理解这点就明白一个常见误区：**键到期不是"立刻消失"**，极端情况下可能短暂残留——所以缓存必须容忍"多存在一会儿"，业务上不能依赖"过期即失效"的精确性（比如用了它做权限开关就危险）。

## 小结

键操作三件事记牢：**命名用冒号分层（实体:主键:属性）、条件写入用 NX/XX、一切临时数据都带 EX 过期**。键有章法，后面的缓存策略、锁、会话设计才有干净的地基。
