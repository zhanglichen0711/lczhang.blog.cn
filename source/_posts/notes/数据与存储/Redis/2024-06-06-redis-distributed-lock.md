单机时代抢资源用进程内锁（`threading.Lock`）就行。服务部署成多个实例后，锁必须跨进程、跨机器——一个实例拿锁，其他实例不能重复执行。这个需求叫**分布式锁**。Redis 因为"快 + 支持原子条件写"，是实现分布式锁最常见的底座。这一篇从最简单可靠的实现讲起，把翻车点全部点出来。

## 为什么单机锁不够

离线任务（文档解析、向量化入库）如果用进程内锁，每个实例的锁互相看不见：

```text
实例 A：拿锁 → 开始解析 doc:42
实例 B：也拿锁（A 的锁我感知不到）→ 也在解析 doc:42   ← 重复执行
```

两份任务同时跑同一文档，产生重复切片、重复入库。分布式锁要求：**锁的状态放在所有实例都能访问的地方**——Redis 正是这个"共享的地方"。

## 用一条命令实现：SET NX EX

核心就是上一篇提过的条件写：`SET key value NX EX 秒数` 同时满足两个条件才成功——

- `NX`（Not eXists）：键不存在才写入（**互斥**：只有一个实例能写成功）；
- `EX`：带过期时间（**兜底**：拿锁者挂了，锁到点自动释放）。

```python
import uuid
import redis

r = redis.Redis(...)

# 拿锁：value 用唯一标识，防止误删别人的锁
lock_key = "lock:doc-parse:42"
token = uuid.uuid4().hex

if r.set(lock_key, token, nx=True, ex=30):
    # 拿到锁，只有我能执行
    try:
        parse_doc(42)
    finally:
        # 释放前先确认锁还是自己的
        if r.get(lock_key) == token:
            r.delete(lock_key)
else:
    print("别人正在处理，跳过")
```

三个细节决定了这套锁靠不靠谱：

1. **value 必须是唯一 token**——释放锁前先 `GET` 比对是不是自己的锁。否则一个实例的锁过期后，另一个实例拿到锁，前一个实例的 `finally` 却把它删了——**误删别人的锁**，互斥直接失效；
2. **过期时间必须设**——没有 EX，拿锁的进程一崩，锁永远在，全系统死锁；
3. **释放要"先验证再删"**——上面代码的 GET 比对 + DELETE 是两步，中间有竞态。严谨做法用 Lua 保证原子：

```lua
-- 原子释放锁：值匹配才删除
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

## 锁过期了，但任务没跑完怎么办

`EX 30` 是个拍脑袋的值：任务普遍 5 秒能完，但偶尔一次跑了 40 秒——**锁在第 30 秒过期，第二个实例抢到锁，两个实例同时处理同一任务**，互斥被破坏。

解决办法是**续期（看门狗模式）**：拿到锁后起一个后台任务，在锁快过期时自动续期（比如每 10 秒把过期时间续到 30 秒），任务结束才停掉续期。市面上成熟的 Redis 客户端（如 Redisson/Redlock 实现）都内置了这个机制：

```python
# 用成熟库（如 redlock-py / Redisson）就不用手写续期
# 示例：redlock-py 心智
from redlock import Redlock

dlm = Redlock([{"host": "localhost", "port": 6379}])
lock = dlm.lock("lock:doc-parse:42", ttl=30000)   # 库自动续期
try:
    parse_doc(42)
finally:
    dlm.unlock(lock)
```

**建议**：生产环境优先用成熟实现（Redlock、Redisson 的 RedisLock），它把"过期续期、原子释放、重试策略"都处理好了。自己手写锁的续期逻辑容易踩坑。

## 三个经典翻车点自查

| 问题 | 后果 | 对策 |
| --- | --- | --- |
| 忘设 EX / 拿锁进程崩溃 | 锁永不过期，全系统死锁 | 必须 EX，且超时兜底 |
| value 不唯一、释放不比对 | 误删别人的锁，互斥失效 | value 用 uuid，释放前校验 |
| 任务时长 > 锁过期时间 | 锁提前释放，重复执行 | 看门狗续期 / 用成熟库 |

## 业务上还要防重复

分布式锁解决了"两个实例同时干"，但还有个更微妙的场景：**任务在锁的保护下执行到一半，服务重启**——重试机制会把任务再投一次，产生重复处理。所以生产级任务处理通常是"锁 + 幂等"双保险：数据库里给任务加唯一约束（如 `doc_id + batch_no` 唯一索引），重复入库自然失败。**锁挡并发，唯一约束挡重试**，两层都上才稳。

## 小结

Redis 分布式锁的正确姿势：**`SET key uuid NX EX` 拿锁、Lua 原子释放、value 用唯一标识防误删、过期时间兜底、长任务靠看门狗续期**，生产环境直接用成熟库而非手写。分布式锁解决的是"并发抢资源"，而业务正确性还需要幂等设计兜底。
