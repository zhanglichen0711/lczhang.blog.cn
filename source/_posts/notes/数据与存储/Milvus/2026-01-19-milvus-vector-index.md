上一篇建集合时我们声明了"向量字段 + 索引类型 HNSW + 度量 IP"。这一篇把这三件事背后的原理讲清楚——不理解索引，你就永远只会抄别人的参数。核心就两个问题：**向量之间的"相似"怎么度量？海量向量怎么搜得快？**

## 度量方式：什么叫"最接近"

搜索的本质是算问题向量和库内向量的距离，取最近的。Milvus 支持三种主度量，选错会直接影响召回语义：

| 度量 | 计算 | 适合 | 说明 |
| --- | --- | --- | --- |
| `IP`（内积） | 点积 | 向量已归一化时 | 值越大越相似，排序直观 |
| `COSINE`（余弦） | 归一化内积 | 未归一化、只看方向 | 对向量长度不敏感 |
| `L2`（欧氏） | 平方距离 | 几何距离有意义的场景 | 值越小越相似 |

实际工程里最常用的选法是：**embedding 模型是否已归一化**。BGE-M3 这类模型默认输出的向量可以直接用 IP；如果你不确定或向量来源杂，用 COSINE 更稳（余弦只看方向，不受向量长度干扰）。

```python
index_params.add_index(
    field_name="embedding",
    index_type="HNSW",
    metric_type="COSINE",     # 与建集合时 schema 无关，索引时指定即可
    params={"M": 16, "efConstruction": 200},
)
```

一个容易踩的坑：**建索引时定的 metric_type，搜索时必须一致**。数据已经按 IP 建好索引，搜索却传 COSINE，结果会完全不对。

## 暴力搜索为什么不行

最朴素的做法是拿问题向量和库内**每一条**算距离（flat scan）：100 万条 × 1000 维，一次查询要做 10 亿次浮点运算。数据量一上来，单次查询就是几十上百毫秒，并发一高直接扛不住。

向量数据库的答案是用 **ANN（近似最近邻）**：不找"绝对最近"，而是找"足够近"——用空间换时间，把搜索从全量扫描变成"在精心组织的索引里走捷径"。

## HNSW：图索引，召回率的代表

HNSW（Hierarchical Navigable Small World）是目前**召回率与速度最均衡**的默认选择，原理是"多层跳表 + 小世界图"：

- 构建时把每个向量连成图，高层是"稀疏的高速路"，低层是"稠密的街区"；
- 搜索时从高层快速"跳到"目标区域，再逐层下到低层精细找邻居。

```python
params={"M": 16, "efConstruction": 200}
```

两个关键参数影响索引质量和查询：

| 参数 | 含义 | 调大效果 | 代价 |
| --- | --- | --- | --- |
| `M` | 每个节点连的邻居数 | 图更稠密、召回更好 | 索引更大、构建更慢 |
| `efConstruction` | 构建时考虑的候选数 | 索引质量更高 | 构建更慢 |

查询时还有个 `ef` 参数（search_params 里设，如 `{"ef": 64}`），决定"搜索时考察多少候选"——**调大 ef，召回更好但更慢**。经验起步值：`M=16`、`efConstruction=200`、查询 `ef` 从 64 起步，按效果与延迟微调。

## IVF：聚类索引，内存敏感时的选择

IVF（Inverted File）的思路是**先聚类再检索**：建索引时把向量用 KMeans 聚成 nlist 个簇，搜索时只查最近的 nprobe 个簇：

```python
index_params.add_index(
    field_name="embedding",
    index_type="IVF_FLAT",
    metric_type="IP",
    params={"nlist": 1024},          # 聚成多少个簇
)

# 搜索时
search_params = {"metric_type": "IP", "params": {"nprobe": 16}}   # 查几个簇
```

- `nlist`：聚类数，越大召回越细但索引越大；
- `nprobe`：搜索时探查的簇数，**nprobe 越大召回越好、越慢**。

IVF 系列还有量化变体（IVF_SQ8 用 8bit 量化压缩向量、IVF_PQ 乘积量化），**用精度换内存**——向量太多内存放不下时的选择。而 `FLAT` 变体不量化，保精度。

## 不同索引怎么选

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 通用默认（百万级内） | HNSW | 召回/速度/内存均衡，不用调太多 |
| 内存吃紧、能接受精度略降 | IVF_SQ8 / IVF_PQ | 压缩向量省内存 |
| 超大库、追求极致内存 | DiskANN（磁盘索引） | 向量放磁盘也能毫秒级 |
| 稀疏向量（BM25 输出） | SPARSE_INVERTED_INDEX / SPARSE_WAND | 稀疏专用，配合全文检索 |
| 数据极少、必须精确 | FLAT（暴力） | 不用索引，全量精确算 |

**默认心智：先 HNSW 跑通，量上来了或内存告急再换**——别在起步阶段优化你用不到的规模。

## 召回率怎么量化

调索引最终看两个指标：

- **Recall@K**：真实最相关的 K 条里，索引召回了多少比例（ANN 是近似的，Recall < 100% 正常）；
- **查询延迟与内存**：速度与资源是否达标。

Milvus 没有内置评测，自己抽样算：拿一批已知正确答案的 query，比较"索引搜索 TopK"与"暴力搜索 TopK"的重合率。**先用 FLAT 跑出"标准答案"，再用 ANN 对比**，这是调索引参数的通用方法。

## 小结

索引的底层心智三句话：**度量方式决定"相似"的定义（IP/COSINE/L2 选对）；HNSW 用图结构换召回率，调 M/efConstruction/ef；IVF 用聚类省资源，调 nlist/nprobe**。所有 ANN 都是"近似"，用 FLAT 当标尺验证召回，别盲目抄参数。
