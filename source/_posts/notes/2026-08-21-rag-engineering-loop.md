RAG 课容易写成二十讲框架说明。落到应用里，可以压成一条闭环：文档进来 → 切分入库 → 查询改写与检索 → 组装上下文生成 → 用评测集证明它没有悄悄变差。

## 最小闭环仍然只有三步

1. **切分**：按标题和语义块切，避开把表格从中间切断。每个 chunk 带 `doc_id`、`section`、`hash`、版本。
2. **召回**：embedding 先取 8–20 条，再用权限、时效、文件类型过滤。rerank 是加分项。
3. **生成**：只根据给定片段回答，关键结论标注出处；片段不够就说不知道。

没有出处的流畅回答，比检索失败更危险。

## 查询侧要先搞清楚「这是什么问题」

不是所有问题都该检索。意图识别负责分流：闲聊、查规范、比条款、要整改建议，走不同 Prompt 和不同过滤条件。query rewrite 解决的是用户口吻和条文口吻不一致，比如把「屋面漏了怎么处理」改写成规范里更可能出现的说法。变体检索（原句 + 改写 + 关键词）比单路 embedding 稳。

## Milvus：索引只是手段

要先问：向量维度、度量方式、过滤字段有没有和 MySQL 主键对齐。HNSW / IVF 影响的是召回和延迟，不是业务正确性。Hybrid search 把稀疏关键词和稠密向量拼在一起，适合规范文本这种「既有编号又有说法」的语料。

运维上更关键的是：upsert 是否幂等、删除是否同步、重建索引会不会打断线上读。

## 编排不要写进一个函数

常见分层：

- FastAPI 入口：鉴权、限流、参数校验
- QAService：选场景、选知识库版本
- Pipeline：改写 → 检索 → 组上下文 → 调模型
- Prompt profile：按场景切换，而不是一个万能系统提示

异步有用，但要给模型调用设超时和并发上限。缓存只适合「embedding 和带版本边界的检索候选」，不要把自由生成的答案当永久真理。

## 版本、隔离、入库

知识库会变。版本号应该打在文档和切片上，查询时显式选择「当前生效版本」。数据隔离按租户 / 项目 / 专业切，过滤条件在检索时就要带上，而不是生成后再靠模型自觉。

入库流水线单独看：解析失败、空页、重复 hash、切片过短过长，都应该在进向量库之前被拦住。质量门禁比多一条 embedding 重要。

## 评测、测试、观测

RAG 不能只用 `assertEqual`。至少准备三层：

- 纯逻辑单测：意图、过滤、上下文拼接
- 评测集：30 道以上业务题，看引用是否命中、是否拒答
- 线上 Trace：模型名、耗时、命中的 `doc_id`、改写前后 query

本地先有评测报告和回归脚本，再谈把 Trace 送到企业观测平台。Docker 交付则是把 API、向量库、模型和初始化脚本变成可重复拉起的环境，而不是在某一台机器上「曾经跑通」。

## 一张对照表

| 环节 | 失败时的典型症状 |
| --- | --- |
| 切分 | 回答只给半句条文，表格错位 |
| 意图 / 改写 | 检索到的全是无关章节 |
| 过滤 / 隔离 | 看到不该看的项目资料 |
| 版本 | 引用了作废标准 |
| 评测缺失 | 换模型后「感觉更好」，过两周才发现引用崩了 |
