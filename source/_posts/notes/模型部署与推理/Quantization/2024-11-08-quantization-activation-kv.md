前两篇量化的是**权重**。但显存的大头不止权重——长上下文场景下，**KV Cache 会反超权重成为最大显存占用者**。这篇讲两块更精细的量化：激活量化（连中间计算也省）和 KV Cache 量化（把缓存压到 8bit）。它们是"显存优化"的最后几块拼图。

## 权重量化后，显存大头变成了什么

短对话：权重占大头。**长上下文 / 大并发**：每个请求都要为已生成的每个 token 存一份 KV，成百上千 token 累积起来，KV Cache 迅速膨胀：

```text
7B INT4 模型：权重 ~4GB
单请求 4K 上下文：KV Cache ~1.5~2GB × 并发数
→ 32 并发长上下文：KV Cache 可能 60GB+，远超权重
```

这也解释了推理引擎里一个矛盾：**模型越来越小（量化），KV Cache 越来越大（上下文长）**。要压显存，必须两条腿走路。

## 激活量化：连计算也省

权重量化只压缩"存储"。**激活量化**把前向计算中的中间激活也量化成 INT8，能用 INT8 矩阵乘（比 FP16 快且有原生硬件支持）：

```python
# 静态激活量化需要校准数据观察激活范围（W8A8 方案）
from transformers import AutoModelForCausalLM
# 例：加载社区 W8A8 量化模型（权重和激活都 8bit）
model = AutoModelForCausalLM.from_pretrained(
    "model-with-activation-quant", torch_dtype="auto")
```

激活量化的注意点：**激活分布波动大**（不像权重固定），容易出现异常大值（outlier）毁掉整个 scale。业界方案（如 SmoothQuant）是"把激活的难量化转移到权重上"——把激活除以一个平滑因子、权重乘回来，让两边都好量化。**激活量化是"更快"的手段，不是"更省显存"的主力**——显存主力看 KV 量化。

## KV Cache 量化：把缓存压到 8bit

KV Cache 默认 FP16 存储。把它量化到 FP8/INT8，缓存显存直接减半：

```python
# vLLM：开启 KV Cache 量化
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --kv-cache-dtype fp8        # 或 fp8_e5m2 / fp8_e4m3
```

要点：

1. **按 token 分块量化**：KV 是流式增长的，不能等整段算完再量化——每来一段算一段的 scale；
2. **精度损失通常很小**：KV Cache 量化到 8bit 对多数任务几乎无损，是"长上下文 + 大并发"场景的刚需；
3. **收益直接**：缓存减半 → 同样显存能支持 2 倍上下文或 2 倍并发。

```text
FP16 KV：支持 4K 上下文 × 16 并发
FP8 KV： 同样显存 → 支持 8K 上下文 × 16 并发（或 4K × 32）
```

## 组合拳：全链路量化后长什么样

现代推理服务的显存分配通常这样配：

| 组件 | 默认 | 优化后 |
| --- | --- | --- |
| 模型权重 | FP16 | INT4（GPTQ/AWQ） |
| KV Cache | FP16 | FP8 |
| 计算激活 | FP16 | INT8/FP16 混合（视硬件） |

三者独立配置、可叠加——这就是"全链路量化"。显存需求可以从基线降 60~75%，而且长上下文场景收益最明显（权重省的比例固定，KV 省的比例随长度放大）。

## 精度影响的"暗面"

KV/激活量化比权重量化更敏感，注意三点：

1. **必须校准与验证**：激活范围要校准数据观察，KV 量化要跑评测集对比；
2. **个别任务退化明显**：长文档精确引用、数学推理这类任务对精度更敏感，量化后要重点抽测；
3. **硬件决定方案**：FP8 在 H100 等 Hopper 架构有原生加速，老卡（A100/3090）上支持有限——先查硬件再选 dtype。

## 小结

量化不止权重：**激活量化让计算更快（W8A8/SmoothQuant），KV Cache 量化让长上下文与高并发成为可能（FP8 缓存显存减半）**。显存优化要"权重 + KV 双管齐下"，现代引擎支持独立配置、组合叠加。量化手段到齐了，下一篇回答最关键的工程问题：怎么量化才算成功——精度与速度的评估账。
