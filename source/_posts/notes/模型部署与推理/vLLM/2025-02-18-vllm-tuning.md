起服务、懂参数之后，真正的性能调优是从"能跑"到"跑得又快又多"。这一篇按收益排序讲 vLLM 的三个高频优化：**前缀缓存（白捡的吞吐）、量化（小显存跑大模型）、张量并行（多卡放大）**。每个都给配置与验证方法。

## 优化一：前缀缓存（先开这个）

多轮对话、批量评测、RAG 场景有个共性：**大量请求共享相同前缀**（system prompt、检索上下文的前半段）。没有缓存时每个请求都把相同前缀重新算一遍预填充——纯浪费。

```bash
# 开启前缀缓存（vLLM 0.4+ 支持）
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --enable-prefix-caching
```

生效原理：PagedAttention 的块共享能力 + 前缀哈希——相同前缀的 KV 块直接复用，省掉整段预填充计算。

```text
场景：RAG 请求都带 2K 相同 system/规则前缀
开启前：每个请求预填充都算一遍 2K token
开启后：第一个请求算完，后续请求直接命中缓存
→ 长前缀场景吞吐可提升数倍（取决于前缀占比）
```

**判断是否适合**：请求间共享前缀占比越高越赚。业务上把"固定不变的指令"收敛成统一前缀（而不是散在各处），能让缓存命中率最大化。

## 优化二：量化（显存不够时的第一选择）

模型装不下 / 想留更多 KV 空间 → 上量化权重（量化篇章的方法，vLLM 直接支持）：

```bash
# AWQ 4bit：7B 从 14GB 降到 ~4GB
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ --quantization awq

# FP8：精度损失更小，Hopper 卡有原生加速
vllm serve Qwen/Qwen2.5-7B-Instruct --quantization fp8

# KV Cache 也压到 FP8（长上下文场景显存大头在 KV）
vllm serve ... --kv-cache-dtype fp8
```

**组合用法**：权重 INT4 + KV FP8，是"小显存跑大模型 + 长上下文"的常见组合。上量化后记得跑评测集验证质量（量化评估篇的流程）。

## 优化三：张量并行（模型大了上多卡）

模型单卡放不下（70B）或想提升单请求吞吐 → 张量并行把模型切到多张卡：

```bash
# 4 卡切分 70B 模型
vllm serve Qwen/Qwen2.5-72B-Instruct-AWQ \
  --quantization awq \
  --tensor-parallel-size 4
```

```text
张量并行：每一层按维度切到多卡，一次前向多卡协同算
→ 能跑更大的模型
→ 单请求延迟更低（每卡算的少）
代价：卡间通信开销；小模型上多卡反而可能更慢
```

**注意**：模型小时别开大并行度（7B 上 2 卡收益小、4 卡可能倒退）；显存以能装下为准，别为了并行而并行。

## 调优顺序与组合

一个务实的调优路径：

```text
1. 起服务（合理基础参数）
2. 开 --enable-prefix-caching（白捡）
3. 压测看瓶颈：
   显存不够/OOM → 量化（INT4/FP8 + KV FP8）
   单请求慢     → 投机解码（--speculative-model）或加大并行
   并发吞吐低   → 调 max-num-seqs + gpu-memory-utilization
4. 每次只改一个，重新压测对比
```

## 验证调优效果

每个优化都要有数据支撑，维护一份配置对比表：

```bash
# 压测脚本（并发 64，固定 max_tokens）对比各配置的吞吐与 p95
python bench.py --url http://localhost:8000/v1

# 期望输出：
# 配置                                  | 吞吐(tok/s) | p95(s)
# baseline                             | 3000        | 1.8
# +prefix-caching（共享前缀场景）        | 5000        | 1.2
# +AWQ(4bit)                           | 4500        | 1.3  ← 显存减半后并发还能更高
# +4 卡 TP                             | 8000        | 0.9
```

## 常见调优误区

| 误区 | 正确认知 |
| --- | --- |
| 一上来就上多卡 | 先测单卡够不够，TP 有通信开销 |
| 量化后不验证质量 | 必须跑评测集（量化可能暗损） |
| 无脑调大 max-num-seqs | 越大延迟越高，找甜点而非拉满 |
| 前缀缓存当万能 | 只有共享前缀场景才赚 |

## 小结

vLLM 调优三板斧：**前缀缓存先开（白捡吞吐）、显存不够上量化（权重 INT4 + KV FP8）、模型大了开张量并行**。方法论上每次只动一个变量、压测对比、维护配置表格。理解原理（上篇）+ 用数据驱动（本篇），vLLM 的性能就能稳稳压榨出来。服务调优好了，下一篇走向生产：部署形态、多模型与可观测。
