前几篇优化的是吞吐与重复计算，但**单个请求的延迟**还有一个结构性问题没解决：自回归解码每一步只能生成一个 token，而大模型每一步都那么贵。投机解码（Speculative Decoding）用"以小博大"的思路突破这个串行——**让便宜的小模型先猜一串，昂贵的大模型一次批量验证**。这一篇讲透原理与适用条件。

## 核心思想：猜一串，验一串

与其让大模型一步步"想"，不如：

```text
1. 用小而快的草稿模型（draft model）先"猜"出接下来 4~5 个 token
2. 把"猜的这串"一次性交给大模型并行验证
3. 猜对了的 token 直接采纳（白赚，不用大模型一步步生成）
4. 猜错的位置回退，从那里让大模型接管继续
```

```text
草稿模型猜:  "混凝土" | "强度" | "不足" | "需要"
大模型验证:  ✓        ✓        ✓        ✗(应为"不够")
结果: 采纳前 3 个，第 4 个用大模型的"不够"，继续下一步
```

**一次大模型前向"验证"了 4 个候选，等于一次算出了多个 token**——生成步数变少，延迟自然下降。

## 为什么能加速：并行验证 > 串行生成

关键点在大模型侧：验证"一串候选"只需要**一次前向传播**（把候选串当输入，一次算出每个位置的分布），而自回归生成这一串需要**串行 4 次前向**。一次并行前向和四次串行前向的耗时差，就是投机解码的收益来源。

```text
自回归:  [大模型算token1] → [算token2] → [算token3] → [算token4]   = 4 步延迟
投机解码: [小模型猜4个] + [大模型1次验证4个]                      ≈ 1.1 步延迟
```

前提是**草稿模型猜得准**——猜得越准，采纳率越高，加速越明显。业界经验：接受率 60~80% 时，单请求延迟通常能降 2~3 倍。

## 部署形态：怎么搞到草稿模型

三种主流方式：

1. **小同族模型**：用同架构的小版本当草稿（如 7B 主模型配 0.5B 草稿）——最通用；
2. **自投机（Self-Speculative）**：用主模型自身的浅层/中间层预测后续 token——免额外模型；
3. **N-gram 投机**：从已生成文本里统计 n-gram 猜下一个词——零额外显存（vLLM 支持 `--speculative-model` / ngram 模式）。

```bash
# vLLM 启用投机解码（草稿模型 + 建议长度）
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --speculative-model Qwen/Qwen2.5-0.5B-Instruct \
  --num-speculative-tokens 5
```

## 收益与代价的权衡

| 维度 | 说明 |
| --- | --- |
| 收益 | 单请求延迟降 2~3 倍（交互型服务体验提升明显） |
| 代价 1 | 多加载一个草稿模型 → 额外显存 |
| 代价 2 | 草稿模型每一步也要算 → GPU 总计算量略增 |
| 代价 3 | 批量并发场景收益下降（GPU 已满载时没有"空闲"去跑草稿） |

**适用判断**：单请求延迟敏感（交互聊天）、GPU 未满载 → 收益大；GPU 已满载的高吞吐批处理 → 收益有限（可能还拖累吞吐）。延迟优化和吞吐优化在这个点上出现了取舍。

## 和采样兼容吗

一个常见疑虑：投机解码会不会改变生成质量？**设计上不会**——验证时会做"拒绝采样"：猜错的 token 按大模型真实分布重新采样，保证最终分布与大模型自回归完全一致。**投机解码是"无损加速"**，这也是它被主流引擎采纳的原因。

## 小结

投机解码用"草稿模型猜一串 + 大模型一次并行验证"破解自回归的串行瓶颈：**接受率高则延迟降 2~3 倍，且不改变生成质量**。代价是额外显存与总计算量略增，最适合"单请求延迟敏感、GPU 有富余"的场景。它是延迟优化里最"巧"的一招。

单请求快了、吞吐高了，怎么科学地证明优化有效？最后一篇：推理性能度量——别再用感觉评估。
