ReAct 是 Agent 的"标准大脑"——走一步看一步。但真实任务往往很长：调研一个课题、整理一份报告、批量处理一批数据，如果 Agent 每一步都临时决定，很容易跑偏——做着做着忘了最初目标，或者在某条岔路上越走越远。**规划（Planning）让长任务可控：先想清楚要做哪几步，再动手。** 而反思（Reflection）补的是另一类缺陷：**做完的质量问题。** 这篇把"规划"和"反思"两个机制讲透——它们怎么落地、各自的边界在哪。

## 规划的本质：把"自由发挥"变成"有步骤地执行"

ReAct 的自由循环适合任务路径不确定的场景；但很多任务其实是"路径可预知"的——只是步骤多。规划的价值是把这些可预知的步骤**显式化**：

- 先让模型产出任务清单（步骤 1/2/3...）；
- 再逐步执行，每步可以单独验证；
- 执行过程中可对照计划检查"有没有跑偏"。

它的工程意义不只是"更有序"，而是三个可量化收益：

1. **可控**：长任务拆成小步后，每步可单独评测、单独重试，出问题能定位到"第几步"；
2. **可恢复**：任务中断后，从失败的步骤重跑，而不是从头再来；
3. **可审计**：计划和实际执行对比，能看出 Agent 是否忠实执行、哪里偏离。

## 规划的落地：Plan-and-Execute

前面模式篇提过 plan-and-execute，这里给出更完整的形态和工程细节：

```python
class PlanAndExecute:
    """规划-执行框架：先出计划，再逐步执行"""

    def run(self, task: str):
        # 阶段一：规划（单独一次调用，输出结构化计划）
        plan = self.make_plan(task)
        # plan = [{"step": 1, "action": "搜索厂商 A 的 GPU 价格", "tool": "web_search"},
        #         {"step": 2, "action": "...", "tool": "web_search"}, ...]

        # 阶段二：执行（逐步，每步独立）
        step_results = []
        for step in plan["steps"]:
            result = self.execute_step(step)     # 每步调工具/子任务
            step_results.append({"step": step, "result": result})

        # 阶段三：汇总（基于所有步骤结果生成最终输出）
        return self.finalize(task, step_results)
```

工程上的三个关键设计：

**1. 计划要"可执行"而非"口号"。** 差的计划是"调研三家厂商"（太粗，执行时还是要自由发挥）；好的计划是"用 web_search 查厂商 A 的 GPU 型号和价格 → 查厂商 B → …"。**计划里的每一步，执行阶段要能直接对应到工具调用。**

**2. 执行中允许"计划修订"。** 现实里第 2 步可能发现第 3 步的前提变了。好的实现允许执行中插入"重新规划"——发现计划不成立时，让模型先更新计划再继续，而不是死板执行完一个错误计划。

**3. 规划也要设上限。** 计划步骤过多说明任务拆得太碎（每步都有开销），过少说明没拆到位。一般一个任务 3-8 步为宜；计划本身失败（模型拆不出合理步骤）要能降级回 ReAct。

## 反思的本质：第二双眼睛

反思是让模型"自己检查自己的工作"。它的价值在于抓住**第一遍生成时遗漏的错误**——很多错误在生成当下看不见，但回头看能发现（漏了条件、逻辑矛盾、格式不对）。

反思的两种实现层次：

**层次一：单轮反思（生成 → 检查 → 修正）。** 模式篇给过：生成草稿，用审视视角检查，根据问题修正。适合"错误容易被发现"的任务（代码、SQL、结构化输出）。

**层次二：持续反思（循环中每一步都带检查）。** 在 ReAct 循环里，模型每次行动后不仅观察结果，还反思"这一步对吗？要不要回退？"——这就是 Agent 的"元认知"，能减少错误累积：

```python
def react_with_reflection(task: str, max_steps: int = 8):
    messages = []
    for step in range(max_steps):
        # 决策：思考 + 决定行动
        action = llm_act(messages + [task])

        if action.is_final:
            # 最终答案前先反思一遍质量
            review = llm_review(task, action.answer)
            if review.ok or step >= max_steps - 1:
                return action.answer if review.ok else llm_fix(task, action.answer, review.issues)
            continue

        # 执行 + 观察
        result = execute(action)
        messages.append(result)
```

## 反思的边界：不是所有任务都值得

反思不是免费的——每次反思都是一次额外模型调用（延迟 + 成本）。而且反思的效果有前提：**模型得能看出自己的错**。两个判断标准：

```text
该用反思：
  · 任务有明确的对错标准（代码能编译、SQL 能跑、格式能校验）
  · 模型"第一遍容易漏、回头看能发现"的错误（漏条件、笔误、不完整）
  · 质量要求高、错误代价大（生成要落库的 SQL、要发给客户的文案）

不该用反思：
  · 开放性问题（"给点灵感"）——没有明确对错，反思无从谈起
  · 模型能力不足以自检的任务——反思只会"自信地确认错误答案"
  · 低延迟强约束场景——多一次调用可能不可接受
```

**工程判断：能不能用"规则"替代反思？** 很多"反思"能做的事，规则做起来更便宜更可靠——JSON 格式错误用解析器校验、SQL 语法用编译器检查、缺字段用 schema 验证。**先上规则，规则覆盖不了的再用反思。** 反思是"规则之外的最后一道柔性检查"，不是第一选择。

## 规划 + 反思的组合形态

真实项目里两者常组合出现，典型的成熟形态：

```text
长任务流程：
① 规划：模型产出任务清单
② 逐步骤执行（每步是一个 ReAct 子循环）
③ 每步结束后轻量反思（结果对不对？要不要重做这一步？）
④ 全部完成后整体反思（有没有漏步骤？结论是否一致？）
⑤ 必要时重新规划缺失部分 → 补执行
```

这套组合适合"调研报告、数据处理、系统运维"这类长流程任务。但注意：**复杂度是叠加的，失控风险也是叠加的**——每一层都要有步数上限、超时、人工介入点（后面 LangGraph 篇讲 human-in-the-loop 时细说）。

## 小结

规划让长任务可控（拆成可执行、可验证、可恢复的步骤），反思让结果可修正（生成后自查）。工程要点：计划要能直接映射到工具调用、执行中允许修订计划；反思要分层次（单轮 vs 循环中）、能用规则替代就别用模型反思。两者都有成本与边界——规划适合路径可预知的长任务，反思适合"错误能被自己发现"的任务。**给 Agent 加"计划"和"反思"，是给它装了方向盘和后视镜——但别让它因此开得更野，上限和护栏一个都不能少。**
