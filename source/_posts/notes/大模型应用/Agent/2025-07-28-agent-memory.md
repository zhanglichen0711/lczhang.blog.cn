模型本身没有记忆——每次对话它都是从零开始读你的消息。你能和 ChatGPT 连续聊天，是因为应用层把历史消息一直带在上下文里。对 Agent 来说，记忆问题更复杂：它不仅要记住"这次任务聊了什么"，还要在任务之间、会话之间记住"用户是谁、偏好什么、上次做到哪了"。**Agent 的记忆不是模型的属性，是应用层的工程设计。** 这篇讲清楚记忆的分层结构、各自的实现方式和取舍。

## 先理解：记忆的三种形态

Agent 的记忆按"生命周期"分三层，工程上要分开设计：

```text
① 短期记忆：当前会话/任务内
   这轮任务聊了什么、做了什么、进行到哪一步

② 长期记忆：跨会话（用户级）
   用户是谁、偏好、历史结论、长期目标

③ 工作记忆：正在进行的任务状态
   任务拆到哪了、哪些步骤完成、中间结果（可恢复）
```

很多人把记忆理解成"上下文越长越好"，其实三层各有各的问题和解法，混为一谈是 Agent 记忆设计失败的主因。

## 短期记忆：把上下文控制在"够用"

短期记忆就是对话历史——问题是**不能无限长**。上下文越长，成本越高、延迟越长，而且模型会"迷失在长上下文里"（前面的关键信息被稀释）。

工程上控制短期记忆的手段：

**手段一：滑动窗口。** 只保留最近 N 轮消息，更早的丢弃或压缩：

```python
def trim_history(messages: list[dict], max_messages: int = 20) -> list[dict]:
    if len(messages) <= max_messages:
        return messages
    # 保留系统提示 + 最近的消息（丢弃最老的中间部分）
    system = [m for m in messages if m["role"] == "system"]
    recent = messages[-max_messages:]
    return system + recent
```

**手段二：摘要压缩。** 窗口滑掉的内容不是直接丢，而是先让模型压缩成摘要，带着摘要继续：

```python
def summarize_old(messages: list[dict]) -> str:
    """把窗口外的旧消息压成一段摘要"""
    old = messages[:-WINDOW]     # 要被挤出的旧消息
    return llm(f"把以下对话压缩成摘要，保留关键信息（用户诉求/已确认事实/未完成事项）：\n{old}")
```

摘要的取舍：省 token 但有信息损失——摘要可能漏掉细节。**实践中"摘要 + 最近原文"的组合最常用**：老消息留摘要、近消息留原文。

## 长期记忆：跨会话记住用户

长期记忆解决的是"用户第二次来，Agent 还记得他"。实现的核心是**把记忆从上下文里拿出来，存成结构化数据**：

```python
# 用户档案：长期记忆的存储形态
user_profile = {
    "user_id": "u_1024",
    "preferences": {"language": "中文", "region": "上海", "report_style": "简洁"},
    "facts": ["负责华东区项目", "关注防水规范更新"],   # 从对话中沉淀
    "history": [{"date": "...", "topic": "...", "outcome": "..."}],
    "todo": ["下次跟进供应商报价"],   # 跨会话的未完成事项
}
```

长期记忆的读写流程：

```text
写入：每次对话结束（或关键节点），从对话中抽取"值得记的"
  → 偏好、确认过的事实、待办事项 → 更新用户档案
读取：新会话开始时，把相关档案注入系统提示
  → 让模型"记得"用户是谁
```

**抽取是长期记忆的难点**——不是所有对话都值得记。值得记的三类：**显式偏好**（"我习惯看表格"）、**稳定事实**（"我在 XX 公司"）、**跨会话待办**（"下次提醒我"）。可以用 LLM 做抽取：

```python
EXTRACT_PROMPT = """从对话中抽取值得长期记住的信息：
1. 用户的明确偏好
2. 用户提供的稳定事实（身份/背景）
3. 需要跨会话跟进的事项
输出 JSON：{"preferences": [], "facts": [], "todo": []}
没有可抽取的信息就输出空列表。"""

def extract_memories(conversation: str) -> dict:
    return json.loads(llm(EXTRACT_PROMPT.format(conversation=conversation)))
```

**长期记忆的工程要点：写入要克制、读取要按需。** 写入克制——什么都记等于没记，还会积累过期信息（要能删除/更新）；读取按需——不要把整个用户档案全塞进上下文，只注入与当前任务相关的部分。

## 工作记忆：让长任务"可恢复"

Agent 跑长任务，最怕中途崩溃——网络断了、进程重启、超时被掐，任务状态全丢，只能从头再来。**工作记忆就是把"任务进行到哪了"持久化**，让 Agent 能从中断处恢复。

```python
# 任务状态：工作记忆的存储
task_state = {
    "task_id": "task_8821",
    "goal": "调研三家云厂商 GPU 价格并出报告",
    "plan": [{"step": 1, "done": True, "result": "厂商A: 4090 ¥3.2/时"},
             {"step": 2, "done": False, "retry": 0}, ...],
    "context": {"user": "u_1024", "deadline": "2025-08-01"},
    "next_action": "执行第 2 步",
}
```

每次任务推进就更新状态存储（Redis 或数据库），崩溃后从 `next_action` 继续：

```python
def save_task_state(task_id: str, state: dict):
    redis.set(f"task:{task_id}", json.dumps(state), ex=86400)

def load_task_state(task_id: str) -> dict:
    raw = redis.get(f"task:{task_id}")
    return json.loads(raw) if raw else None

# 崩溃恢复：从持久化状态继续，而不是从头跑
state = load_task_state(task_id) or initialize_task(task_id)
while not state["done"]:
    state = execute_next_step(state)
    save_task_state(task_id, state)
```

**工作记忆是长任务 Agent 生产化的前提**——没有它，Agent 只能做"一口气跑完"的短任务，任何中断都是前功尽弃。它和 LangGraph 的状态管理是同一件事（框架篇会讲），这里先建立认知。

## 记忆的边界与风险

设计记忆时三个必须警惕的问题：

**问题一：记忆污染。** 长期记忆里的过期信息会误导当前判断（用户三个月前要"简洁报告"，现在要详细版）。**记忆要有更新时间、要有"遗忘"机制**（定期清理/让模型判断相关性）。

**问题二：隐私。** 记忆里存了大量用户信息，等于握着一份敏感数据库——存取要鉴权、要脱敏、要能按用户要求删除（合规红线，安全系列会细讲）。

**问题三：不要把记忆当"真相"。** 记忆是"模型抽取的"，抽取可能出错。重要事实的读取要允许用户纠正（"我不在上海"→ 更新档案），别让一个错误的长期记忆一直误导下去。

## 小结

Agent 的记忆是应用层设计，分三层：短期记忆（对话历史，用滑动窗口 + 摘要控制长度）、长期记忆（用户档案，跨会话持久化，抽取要克制、读取要按需）、工作记忆（任务状态，持久化支持崩溃恢复）。三层的共同工程原则：**记忆是资源不是无底洞，要控制长度、要能更新删除、要注意隐私。** 没有记忆的 Agent 每轮都失忆；记忆设计混乱的 Agent，比失忆更危险——它会"自信地"用错误记忆做事。
