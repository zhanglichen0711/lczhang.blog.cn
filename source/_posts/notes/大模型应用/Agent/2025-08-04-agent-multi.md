单 Agent 处理不了的任务，是不是拆成多个 Agent 就能解决？这是多 Agent（Multi-agent）最容易被误解的地方。**多 Agent 不是"一个模型不够用两个凑"，它的价值在两类明确场景：分工（不同领域各需专家设定）和并行（任务可拆分同时跑）。** 而它的代价——通信、协调、上下文传递——在单 Agent 时代根本不存在。这篇讲清楚：什么时候值得拆、怎么拆、怎么让多个 Agent 协作而不打架。

## 单 Agent 的边界在哪

先明确单 Agent 做不到什么，才有拆分的理由：

**场景一：角色冲突。** 一个任务里需要"严格的审查者"和"创意的生产者"两种矛盾的角色设定。让同一个模型又当选手又当裁判，效果往往打折扣——**拆成两个 Agent，一个生产、一个审查，角色更纯粹。**

**场景二：专业分工。** 任务横跨多个领域：检索资料（搜索型）、数据分析（工具型）、写报告（写作型）。一个 Agent 要同时具备三种"专家人格"，提示会互相干扰——**各配一个专家 Agent，各自只装一种技能包。**

**场景三：并行提速。** 任务可以拆成互不依赖的多个子任务（调研 10 个厂商），单 Agent 串行做很慢——**多个 Agent 并行各自查一个，时间除以 N。**

反之，如果任务是一个"连贯的流水线"（每步依赖上一步的完整上下文），拆成多 Agent 只会增加上下文传递损耗——这种任务应该用单 Agent（或 Planning 模式），而不是多 Agent。

## 多 Agent 的两种协作架构

**架构一：编排者-执行者（Orchestrator-Workers）。** 一个编排 Agent 拆任务、派活、收结果、整合。最常见、最可控：

```text
编排 Agent
 ├─► 搜索 Agent（查厂商 A 价格）→ 结果回编排
 ├─► 搜索 Agent（查厂商 B 价格）→ 结果回编排
 └─► 分析师 Agent（汇总对比）→ 结果回编排
编排 Agent：整合所有结果，产出最终报告
```

实现上，编排者通过"让子 Agent 跑任务并拿回结果"的机制工作：

```python
class Orchestrator:
    """编排者-执行者：编排 Agent 派活给专家 Agent"""

    def run(self, task: str):
        # 1. 编排者拆解任务，产出子任务清单（各带领域标签）
        subtasks = self.planner.split(task)
        # [{"id": 1, "domain": "search", "prompt": "查厂商A GPU价格"}, ...]

        # 2. 按领域分发给对应的专家 Agent（并行）
        results = {}
        for st in subtasks:
            worker = self.get_worker(st["domain"])   # 领域 → 专家 Agent
            results[st["id"]] = worker.run(st["prompt"])   # 可并行

        # 3. 编排者拿到所有子结果，整合成最终输出
        return self.planner.integrate(task, results)
```

**架构二：对话式协作（Peer-to-Peer）。** Agent 之间直接对话协商，没有中心编排者。灵活但难控——容易跑偏、死循环、上下文爆炸。**新手不要从这种架构开始**，等编排者架构跑熟、确实遇到瓶颈再说。

## 多 Agent 的三个工程难点

**难点一：子任务上下文隔离。** 每个子 Agent 只该看到自己任务相关的上下文，而不是整个任务的完整历史——否则又是"一个超长上下文"，还叠加了多份拷贝。设计原则：**编排者分发的是"任务简报"，不是"全部对话"。**

**难点二：结果合并的质量。** 多个子 Agent 的结果拼起来，可能有冲突、有重复、有格式不一致——编排者整合时要做冲突消解（哪个结果可信）、去重、统一格式。**整合这一步是质量的关键，也是最容易被低估的**——很多人以为子任务做好了，汇总自然好，实际上汇总是个独立的难点。

**难点三：失败传播与重试策略。** 一个子 Agent 失败了，是重试它、换方案、还是跳过？失败如果不隔离，会传染给整合结果。设计上要给每个子任务独立的失败处理：重试上限、降级方案（子任务失败 → 编排者标注"该部分未完成"而不是瞎编）。

## A2A：Agent 之间的通信协议

多 Agent 要协作，Agent 之间怎么"说话"也需要协议——这就是 A2A（Agent-to-Agent）。它和 MCP 的分工要分清（前面 MCP 篇提过，这里展开）：

```text
MCP：管 Agent 与工具（Agent 怎么调用外部系统）
A2A：管 Agent 与 Agent（Agent 之间怎么通信协作）
```

A2A 协议定义 Agent 之间的通信方式：Agent Card（Agent 的能力描述，让别的 Agent 知道"这个 Agent 能干什么"）、任务交接、结果返回。它解决的问题和 MCP 类似——**让不同团队开发的 Agent 能互相发现、互相调用，而不是每对 Agent 都要定制对接。**

对大多数团队，现阶段要做的不是自己实现 A2A，而是**理解这个概念边界**：当你的多 Agent 系统需要和其他团队的 Agent 协作时，A2A 才有实际意义。自己内部的多个 Agent，用编排者架构 + 内部协议就够。

## 什么时候不该用多 Agent

给一张"反推荐"清单：

```text
不该拆多 Agent 的情况：
· 任务流程是线性的（A→B→C 每步依赖前步完整上下文）→ 单 Agent + Planning
· 任务不跨领域、不需要并行 → 单 Agent 更稳更便宜
· 模型单 Agent 表现都不稳 → 拆成多个只会放大不稳定
· 团队还没有单 Agent 的评测体系 → 先建地基，别上复杂度
```

**判断心法：多 Agent 是"最后一个选项"，不是"第一个选项"。** 先确认单 Agent + 好的工具设计 + Planning 确实解决不了，再考虑拆分。多 Agent 的复杂度是乘法级的（每个 Agent 都要设计、评测、监控），收益只有场景匹配时才兑现。

## 小结

多 Agent 的价值在两类场景：角色/领域分工（各配专家设定）和可并行任务（提速）。协作架构从编排者-执行者开始（可控），对话式协作后置。工程难点：子任务上下文隔离、结果合并消解、失败隔离与重试。A2A 是 Agent 间通信协议，与 MCP（Agent-工具）分工不同。**多 Agent 是最后才考虑的复杂度——先证明单 Agent 不够，再拆。** 多 Agent 系统失败的案例，大多不是"协作没做好"，而是"根本不该拆"。
