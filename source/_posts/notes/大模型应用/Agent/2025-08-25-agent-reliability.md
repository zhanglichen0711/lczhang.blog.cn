Agent 系列走到工程化收口。前面讲了怎么让 Agent"会做事"（工具、模式、记忆）、"被看清"（可观测）、"被证明"（评测）。这一篇讲生产化绕不开的三件事：**可靠性（别失控）、成本（别烧钱）、安全（别越权）。** 一个能跑的 Agent demo，和一个能上生产的 Agent，差距全在这三件事的工程细节里。

## 可靠性：给"自由发挥"装上护栏

Agent 的本质是让模型在循环里自主决策——自主就意味着可能失控。可靠性的工程目标不是"消灭失控"（做不到），而是**把失控限制在可控范围内**。五道护栏：

**护栏一：步数上限。** 最基础也是最重要的护栏。没有上限的 Agent 可能无限循环，直到把预算烧光：

```python
def run_agent(task, max_steps: int = 10):
    for step in range(max_steps):
        ...
    # 触发上限时的处理：不是直接失败，而是"体面收场"
    return {"status": "incomplete", "reason": "step_limit",
            "partial_result": ..., "message": "任务步骤过多，建议拆分或人工处理"}
```

**护栏二：单步超时与总体预算。** Agent 每一步可能卡住（工具超时、模型响应慢）。给单步设超时，给整个任务设成本/时间预算：

```python
async def run_with_budget(task, cost_limit_usd: float = 1.0):
    total_cost = 0
    while True:
        step_cost = await execute_step_with_timeout(task, timeout_s=30)
        total_cost += step_cost
        if total_cost > cost_limit_usd:      # 成本预算熔断
            return {"status": "budget_exceeded", "cost": total_cost}
```

**护栏三：循环与卡死检测。** 可观测篇讲过 detect_loop / detect_stuck——检测到异常要主动终止，而不是等步数上限自然耗尽。

**护栏四：降级路径。** Agent 失败时要有"兜底行为"——不是裸报错，而是降级：告知用户"自动处理失败，已转人工"，或给出部分结果。**生产 Agent 的失败应该是优雅的降级，不是崩溃。**

**护栏五：确认机制。** 关键动作（花钱、发消息、删数据）执行前要求确认——human-in-the-loop（人工介入）是 Agent 可靠性的终极护栏，LangGraph 篇会专门讲实现。

## 成本：Agent 是"成本放大器"

Agent 的成本结构和小模型调用完全不同，必须单独治理：

**成本特点一：不可预知。** 单次问答成本是确定的（token 数可估），Agent 任务成本取决于走多少步——而步数不可预知。**同一个任务，顺利 3 步完成，卡壳可能 15 步。**

**成本特点二：错误在烧钱。** Agent 每犯一次错（调错工具、死循环重试），都在产生真实费用。**降成本不只是选便宜模型，更是减少无效步数**——工具设计（让模型第一次就调对）、循环检测（及时止损）、评测（发现步数退化），都是成本手段。

**成本治理三板斧：**

```text
① 预算熔断：任务级成本上限（护栏二），超了就停
② 步数优化：用评测监控平均步数，退化即成本上涨的信号
③ 模型分级：简单步骤用小模型（判断要不要调工具），
            复杂推理才用大模型——Agent 里 80% 的步骤可能只需要小模型
```

一个实用的分级：**"决策路由"用小而快的模型**（判断该不该调工具、该调哪个），**"关键生成"用大模型**（最终回答、复杂推理）。路由错了代价小，生成错了代价大——成本花在该花的地方。

## 安全：Agent 比问答系统危险一个量级

普通问答系统只会"说错话"；Agent 会**做错事**——调了不该调的工具、访问了不该访问的数据、执行了有副作用的操作。安全设计必须升级：

**边界一：工具权限白名单（按用户）。** Agent 能调的工具不是全局的，要按用户/角色过滤——普通用户看不到管理工具，A 用户调不了 B 用户的数据工具：

```python
def get_visible_tools(user: User) -> list[Tool]:
    """按角色返回该用户可见的工具集"""
    base = [tool for tool in ALL_TOOLS if tool.role in user.roles]
    return [t for t in base if not t.is_admin_only or user.is_admin]
```

**边界二：副作用动作二次确认。** 有外部副作用的工具（发消息、改数据、调支付）不能自动执行——前面工具篇和可靠性的"确认机制"在这里是安全需求。**读操作可以自动，写操作必须确认。**

**边界三：数据权限下推。** Agent 调工具时，数据权限要在工具实现层强制（检索过滤篇的原理在 Agent 里同样成立）——工具内部校验用户权限，而不是信任 Agent 传来的参数。

**边界四：Prompt 注入防护升级。** Agent 比 RAG 更容易被注入攻击——工具返回的内容会进入模型上下文（间接注入：一个恶意网页让 Agent 调危险工具）。安全系列的纵深防御在这里全部适用：工具返回内容按不可信数据对待、敏感动作独立校验、全量审计。**Agent 的安全红线：工具能做的危险操作，永远小于模型能提议的范围。**

## 审计：Agent 的"黑匣子"

生产 Agent 必须全量审计（可观测篇的轨迹就是审计基础）。审计不只是为了排查，也是为了**追责与合规**：Agent 执行了某操作（发了一封邮件、删了一条数据），要能回答"是谁的任务、Agent 基于什么决策执行的、有没有经过确认"。把决策链（thought-action-observation）留档，是对用户、对监管、对自己团队的保护。

## 一条上线前的工程检查清单

```text
可靠性：□ 步数上限 □ 单步超时 □ 成本预算 □ 循环检测 □ 优雅降级
成本：  □ 预算熔断 □ 平均步数有基线 □ 模型分级（小模型做路由）
安全：  □ 工具按用户白名单 □ 写操作确认 □ 数据权限在工具层
       □ 注入防护（工具返回不可信） □ 全量审计轨迹
```

## 小结

Agent 生产化三件事：可靠性（五道护栏：步数、超时预算、循环检测、降级、确认，把失控限制在可控范围）、成本（预算熔断 + 步数优化 + 模型分级，Agent 是成本放大器必须单独治理）、安全（工具按用户白名单、写操作确认、数据权限下推、注入防护升级、全量审计）。**Agent demo 和 Agent 产品的距离，就是这十几条工程细节的距离。模型负责聪明，系统负责不出事。**
