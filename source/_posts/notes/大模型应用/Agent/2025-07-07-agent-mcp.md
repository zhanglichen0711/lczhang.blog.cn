做 Agent 做到一定规模，会遇到一个绕不开的重复劳动：**每个 Agent 客户端、每个框架，都有一套自己的工具调用协议。** 你在 A 框架里把数据库封装成工具，换到 B 框架要重写一遍；你的工具说明散落在各个业务仓库里，改一处要同步 N 处。MCP（Model Context Protocol，模型上下文协议）要解决的就是这个：**把"模型如何发现和调用外部工具"标准化，让工具侧自己描述自己，应用侧一次接入、处处可用。**

## 为什么需要 MCP：三个真实痛点

**痛点一：工具封装反复造轮子。** 同一个"查数据库"的能力，为 LangChain 封装一次、为自研 Agent 封装一次、为某个商业 Agent 平台再封装一次。每次封装都是把工具的说明（参数、副作用、限制）重新写一遍——**同一份知识维护 N 份，必然漂移。**

**痛点二：工具说明和工具实现分离。** 传统做法里，工具说明写在"模型应用的提示词或代码里"，工具实现写在"业务系统里"。工具升级了参数，说明没人同步更新——模型拿着过期的说明去调新的接口，必然出错。

**痛点三：接入新客户端成本高。** 想让你的工具同时被不同的 Agent 客户端使用，每个客户端都有适配成本。

MCP 的思路：**协议让"工具作者"来定义工具**——工具侧提供标准的工具描述（叫什么、参数、副作用），模型应用去发现和调用。这样工具说明和工具实现待在一起（由最懂工具的人维护），任何支持 MCP 的客户端都能接入。

## MCP 的基本概念

MCP 采用客户端-服务器架构，把"工具"变成标准化的资源：

```text
┌─────────────────┐        MCP 协议        ┌──────────────────┐
│  Agent 应用（客户端）│ ◄──────────────────► │  MCP Server（服务端）│
│  宿主 / 框架        │   发现工具 / 调用工具   │  工具/资源/提示      │
└─────────────────┘                        └──────────────────┘
                                                │
                                          ┌─────┴─────┐
                                          │ 业务系统    │
                                          │ 数据库/API  │
                                          └───────────┘
```

几个核心概念：

- **Tool（工具）**：可被模型调用的函数，带名称、描述、参数 schema（JSON Schema）；
- **Resource（资源）**：可提供给模型的上下文数据（如文件、数据库记录）——让模型"读"而不是"调"；
- **Prompt（提示模板）**：工具侧预定义的提示，把"怎么用这个系统"的知识固化在服务端；
- **传输**：MCP 支持 stdio（本地进程）、SSE / Streamable HTTP（远程）等传输方式。

对应用开发者，MCP 意味着：**你不再需要在自己的业务代码里维护一份容易过期的工具说明书**——工具侧（MCP Server）自己描述自己，你只要连上它、做好权限与审计即可。

## 写一个最小 MCP Server

以 Python 为例（官方 SDK），把"查天气"封装成一个 MCP 工具：

```python
# mcp_server.py —— 一个最小的 MCP Server
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather-server")

@mcp.tool()
def get_weather(city: str, date: str = "今天") -> dict:
    """查询指定城市的天气。city 用中文城市名，date 支持今天/明天或 YYYY-MM-DD。"""
    # ……真正的业务逻辑：调天气 API / 查本地数据
    return {"city": city, "date": date, "condition": "晴", "temperature": 28}

if __name__ == "__main__":
    mcp.run()   # 默认 stdio 传输，供本地 Agent 客户端连接
```

这个 Server 启动后，任何支持 MCP 的 Agent 客户端（框架、应用）都能连上它、自动发现 `get_weather` 工具并调用。**你只写了一次工具定义，所有客户端共享。**

在 Agent 应用侧接入（以官方 Python SDK 为例）：

```python
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

# 连接 MCP Server
server_params = StdioServerParameters(command="python", args=["mcp_server.py"])
async with stdio_client(server_params) as (read, write):
    async with ClientSession(read, write) as session:
        await session.initialize()

        # 发现工具：客户端自动拿到工具清单
        tools = await session.list_tools()
        for t in tools.tools:
            print(t.name, t.description)   # get_weather 查询指定城市……

        # 调用工具
        result = await session.call_tool("get_weather", {"city": "上海"})
        print(result.content)              # 工具返回结果
```

## MCP 与 Function Calling 的关系

很多人混淆这两个概念，其实它们是不同层的：

- **Function Calling** 是"模型输出调用意图"的**模型能力**（上一篇讲过）——解决"模型怎么表达想调工具"；
- **MCP** 是"工具怎么被描述和调用"的**协议标准**——解决"工具怎么接入应用"。

关系是：**MCP 是 Function Calling 之上的一层**。模型用 Function Calling 表达"想调 get_weather"，而"get_weather 是什么、怎么调、连到哪个系统"由 MCP 的发现机制提供。实践中：

```text
Agent 框架（如 LangGraph）→ 通过 MCP 客户端连接工具 → 工具的 schema 进入上下文
→ 模型用 Function Calling 表达调用 → 框架经 MCP 执行 → 结果回填
```

## 工程上接入 MCP 的三件事

**权限**：MCP Server 暴露了工具，但"谁可以调哪些工具"必须由你的应用层控制——工具白名单、按用户过滤、敏感工具鉴权。协议标准化不解决权限问题，**权限永远是你的责任**（呼应工具设计篇的"模型提议、程序批准"）。

**审计**：MCP 调用要全量记录（谁、何时、调了什么工具、传了什么参数、结果如何）——Agent 可观测的基础，也为权限事故留追溯。

**可靠性**：远程 MCP Server 会超时、会挂——调用要设超时、失败要能降级（提示"工具暂不可用"而不是让模型硬编）。

## 什么时候值得上 MCP

MCP 不是所有场景的必需品。判断标准：

- **工具要被多个 Agent 客户端复用** → 值得（一次封装多处用）；
- **工具说明频繁变、且和实现分离导致漂移** → 值得（说明跟着实现走）；
- **只有一个 Agent 调一套私有工具** → 可以不上，直接 Function Calling 更轻（少一层抽象）。

**别为了"用上 MCP"而上 MCP**——它是解决"重复封装与说明漂移"的标准化手段，问题不存在时，抽象就是负担。

## 小结

MCP 把"模型如何发现和调用工具"标准化：工具侧自己描述自己（Server 提供工具/资源/提示），应用侧一次接入处处可用。它解决三个痛点：重复封装、说明与实现分离、客户端接入成本高。与 Function Calling 的关系是：FC 是模型能力（表达调用意图），MCP 是协议（工具接入标准），FC 跑在 MCP 之上。工程上接入时，权限、审计、可靠性三件事仍是你自己的责任。**协议的价值不在协议本身，在接入的生态规模——工具封装成标准协议，是 Agent 走向规模化的必经之路。**
