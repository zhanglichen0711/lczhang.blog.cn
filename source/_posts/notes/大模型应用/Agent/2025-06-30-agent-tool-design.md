Agent 圈有句话："Agent 好不好用，一半取决于模型，另一半取决于工具。" 很多 Agent 项目失败，不是模型不够聪明，而是**工具设计得一塌糊涂**——模型想调工具，却不知道工具是干嘛的、参数怎么传、失败了会怎样，于是一次次瞎猜。这一篇讲工具设计的三个契约：**名称契约、参数契约、错误契约**。把这三件事做好，Agent 的成功率会肉眼可见地提升。

## 先理解：模型是"读说明书"用工具的

模型用工具的方式，和程序员用 API 完全不同：**程序员会读文档、看类型、写代码调；模型只是"读你的描述文字"，然后猜测怎么调。** 它没有编译器帮它检查参数，没有 IDE 帮它补全——它唯一的依据，就是你在工具声明里写的描述。

所以工具设计的本质是：**写给"不会问问题、只会照字面理解"的调用者看的 API 文档。** 一个工具描述里的含糊之处，程序员会来问你，模型只会猜——而猜错的后果由你的系统承担。

## 名称契约：让模型一眼看懂"这是干什么的"

工具名称是模型的第一印象。命名有两个原则：

**原则一：动词开头，说清动作。** `search_documents`、`send_email`、`get_inventory`——模型从名字就知道"这个工具能做什么"。避免模糊命名：`process_data`、`handle_request`、`do_stuff`——模型看了等于没看。

**原则二：避免名字相近的工具。** `get_weather` 和 `check_weather` 会让模型纠结选哪个。同类工具如果必须存在，用参数区分而不是用名字区分——**工具数量越少、边界越清，模型调用越准。**

```text
好：search_employee(emp_id) / search_contract(keyword)
坏：search1 / search2（模型不知道区别）
```

工具的数量也要克制：**能用 5 个工具解决的问题，别注册 20 个。** 工具越多，模型的选择难度越大、调错率越高。给 Agent 的工具要像给新人的权限——只给当前任务需要的，而不是把公司所有接口都开放给它。

## 参数契约：让模型"不犯错地"传参

参数设计决定了模型传参的准确率。三个关键点：

**关键点一：参数要少而明确。** 一个工具五六个参数，模型很容易漏传或错传。**能合并的合并，能默认的默认，只留模型必须决策的参数。**

```text
差设计：
search_orders(customer_id, date_from, date_to, status, page, page_size, sort_by, sort_desc)
（模型：8 个参数，每个都可能猜错……）

好设计：
search_orders(customer_id, date_from, date_to, status="all")
（模型：只决策 4 个，其他有默认）
```

**关键点二：description 写清"值怎么填"。** 参数描述要告诉模型格式和取值范围：

```python
"parameters": {
    "type": "object",
    "properties": {
        "date_from": {
            "type": "string",
            "description": "起始日期，格式 YYYY-MM-DD，如 2025-06-01。不要用'上个月'这类模糊说法。"
        },
        "status": {
            "type": "string",
            "enum": ["pending", "paid", "cancelled"],   # 枚举锁死取值范围
            "description": "订单状态，只接受这三个值"
        }
    },
    "required": ["date_from"]
}
```

`enum` 是参数契约里最有力的工具——**能用枚举限定取值范围的，就别让模型自由填字符串**。模型对"从三个选项里选"的把握，远高于"自己发明一个值"。

**关键点三：required 只列真必填。** required 之外的参数模型可能不传，你的代码要能处理缺省。把"没有默认值的"设为必填，其余给默认——**别让模型为它不关心的参数做决定。**

## 错误契约：让失败"可恢复"

工具会失败：查无数据、参数非法、下游超时、权限不足。模型怎么处理失败，取决于你的工具怎么返回失败——这是 Agent 工程里最容易被忽视、却最影响稳定性的环节。

**反面教材：失败伪装成成功。**

```python
# 工具内部出错，却返回了一个"看似正常"的结果
def get_weather(city):
    try:
        return weather_api(city)
    except Exception:
        return {"temperature": 25, "condition": "晴"}
    # 模型以为查到了，实际是编的 → 用户被误导
```

这是最危险的做法——模型无法区分"真实结果"和"错误兜底"，会把编造的数据当成真的继续推理。**错误必须显式、结构化地返回：**

```python
def get_weather(city: str) -> dict:
    """返回统一结构：成功或失败都让模型一眼看懂"""
    try:
        data = weather_api(city)
        return {"success": True, "data": data}
    except CityNotFoundError:
        return {"success": False, "error": "city_not_found", "message": f"未找到城市：{city}，请检查城市名"}
    except TimeoutError:
        return {"success": False, "error": "timeout", "message": "天气服务超时，请稍后重试"}
    except PermissionError:
        return {"success": False, "error": "permission_denied", "message": "无权查询该城市天气"}
```

统一错误结构的价值：**模型看到 `success: False` + 明确的 error 类型，就能做出正确的恢复决策**：

- `city_not_found` → 换个城市名重试或询问用户；
- `timeout` → 稍后重试，或告知用户服务暂时不可用；
- `permission_denied` → **不要重试**（重试也没用），直接告知用户无权限。

错误契约的黄金规则：**让模型能区分"值得重试的错误"和"重试也没用的错误"。** 一个把所有失败都返回 `{"error": "failed"}` 的工具，模型只能盲目重试——既烧钱又陷入死循环。

## 一个工具设计自检清单

写完一个工具，对照检查：

```text
□ 名称：动词开头，一看就懂是干什么的
□ 描述：写清"何时该调、何时不该调、参数怎么填、失败会怎样"
□ 参数：少而明确，enum 锁取值范围，只留必填
□ 返回值：统一结构，成功/失败显式区分
□ 错误：错误类型可区分（可重试 vs 不可重试）
□ 安全：只在白名单内，不暴露危险操作
```

## 从一次真实失败学到的

我早期写过一个"查合同"的工具，参数就一个 `keyword`。结果模型经常传"帮我看看合同里关于赔偿的条款"这种一整句话当 keyword——检索全乱。后来把参数拆成 `keyword` + `contract_type`（enum 锁死）+ `fuzzy`（布尔），并在描述里写明"keyword 只填 2-5 个字的核心词，不要整句粘贴"，调用准确率立刻上来了。

**工具设计的改进，和提示词一样要靠评测驱动**：把模型调用工具的真实失败案例收进评测集（Agent 评测篇会讲），每次工具描述改动后跑一遍，看"该调的工具调对没有、参数传对没有"。工具也是要持续迭代的"代码"，不是写完就完事。

## 小结

工具是 Agent 的"手脚"，工具设计决定 Agent 能力的边界。三个契约：名称契约（动词开头、边界清晰、数量克制）、参数契约（少而明确、enum 锁值、只留必填）、错误契约（成功/失败显式区分、错误类型可判断是否值得重试）。**模型是照字面理解工具说明的调用者——把工具设计成"它不会问问题也能用对"，Agent 就成功了一半。**
