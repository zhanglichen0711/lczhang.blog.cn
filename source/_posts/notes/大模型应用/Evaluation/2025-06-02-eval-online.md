离线评测（拿固定评测集跑）解决的是"改动前测一测"的回归问题，但它有个天然盲区：**评测集是你的题，线上流量是用户的题。** 评测集再精心设计，也覆盖不了真实用户的全部问法——一个"没想过会有人这么问"的问题，只有在线上才会出现。所以评测体系必须延伸到线上：**线上评测不是等用户投诉，而是主动采集、主动评分、主动发现问题。**

## 为什么需要线上评测

三个场景说明离线评测的盲区：

1. **长尾问题。** 评测集覆盖 100 个典型场景，线上来了第 101 种问法——系统答得怎样，只有线上知道；
2. **分布漂移。** 评测集里"查规范"占 60%，线上实际"闲聊+对比"占 60%——评测集测的是你以为的分布，不是真实的；
3. **悄悄变差。** 模型厂商更新、知识库更新、提示微调——系统可能整体缓慢变差，单靠"用户没投诉"无法发现。

**核心矛盾：真实质量只发生在真实流量里，而真实流量无法预先写成评测集。** 解法就是线上评测——在真实流量经过系统时，采集 + 评分 + 分析。

## 线上评测的基石：trace

线上评测的第一步是**给每次请求留痕**——trace（RAG 篇、可观测篇都提过，这里从评测视角再收拢）。评测需要的 trace 信息：

```python
trace = {
    "request_id": "req_8f3a",       # 贯穿全链路
    "question": "屋面漏了怎么处理",   # 用户真实问题
    "intent": "rag",                 # 路由结果
    "retrieved_docs": [              # 召回了什么
        {"doc_id": "doc_003", "section": "4.2", "score": 0.81},
    ],
    "answer": "……",                  # 系统回答
    "sources": ["doc_003/4.2"],      # 标注的出处
    "latency_ms": 812,               # 延迟
    "cost_cents": 1.2,               # 成本
    "user_meta": {"scene": "web"},   # 业务维度（匿名化）
    "created_at": "2025-06-02T10:00:00Z",
}
```

trace 的采集有两条纪律：

- **全量采集结构**（至少 request_id/question/answer/sources/耗时），量大了再考虑抽样；
- **敏感信息脱敏**——用户问题和回答都可能含隐私，trace 入库前脱敏（用户 ID 匿名化、问题按策略处理），这条红线在安全系列讲过，线上评测最容易在这里翻车。

## 线上评分：分层抽样 + 自动化打分

线上流量不能全量人工评（太贵），也不能全量 Judge 评（成本高）。标准做法是**分层抽样 + 分级评分**：

**第一层：规则实时门禁（全量、秒级）。** 每条请求过轻量规则，拦截明显问题：

```python
def realtime_gate(trace) -> dict:
    """线上实时质量门禁：全量过，秒级，拦截明显异常"""
    flags = []
    if trace["answer"] is None or trace["answer"] == "":
        flags.append("empty_answer")
    if not trace["sources"]:                       # RAG 回答没出处
        flags.append("no_source")
    if trace["latency_ms"] > 5000:                 # 超时
        flags.append("slow")
    if trace.get("error"):
        flags.append(f"error:{trace['error']}")
    return {"flags": flags, "needs_review": bool(flags)}
```

实时门禁的价值：**不用等用户投诉，异常当场被标记**。被标记的请求进"待人工复核"队列。

**第二层：抽样 Judge 评分（定时、批量）。** 对正常流量按比例抽样（如 5%），用 LLM-as-Judge 按维度打分：

```python
def sampled_judge_eval(traces: list[dict], sample_rate=0.05):
    """抽样评分：从流量里按场景分层抽 5%，Judge 打分"""
    sampled = stratify_sample(traces, sample_rate)   # 按 intent/场景分层
    scores = []
    for t in sampled:
        s = judge_answer(t["question"], t["answer"], t.get("sources"))
        scores.append({**s, "request_id": t["request_id"], "scene": t["user_meta"]["scene"]})
    return aggregate_by_scene(scores)   # 按场景汇总：各场景质量分
```

抽样要**按场景分层**（web/客服/内部工具各抽一点），避免全抽到容易的。Judge 的成本在这里可控——只评 5% 的流量。

**第三层：人工复核（争议、差评、门禁命中）。** 三层里最贵的一层只留给最值得看的：实时门禁标记的、Judge 打低分的、用户主动反馈差评的。

## 差评回流：线上评测的闭环

线上评测的终点不是"发现问题"，是**把问题变成改进**——通过"差评回流"闭环：

```text
线上 trace → 规则门禁 / 抽样 Judge → 发现差评
   ↓
人工复核：确认是系统问题（非用户无理要求）
   ↓
归类根因：检索漏？切分坏？提示漂移？模型退化？
   ↓
1. 修复（改检索/切分/提示/换模型）
2. 把该 case 补进离线评测集（坏案例归档）→ 防复发
   ↓
回归：跑离线评测集确认修复没引入新问题
   ↓
上线：修复经评测集验证后发布
```

这个闭环把"线上"和"离线"打通了：**线上发现的坏案例，回流成离线评测集的回归题**——离线评测集因此不断逼近真实分布，线上质量因此持续被监控。这正是 RAG 篇说的"评测是引擎而非报告"的完整形态。

## 线上质量看板：几个必看的指标

线上评测的产出应该落在看板上，长期跟踪。必看的指标组：

```text
质量类：
  抽样质量分（按场景）       → 整体质量趋势
  差评率（门禁+Judge 命中占比） → 问题密度
  忠实性分（RAG）            → 幻觉风险

行为类：
  拒答正确率 / 路由准确率     → 边界是否守住
  无出处回答占比（RAG）       → 溯源是否可靠

工程类：
  延迟 P95、成本、错误率      → 体验与成本
  差评根因分布               → 下一步优化方向
```

**看板的核心用途是看趋势**：某指标连续几天下降，就是系统在退化（可能是模型更新、知识库变化、prompt 漂移），要第一时间定位。比"某天分数高不高"重要得多。

## 小结

线上评测解决离线评测的盲区——真实分布与长尾问题。三件事：全量 trace 采集（脱敏是红线）、分层评分（规则门禁全量 + Judge 抽样 + 人工复核争议）、差评回流闭环（坏案例补进离线评测集）。**评测体系的完整形态是线上线下一体：离线评测保回归，线上评测抓真实，差评回流让两边互相喂。** 单靠离线评测集的系统，是在模拟考里拿高分；接上线上评测，才是面对真题。
