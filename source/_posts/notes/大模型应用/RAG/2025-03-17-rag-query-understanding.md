RAG 的召回质量，不止取决于知识库这边（切分、embedding），还取决于**查询这边**——用户的问题长什么样，直接决定检索能不能命中。很多 RAG 项目把精力全花在优化知识库，却忽略了查询理解：用户一句"屋面漏了咋整"，和你知识库里"屋面防水层渗漏处理"的表述隔着一条语义鸿沟。这一篇讲查询侧的两件事：**意图分流（要不要检索）和查询改写（怎么检索更准）。**

## 意图分流：不是所有问题都该检索

RAG 系统最常见的浪费，是把**所有问题**都丢进检索流程。但实际上用户的问题五花八门：

```text
"什么是防水等级？"        → 需要检索规范
"屋面防水等级怎么确定？"   → 需要检索 + 推理
"4.2 条和 4.3 条有什么区别？" → 需要检索对比
"谢谢你"                → 闲聊，检索浪费
"帮我写个周报"           → 不是知识库的活
"今天天气怎么样？"        → 无关，别检索
```

如果对"谢谢你"也做一次向量检索、再拼上下文调模型，结果就是：浪费 token 和时间，还可能检索出不相干内容干扰模型回复。**意图分流就是在检索之前，先判断"这个问题要不要检索、走哪条处理路径"。**

一个务实的意图分类（不是越细越好，够路由就行）：

```text
闲聊 / 知识问答（走 RAG）/ 对比分析 / 其他
```

用提示工程系列学过的方法实现意图分类（Function Calling 输出 intent），路由到不同处理：

```python
def route(question: str) -> str:
    """返回: rag / chat / unsupported"""
    intent = classify_intent(question)   # 用 LLM + JSON 输出
    mapping = {
        "chat": "chat",            # 闲聊直接对话，不检索
        "rag": "rag",              # 知识问答走检索
        "unsupported": "chat",     # 超出范围，明确告知
    }
    return mapping.get(intent, "rag")
```

意图分流的收益不只是省成本——它**保护了回答质量**：闲聊问题不被检索噪音污染，无关问题不硬凑知识库答案。没有意图分流的 RAG，是拿所有问题去撞一个它不万能的知识库。

## 查询改写：把用户的话翻译成文档的语言

这是查询理解里最容易被低估的一步。用户在问"屋面漏了怎么处理"，你知识库的文档写的是"屋面防水层渗漏的维修与堵漏"。两者的字面和向量表达都不完全对齐——embedding 能缓解一部分语义鸿沟，但**改写（query rewrite）能主动消除它**。

改写的思路：**把用户的自然口语，改写成知识库里更可能出现的专业表述**，再拿改写后的 query 去检索。

```text
用户原话：屋面漏了应该怎么处理？
改写后：屋面防水层渗漏 维修 处理 方案
（更贴近规范文档的术语表达，检索命中率更高）
```

实现改写，用一次额外的 LLM 调用：

```python
REWRITE_PROMPT = """你是一个检索查询改写器。
用户的问题将用于检索技术规范文档，请把它改写成：
1. 使用文档中可能出现的专业术语
2. 保留所有关键限定条件（对象、场景）
3. 输出不超过 30 字，直接给改写结果

用户问题：{question}
改写结果："""

def rewrite_query(question: str) -> str:
    return call_llm(REWRITE_PROMPT.format(question=question))
```

## 多路召回：别把鸡蛋放一个篮子里

改写后的 query 也不一定完美。工程上更稳的做法是**多路召回**：同一问题生成多个检索变体，分别检索后合并结果：

```python
def multi_query_recall(question: str, top_k: int = 5):
    # 生成多个检索查询：原句 + 改写 + 关键词版
    queries = [
        question,                          # 原句
        rewrite_query(question),           # 改写版
        extract_keywords(question),        # 关键词版
    ]
    all_hits = []
    for q in queries:
        all_hits.extend(vector_search(q, top_k=top_k))
    # 按 doc_id 去重合并，保留最高分
    return dedupe_merge(all_hits)
```

为什么多路比单路稳？因为**每一条检索路径都有自己的盲区**：原句保留用户口语可能漏掉术语文档，改写版可能过度改写丢信息，关键词版能兜底专有名词。三路合起来，比任何单路都更可能覆盖"该命中的文档"。代价是多几次检索——在召回质量面前，这个代价通常值得。

## 一组实测经验

在规范问答这种"术语密集"的场景里，查询理解的收益排序大概是：

1. **意图分流**：挡掉无关查询，质量与成本双收益（最大）；
2. **改写**：口语→术语，命中率提升明显；
3. **多路召回**：锦上添花，对模糊问题尤其有效。

一个容易被忽略的细节：**改写不是越"书面"越好。** 改写得过度，可能把用户的限定条件改丢（比如"去年的规范"被改成"规范"，时效条件就丢了）。改写必须保留所有关键限定——它做的是"翻译"，不是"概括"。

## 小结

查询理解是召回质量的前置环节，两件事：意图分流决定"要不要检索、走哪条路径"，挡住无关查询、保护质量；查询改写把用户口语翻译成文档术语，配合多路召回提升命中率。判断标准很简单：**用户问不中，别只怪知识库——先看查询侧有没有把用户的话"翻译"对。**
