RAG 里最不起眼、却最影响质量的环节，是切分。它不像检索那样有漂亮的算法可讲，也不像生成那样能直观看到效果——但**几乎所有"答非所问""引用错乱"的线上问题，追到根上都是切分切坏了。** 一个在切分时被拦腰切断的条款，后续无论检索多准、模型多强，都不可能给出正确回答——烂 chunk 进，烂答案出。

## 为什么"固定长度切分"是大多数问题的源头

最简单的切分方案是按固定字符数切（比如每 500 字一段）。它的优点是实现容易，缺点是**完全无视文档的语义结构**，造成的后果很典型：

- **条款被切断**：规范里"第 4.2.1 条"从中间被劈成两段，检索到上半段时，模型不知道这条的完整约束；
- **表格被劈开**：一个对比表被切成上下两半，各自失去表头，召回了也读不懂；
- **列表与标题分离**：检索到列表项，却看不到它属于哪个标题——上下文信息丢了；
- **检索粒度错乱**：一段里塞了两个无关主题，召回时"文不对题"的概率大增。

固定长度切分的本质问题：**它切的是字符，不是语义**。而检索和生成都是基于语义的——字符边界与语义边界错位，整个链路都会跟着错。

## 结构感知切分：按文档的"天然边界"切

更可靠的做法是尊重文档自己的结构。文档本身就有语义边界：章节标题、段落、表格、列表——**切分应该顺着这些边界走，而不是无视它们。**

以常见的规范类文档为例，切分策略是分层的：

```text
① 解析出标题层级（1 级 / 2 级标题、条款编号）
② 以"标题 + 其下内容"为一个候选块
③ 若候选块过长（如一个 2 级标题下内容超长），
   按段落或语义点二次切分
④ 若候选块过短（如只有标题没内容），
   与相邻块合并，避免产生无信息量的碎片
```

每一层都保留结构信息作为元数据——切出来的每个 chunk 至少带 `doc_id`（哪篇文档）和 `section`（哪个章节），这样回答时能标注"依据 4.2.1 条"而不是"依据某个 500 字碎片"。

## 表格、代码、列表：三种特殊内容的处理

通用切分器在这三类内容上最容易翻车，值得单独说：

**表格**：表格的语义在"表头 + 单元格"的对应关系里。整体保留表格（即使较长），比切成几段更安全；实在过长，按行组切并**保留表头**。失去表头的表格碎片是检索灾难。

**代码块**：不要把代码从中间切断——切成不完整代码的 chunk，检索到后模型看到的是一段语法残缺的文本。要么整块保留，要么按函数/类边界切。

**列表**：列表项依赖列表的整体语境。切分时把"列表标题 + 完整列表"作为一块，不要单独切出某个列表项。

判断切分是否合理的最直接方法：**抽查切分结果，看每个 chunk 单独拿出来读，是否仍然"讲得清一件事"。** 如果读不懂，这个 chunk 就是坏的，无论检索多准都救不回来。

## 元数据：chunk 的"身世信息"

切分不只是把文档切块，还要给每块**打上元数据**。这决定了检索之后你能做什么：

```python
chunk = {
    "content": "4.2.1 屋面防水等级应根据建筑类别、重要程度确定……",
    "doc_id": "doc_2025_003",        # 来自哪篇文档
    "section": "第四章 防水工程/4.2 防水等级",  # 来自哪个章节
    "hash": "8f3a2c91",              # 内容指纹（去重用）
    "version": "2025-01",            # 文档版本
    "created_at": "2025-02-01",
    # 业务字段（按需）：project_id / owner / visibility 等
}
```

为什么元数据这么重要？因为后续几乎所有工程能力都建立在它之上：

- **溯源**：回答标注出处靠 `doc_id` + `section`；
- **过滤**：权限过滤靠业务字段（如 `visibility`、`owner`），时效过滤靠 `version`/`created_at`（系列第 7 篇）；
- **去重与更新**：`hash` 判断文档是否变化，`version` 支持版本切换（系列第 9 篇讲入库流水线时细说）。

**没有元数据的 chunk，只是字符串；带元数据的 chunk，才是可管理、可过滤、可追溯的知识单元。**

## 切分长度：没有万能值，用场景定

"chunk 应该切多长？"是新手最爱问、却没有标准答案的问题。经验区间与取舍如下：

| 场景 | 倾向 | 原因 |
|---|---|---|
| 规范 / 条款类 | 块稍短、边界清晰 | 一条条款一个块，命中即整条 |
| 长文 / 教材类 | 块可稍长 | 语义需要上下文支撑 |
| 对话 / 日志类 | 按轮次切 | 保持上下文完整 |

长度本身不是目标，**"一个块 = 一个可独立理解的语义单元"才是目标**。与其纠结 300 还是 500 字，不如先按结构切出来看实际分布，再对过长/过短的块做二次处理。可以加少量重叠（chunk 间重叠几十字）来缓解边界切断问题——但重叠只是缓解，不能替代结构切分。

## 小结

切分是 RAG 质量的第一道闸：固定长度切分切的是字符不是语义，最容易切坏条款和表格；结构感知切分顺着文档的标题层级走，才接近人的阅读单位；表格、代码、列表要特殊处理；每个 chunk 必须带元数据（doc_id/section/hash/version），它决定了你后续能不能溯源、过滤、管理。判断标准很简单：**每个 chunk 单独拿出来读，要能讲清一件事。**
