RAG 做到一定阶段，会遇到一个比"召回准不准"更严重的问题：**召回了不该召回的内容。** 用户 A 的问题命中了用户 B 的私有文档，模型"流利地"把别人的机密回答了出来——这在多租户知识库里是安全事故，不是质量问题。这篇讲 RAG 生产化的关键一课：**检索过滤——权限、时效与版本隔离，必须在检索这一层做掉，而不是指望模型不泄露。**

## 为什么不能指望"模型自觉"

有人会觉得：给系统提示加一句"不要泄露其他用户的数据"，模型不就不会答了吗？这是把安全建立在模型的自觉上——而模型没有"自觉"可言：

- 模型分不清哪些文档是 A 的、哪些是 B 的——文档里不会自己标"我是 B 的机密"；
- 检索阶段如果就把 B 的文档喂进了上下文，生成阶段模型只会把它当成正常资料使用；
- 提示词能加权重，但挡不住"恰好相关的私有文档"被正常引用。

**正确的做法是让不该出现的内容根本到不了模型面前**——在检索这一层，用过滤条件把无权访问的文档直接排除。数据边界是架构问题，不是提示词问题。

## 权限过滤：把过滤条件写进检索

要让检索层做过滤，前提是**每个 chunk 都带权限元数据**（这也是切分篇强调元数据的原因）。给 chunk 打上可见性标签：

```python
chunk = {
    "content": "……",
    "doc_id": "doc_2025_003",
    "visibility": "internal",        # 可见范围：public / internal / private
    "owner": "user_1024",            # 私有文档的属主
    "org": "org_a",                  # 组织隔离
    "allowed_roles": ["admin"],      # 角色限制（可选）
}
```

检索时，把当前用户的权限转成**过滤表达式**，让向量库在召回时就排除无权文档。以 Milvus 为例，过滤条件（expr）与向量检索一起执行：

```python
def search_docs(query: str, user: User, top_k: int = 5):
    # 把用户权限翻译成过滤表达式——无权文档在存储层就被排除
    expr = (
        f'visibility == "public" || '
        f'(visibility == "internal" && org == "{user.org}") || '
        f'(visibility == "private" && owner == "{user.id}")'
    )
    hits = milvus.search(
        data=[embed(query)],
        filter=expr,          # 过滤在向量检索内部完成
        limit=top_k,
    )
    return hits
```

关键点：**过滤是"检索时同步执行"的，而不是"检索后应用层再删"。** 为什么？因为后者意味着 B 的私有文档已经被召回到应用内存里了——如果日志、缓存、调试输出里漏了，照样泄露。**权限的边界要划在存储查询这一层，让无权数据根本不出库。**

## 时效过滤：别让过期文档当现行标准

知识库另一个常见事故：文档更新了，旧的还躺在库里，检索时新旧混在一起。规范类文档尤其危险——用户问的是 2025 年的要求，检索却命中了 2023 年的旧版条款。

解决靠两个元数据配合：**version（版本）与生效时间**。检索时显式限定：

```python
expr = 'status == "effective" && version == "2025-01"'
```

工程上的常见做法：

- 入库时标记每个 chunk 的**生效状态**（effective / superseded）与所属版本；
- 查询侧**显式选择版本**（系统默认用当前生效版本，特殊场景可查历史版本）；
- 旧版本可以保留（用于追溯对比），但默认检索只命中"当前生效"的文档。

这里有个设计取舍：**保留历史 vs 默认只查现行**。默认应该只查现行（符合用户预期），历史版本按需提供（如"对比 2023 和 2025 版差异"这种查询走专门通道）。

## 版本隔离：文档更新时的替换策略

知识库的文档会迭代：一份规范 v1 被 v2 替代。如果只是把 v2 追加进库而不处理 v1，会出现"同一条款两版并存、检索随机命中"的混乱。正确的版本管理是：

```python
def upsert_document(new_version_chunks: list[dict]):
    """文档更新的标准流程：新版本入库 + 旧版本标记失效"""
    doc_id = new_version_chunks[0]["doc_id"]
    # 1. 把该 doc 的旧版本全部标记为 superseded
    milvus.upsert(
        [{"doc_id": doc_id, "status": "superseded"}],
        filter=f'doc_id == "{doc_id}" && status == "effective"',
    )
    # 2. 新版本入库，标记 effective
    milvus.upsert(new_version_chunks)

    # 幂等性关键：相同 hash 的 chunk 重复写入应被去重/覆盖，
    # 不能让一次重跑产生两份相同数据（系列入库篇详述）
```

删除旧版本时要考虑**引用一致性**：如果用户收藏了基于旧版回答的链接，旧版直接物理删除会让追溯断链。所以常用"软失效"（标记 superseded）而非物理删除——既保证默认检索干净，又保留追溯能力。

## 一个完整的过滤设计清单

把上面串起来，多租户知识库的检索过滤应该是这样：

```python
def build_filter(user: User, kb_version: str | None = None) -> str:
    """组装检索过滤表达式：权限 + 时效 + 版本 + 租户"""
    clauses = [
        # 权限：可见性 + 属主 + 组织
        f'(visibility == "public" || '
        f'(visibility == "internal" && org == "{user.org}") || '
        f'(visibility == "private" && owner == "{user.id}"))',
        # 时效：只查生效中
        'status == "effective"',
    ]
    # 版本：默认当前生效版本，可按需指定
    if kb_version:
        clauses.append(f'kb_version == "{kb_version}"')
    return " && ".join(clauses)
```

**设计检查表：**
- 每个 chunk 是否带全了权限/组织/版本/状态元数据？（没有元数据就谈不上过滤）
- 过滤是否在存储查询层完成，而不是应用层后删？
- 文档更新是否走"新入库 + 旧失效"的幂等流程？
- 默认检索是否只命中"当前生效 + 有权访问"的数据？

## 小结

检索过滤是 RAG 生产化的分水岭：权限、时效、版本隔离都必须在**检索层**完成，让无权或过期的数据根本到不了模型面前。做法是给 chunk 打全元数据，把用户权限翻译成过滤表达式随检索执行；文档更新走"新版本入库 + 旧版本失效"的幂等流程。**判断标准：不该出现的文档，在存储层就被挡住——而不是靠模型自觉、靠应用层补救。**
