RAG 闭环里，检索产出的是"候选片段"，真正决定回答质量的，是这些片段**怎么被组装进提示词**——这一步叫上下文组装（context assembly）。同样的召回结果，拼得讲究和拼得随意，回答质量可以差出几个档次。原因在于：**模型会把上下文里的每段话都当作"事实依据"，你塞进去的噪音，它会当成真的一起用。** 组装的艺术就是让模型"只看该看的"。

## 上下文里最常见的两个问题

**问题一：塞了噪音。** 召回的前 5 条里可能只有 3 条真正相关，另外 2 条是"沾边但没用"的。如果全塞进去，模型可能被不相关的片段带偏，答出与问题无关的内容，甚至引用错误的出处。**噪音是 RAG 回答质量的第一杀手。**

**问题二：信息顺序混乱。** 直接按相似度分数排序拼接，可能把"背景定义"放在"具体条款"后面——模型的注意力对上下文顺序敏感，最相关的信息应该放在它最容易注意到的位置。

## 组装的原则：质量优于数量

组装的第一步是**去噪**——只把真正相关的片段喂给模型，宁缺毋滥：

```python
def assemble_context(hits: list[dict], max_chunks: int = 4) -> str:
    """从召回的候选里，精选最相关的片段组装上下文"""
    # 1. 过滤低相关候选（分数阈值 / rerank 之后取前 N）
    relevant = [h for h in hits if h["score"] > THRESHOLD][:max_chunks]

    # 2. 按文档逻辑排序（如按章节顺序），而不是按分数排
    relevant.sort(key=lambda h: h["section_order"])

    # 3. 带来源标注拼接
    blocks = []
    for h in relevant:
        blocks.append(
            f"[来源：{h['doc_name']} / {h['section']}]\n{h['content']}"
        )
    return "\n\n".join(blocks)
```

几个要点：

- **设阈值过滤低分候选**——相关度不够的宁可不要，也别污染上下文；
- **按文档逻辑排序**而非分数排序——规范类文档按条款顺序呈现，模型更容易组织出有条理的回答；
- **保留来源标注**——让模型知道每段话出自哪里，为"带出处回答"打基础。

## 提示词结构：把上下文放在模型最该看的位置

上下文组装不只是"拼字符串"，还要设计提示词结构。一个经过验证的 RAG 生成提示骨架：

```text
你是一个知识库问答助手。请依据下面【资料】中的内容回答用户问题。

【资料】
[来源：屋面工程规范 / 4.2 防水等级]
4.2.1 屋面防水等级应根据建筑类别、重要程度及使用功能确定……
[来源：屋面工程规范 / 4.3 材料要求]
……

【用户问题】
{question}

【要求】
1. 只依据【资料】回答，资料中未提到的内容，回答"资料中未找到"
2. 涉及具体条款时，标注出处（规范名 + 条款号）
3. 若【资料】之间存在矛盾，指出矛盾并说明差异
4. 不要使用【资料】之外的知识作答
```

几个设计点：

- **资料用明确的标记包裹**【资料】...【用户问题】...【要求】——结构清晰的提示比散文更能让模型"知道边界在哪"（呼应提示工程篇）；
- **"资料之间矛盾时指出矛盾"** 这条很关键——多租户或版本混杂的知识库里，不同来源可能说法不一，与其让模型"选一个编圆"，不如让它如实指出矛盾；
- **拒答要求写在显眼位置**——"资料中没有就说没有"，这是防幻觉的最后一道提示词闸门。

## 处理冲突与矛盾片段

当召回结果内部不一致时（比如新旧版本条款并存、两份文档说法冲突），组装层就要介入：

```python
def resolve_conflicts(relevant: list[dict]) -> list[dict]:
    """冲突处理：同主题多条时，按优先级保留"""
    # 优先级：版本新的 > 版本旧的；权威来源 > 一般来源
    return sorted(
        relevant,
        key=lambda h: (h.get("version_rank", 0), h.get("authority", 0)),
        reverse=True,
    )
```

优先级可以来自元数据（版本、来源类型），也可以来自业务规则。**组装层的"选谁"逻辑，本质是把知识库的权威性判断前置**——别把这个判断丢给生成模型临时发挥。

## 长度控制：别把上下文塞爆

上下文越长，成本越高、延迟越长、注意力越分散。组装时做长度预算：

```python
MAX_CONTEXT_CHARS = 4000  # 按业务和模型窗口设定预算

def assemble_with_budget(hits: list[dict], budget: int = MAX_CONTEXT_CHARS) -> str:
    relevant = sorted(hits, key=lambda h: h["score"], reverse=True)
    selected, total = [], 0
    for h in relevant:
        if total + len(h["content"]) > budget:
            continue       # 超预算的片段不再加
        selected.append(h)
        total += len(h["content"])
    return format_blocks(selected)   # 再按文档逻辑排序展示
```

预算分配的心得：**与其塞 8 段半相关的长文，不如精选 3~4 段高相关且完整的片段。** 上下文质量与长度不成正比，甚至长度过长会稀释注意力——"让模型只看该看的"意味着敢于做减法。

## 常见踩坑：三种"组装事故"

**事故一：把整个检索结果无脑塞进提示。** 20 条全塞 = 噪音大全，回答被不相关内容带偏的几率极高。

**事故二：片段去掉了来源信息。** 只拼 content 不拼 doc_id/section——模型想标出处也无从标起，追溯链断裂。

**事故三：改写 query 被当成资料塞给模型。** 查询改写的结果是用来检索的，不是用来回答的——把改写结果混进上下文，等于告诉模型"用户其实问的是 X"，可能误导回答方向。

## 小结

上下文组装决定模型"看到什么"，也就决定了它会"答出什么"。四条原则：质量优于数量（敢做减法去噪）、按文档逻辑排序（而非分数）、带来源标注（为溯源打底）、控制长度预算（防注意力稀释）。冲突片段用元数据优先级前置裁决，别丢给模型临场发挥。**组装的艺术不是"怎么把更多内容塞进去"，而是"怎么让模型只看到该看的"。**

下一篇处理知识库的"上游"——入库流水线。文档从进来到进库，中间怎么清洗、怎么设质量门禁，决定了知识库本身的健康度。
