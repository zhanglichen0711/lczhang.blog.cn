RAG 系列走到最后一篇，把前面十一篇的知识串成一条**工程闭环**。RAG 课容易写成二十讲框架说明，落到应用里，可以压成一句话：**文档进来 → 切分入库 → 查询理解与混合检索 → 组装上下文生成 → 用评测集证明它没有悄悄变差。** 前面每一篇是闭环上的一个环节，这篇讲它们怎么协同成一个能上线的体系。

## 闭环全景：从文档到带出处的回答

```text
┌──────────────────────────── 入库侧 ───────────────────────────┐
│ 原始文档 → 解析清洗 → 结构切分(带元数据) → 质量门禁 → 向量化入库 │
│           （rag-chunking / rag-ingestion）                    │
└──────────────────────────────────────────────────────────────┘
                          ↓ chunk 库（带权限/版本/状态元数据）
┌──────────────────────────── 查询侧 ───────────────────────────┐
│ 用户问题 → 意图分流(要不要检索) → 改写 → 混合检索+权限过滤      │
│   → rerank 精排 → 上下文组装 → 按场景提示生成 → 带出处回答       │
│ （rag-query-understanding / rag-hybrid / rag-filter-acl      │
│    / rag-context-assembly / rag-service）                    │
└──────────────────────────────────────────────────────────────┘
                          ↓ 每次请求打 trace
        ┌──── 评测与观测：单测 / 评测集 / 线上 trace ────┐
        │        （rag-evaluation，喂回入库侧与检索侧）       │
        └───────────────────────────────────────────────┘
```

这套体系里每个环节前面都有专篇，这里从"协同"的角度讲五个关键决策。

## 决策一：最小闭环仍然是地基，别在没跑通前堆组件

回顾整个系列，最容易犯的错误是**在最小闭环没跑通时就堆工程组件**：意图分流、混合检索、rerank、评测平台，一股脑全上。结果是系统复杂到出了问题都不知道是哪一环的。

正确的顺序（每一篇其实都在强调）：

```text
第一步：跑通三步闭环（切分→召回→生成），用三条底线测试验证
        （命中答得对 / 范围外拒答 / 出处经得起核对）
第二步：逐个补工程环节，每补一个用评测集证明"确实变好了"
第三步：才谈服务化、权限隔离、完整评测体系
```

**先让系统简单到能看清全貌，再让它复杂到能解决真实问题。** 复杂化必须是"缺什么补什么"的结果，而不是"有什么上什么"的冲动。

## 决策二：检索质量是"组合拳"，不是"单个神组件"

很多人以为检索质量靠一个"最好的 embedding 模型"或"最贵的 rerank"。实际经验是，检索质量是组合拳，每拳解决一个问题：

```text
① 查询理解：意图分流挡掉无关，改写对齐术语     → 解决"问不中"
② 多路召回（原句+改写+关键词）               → 解决"单路盲区"
③ 混合检索 BM25 + 向量 + RRF                → 解决"精确词 vs 语义"
④ rerank 精排                              → 解决"候选噪音"
⑤ 权限/版本/时效过滤（贯穿始终）              → 解决"不该召回的"
```

每一层都便宜、都可独立验证、都解决明确问题。**检索优化的判断标准不是"用了几个高级组件"，而是"评测集召回率每一层加完后确实在涨"。** 加完一层没涨，说明这层在你场景里不需要——撤掉，别为了架构完整而留它。

## 决策三：数据隔离是架构问题，不是提示词问题

多租户 / 多业务线的知识库，最容易在"隔离"上翻车。整个系列的立场是明确的：**权限、版本、时效的隔离必须在检索层完成**——每个 chunk 入库时带全元数据（可见性、属主、组织、版本、状态），检索时把用户权限翻译成过滤表达式，让无权或过期的数据**根本不出库**。

工程上的三个硬要求：

1. 入库时 chunk 元数据不齐 → 拒绝入库（质量门禁的一部分）；
2. 检索过滤写在向量库查询条件里，不是应用层"检索后再删"；
3. 文档更新走"新版本入库 + 旧版本失效"的幂等流程，默认只查现行版本。

**隔离不是"加个字段"，是贯穿入库、检索、版本管理的系统设计。** 这块做扎实，RAG 才能从"演示工具"变成"生产系统"——因为真实业务的第一诉求不是"答得聪明"，是"不该看的不泄露"。

## 决策四：评测要建成"闭环的引擎"，而不只是一次性报告

评测不是"上线前跑一次的报告"，而是**驱动系统持续变好的引擎**。闭环是这样转的：

```text
① 每次改动（切分/检索/提示/模型）→ 跑评测集
② 评测集指标不降 → 才允许上线；降了 → 定位是哪个环节导致的
③ 上线后 → 看线上 trace，发现真实坏案例
④ 坏案例 → 补进评测集 → 下次改动有据可依
```

评测集的三层结构（单测 / 评测集 / 线上 trace）在系列里详述过，这里强调它的**运转节奏**：评测不是月末做一次的事，是每次改动的门槛、每次事故的入口、每次迭代的指南针。**一个没有评测集的 RAG 系统，每次改动都是在赌。**

## 决策五：服务化让闭环"可演进"

把 RAG 包成分层服务（入口 → 业务 → 编排 → 提示），最大价值是**可演进性**：换检索实现不动编排、调提示不动代码、加场景不动架构。分层配合前面四套体系（质量门禁、隔离、评测、trace），RAG 系统就具备了持续迭代的工程条件——任何一个环节出问题，都能定位、能回滚、能验证修复。

## 一个可落地的工程清单

把整个闭环浓缩成上线前的检查清单，逐项打勾：

```text
□ 入库：解析失败显式报错；坏 chunk 被门禁拦截；入库幂等可重跑
□ 元数据：chunk 带 doc_id/section/hash/version/权限字段
□ 查询：意图分流在位；改写保留关键限定；多路/混合检索按需上
□ 隔离：过滤在检索层；默认只查有权 + 生效中的数据
□ 生成：提示要求只依据资料 + 带出处 + 拒答；低温度
□ 评测：三层测试就位；评测集含命中/拒答/溯源题；坏案例回流
□ 服务：分层架构；超时与并发上限；每层有 trace 日志
□ 上线：任何改动先过评测集，再灰度，再全量
```

## 小结：RAG 是工程，不是魔法

把十二篇浓缩成三个认知：

1. **RAG 的最小本质只有三步**（切分、召回、生成），所有复杂组件都是为让这三步更稳而服务的；
2. **质量来自工程组合而非单个组件**——切分打底、查询理解提命中、混合检索+rerank 压噪音、隔离保安全、评测保回归，缺哪块补哪块；
3. **可上线的 RAG 是体系**——质量门禁保证输入健康，检索过滤保证数据边界，评测闭环驱动迭代，分层服务让一切可演进。

**没有出处的流畅回答，比检索失败更危险。** 这句话是 RAG 工程闭环的起点，也是终点——切分是为了切出可引用的块，检索是为了找到该引用的内容，评测是为了验证引用没出错。把这条闭环跑扎实，RAG 就是一个可以放心交给用户的系统，而不是一个演示时惊艳、生产时惊险的原型。
