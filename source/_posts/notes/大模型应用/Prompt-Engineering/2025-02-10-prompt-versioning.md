提示工程系列最后一篇，讲一个经常被忽视、却决定线上稳定性的主题：**提示的工程化管理。** 很多人把提示当成"一段随时能改的文本"——线上效果不好，直接改几个字就部署了，改坏了再改回来。这种随意的代价是：你不知道哪次改动导致了什么变化，不知道线上跑的是哪个版本，出了问题无法回滚。**提示一旦上了生产，它就是代码——是线上系统的一部分，必须按代码的纪律管理。**

## 为什么提示必须版本化

提示对输出的影响，比大部分代码改动都敏感。改一个字可能让召回质量天翻地覆，而这种变化往往是"悄悄发生"的——不报错、不崩溃，只是输出分布漂移了。没有版本管理，你会面临三个问题：

**问题一：无法定位回归。** "最近回答质量好像变差了"——是哪次提示改动引起的？如果你上周改了三次提示都没记录，这个问题无解。

**问题二：无法回滚。** 发现新提示有问题，想回到上一版？没有版本，上一版长什么样你都不知道。

**问题三：无法对比。** 团队里想试两版提示哪个好，没有版本就无从对比。

## 提示的版本化实践

最简单的做法：**提示不进代码字符串，进独立的配置文件或提示管理表，带版本号。** 像管理数据库 schema 一样管理提示。

```yaml
# prompts/intent_classifier.yaml
version: v3
updated_at: 2025-01-20
purpose: 判断用户问题意图，用于问答路由
model: qwen-plus
messages:
  - role: system
    content: |
      你是一个问答系统的意图分类器。
      把用户问题分为三类：查规范 / 查案例 / 其他。
  - role: user
    content: |
      分类下面这个问题：
      用户：{question}
      类别：
examples:
  - user: 屋面防水等级怎么定？
    label: 查规范
  - user: 今天天气怎么样？
    label: 其他
```

工程上要配套三件事：

**1. 提示与代码同仓库。** 提示文件跟着代码走 Git，改动可追溯、可 review。不要只存在数据库或只贴在对话记录里。

**2. 运行时按版本加载。** 代码里不写死提示内容，而是从配置文件加载并带上版本号——这样线上日志里能记录"这次请求用的是哪个版本的提示"，出问题能精确归因。

**3. 灰度发布。** 提示改动别全量上线。先让 10% 流量用新提示，对比指标后再放量。这和代码灰度是同一个道理——**提示是最敏感的生产代码，最需要灰度。**

## 评测：提示改动的"测试用例"

代码有单测，提示也该有。给每个关键提示配一套**固定的评测用例**——一组"输入→期望输出"的业务题，每次改动提示后跑一遍，看通过率有没有下降。

```python
# 意图分类的评测用例
INTENT_TEST_CASES = [
    ("屋面防水等级怎么定？", "查规范"),
    ("商场屋顶渗漏有整改案例吗？", "查案例"),
    ("帮我写一首诗", "其他"),
    ("规范里外墙保温厚度要求是多少？", "查规范"),   # 边界：问规范数值
    ("最近天气热，屋面会不会开裂？", "其他"),        # 边界：口语化 + 疑似查规范
]

def evaluate_intent_prompt(build_prompt_fn, model: str) -> dict:
    correct = 0
    errors = []
    for question, expected in INTENT_TEST_CASES:
        prompt = build_prompt_fn(question)
        result = call_model(prompt, model=model)
        if result == expected:
            correct += 1
        else:
            errors.append({"question": question, "expected": expected, "got": result})
    return {"pass_rate": correct / len(INTENT_TEST_CASES), "errors": errors}
```

这套用例的维护原则：

- **每次线上误分类，把那条真实输入加进用例**——就像修 bug 时先加回归测试；
- 用例覆盖**典型分支 + 边界案例**（见少样本那篇的挑选原则）；
- 改动提示的验收标准是"用例通过率不低于上一版"，否则不部署。

## 用 A/B 对比代替"我觉得更好"

评测用例能防回归，但提示的"改进"往往没有标准答案——新提示在用例上持平，但可能真的更好（或更差）。这时需要 A/B 对比：新老提示各服务一部分真实流量，对比业务指标（准确率、用户反馈、拒答率、成本）。

```text
改提示的完整流程：
1. 从线上误分类里挑问题，形成新提示假设
2. 离线：新提示在评测用例上跑，通过率不低于老版才继续
3. 灰度：新提示接 10% 流量，对比业务指标 1-3 天
4. 放量：指标更好或持平 → 全量；变差 → 回滚到老版
5. 归档：无论成败，把这次改动和结论记录进提示的变更日志
```

这套流程和代码发布的差别只有一点：**提示的改动频率更高、影响更隐蔽，所以纪律要更严。**

## 变更日志：提示的"git history"

给每个提示维护一段变更说明，记录改了什么、为什么改、结果如何：

```text
v3 (2025-01-20)：
  - 在 system prompt 中新增"不确定时归为闲聊"的兜底指令
  - 背景：线上 15% 的无意图问题被误分为查规范
  - 验证：评测用例通过率 92% → 96%，误分类下降
v2 (2025-01-10)：
  - 更换意图示例 2 个，贴近真实口语输入
  - 验证：边界用例通过率提升
```

三个月后回看这份日志，你能清楚说出"这个提示是怎么演进成现在这样的"——这既是团队资产，也是线上问题归因的第一手材料。

## 小结

把提示当代码管理，是提示工程从"个人技巧"走向"团队工程"的分水岭。四件事：版本化（进仓库、带版本号）、评测（固定用例防回归）、灰度（新提示先小流量）、变更日志（记录每一次改动的因果）。**提示是线上运行的程序，而程序没有版本管理和测试，就是在裸奔。**

到此提示工程六篇完结：从理解模型续写机制，到结构化四件套、少样本、输出约束、思维链，再到工程化管理——你已经有了把模型"调教"成稳定组件的能力。下一篇开始进入大模型应用的核心版块 RAG：给模型外挂知识，让它回答它没学过的问题。
