前两篇讲了多模态的能力和 VLM 的调用，这一篇回答最关键的问题：**这些能力在真实业务里怎么组合成能用的方案。** 因为真实业务几乎没有"纯看图"或"纯读文"的场景——一份质检记录里既有缺陷照片又有文字结论，一份验收报告里既有扫描图章又有条款文字。**多模态应用的正确形态是"组合"：让每个模型干它最擅长的一段，用工程把它们缝成一个完整流程。** 这篇用两个最典型的业务场景展开。

## 场景一：工程质检——"看图定缺陷 + 出报告"

这是图文协同最典型的场景：现场拍一堆照片，要判断有没有缺陷、什么缺陷、多严重，最后出一份带结论和建议的报告。单靠任何一个模型都做不完整——**检测靠 CV、理解靠 VLM、规范依据靠 RAG**。

完整流程拆解：

```text
现场照片（几十张）
   ↓ ① CV 检测（传统视觉模型）
   │    每张图框出疑似缺陷区域 + 初步分类 + 置信度
   ↓ ② 分流
   │    高置信缺陷 → 直接采纳 CV 结果（快、便宜）
   │    低置信/模糊样本 → 升级给 VLM 判断
   ↓ ③ VLM 细看（只处理升级上来的少数图）
   │    结合裁剪后的局部图，判断缺陷类型、成因、严重度
   ↓ ④ RAG 查规范
   │    根据缺陷类型，检索对应规范条款和处理要求
   ↓ ⑤ LLM 汇总
   │    生成质检报告：每处缺陷（位置/类型/依据/建议）
```

**为什么这样组合而不是全用 VLM？算一笔账**：几十张图全送 VLM，图像 token 成本高一个量级、延迟翻倍；而 CV 能秒级处理 90% 的清晰缺陷。**VLM 只处理 CV 拿不准的少数**——成本可控，准确率反而更高（VLM 看"疑难样本"比批量看图更专注）。

实现上的衔接（每段的输入输出要结构化）：

```python
def quality_inspection(photos: list[str]) -> dict:
    """工程质检流水线：CV 粗检 + VLM 精判 + RAG 依据 + LLM 报告"""
    findings = []
    for photo in photos:
        # ① CV 初检：框缺陷 + 置信度
        cv_result = cv_detect(photo)      # [{box, type, conf}, ...]

        for det in cv_result:
            finding = {
                "photo": photo,
                "box": det["box"],
                "defect_type": det["type"],
                "confidence": det["conf"],
            }
            # ② 低置信 → 升级 VLM（裁局部图细看）
            if det["conf"] < 0.8:
                crop = crop_image(photo, det["box"])
                vlm_verdict = vlm_judge(crop, det["type"])
                finding.update(vlm_verdict)      # 修正类型/严重度

            # ③ 高置信缺陷 → RAG 查规范依据
            if finding["confidence"] >= 0.7:
                finding["spec_ref"] = rag_query(
                    f"{finding['defect_type']} 处理要求 {finding.get('severity','')}"
                )
            findings.append(finding)

    # ④ 汇总成报告
    return llm_report(findings)   # 结构化质检报告
```

**这条流水线的主线是"分工"**：CV 负责"框得准"、VLM 负责"看得懂"、RAG 负责"查得着"、LLM 负责"写得出"。每个模型只做最擅长的一段，中间用结构化数据衔接（缺陷框 → VLM 只看框内、缺陷类型 → RAG 只查对应规范）。

## 场景二：图文混合文档的知识库——"VLM 前置解析 + RAG 检索"

企业知识库里大量文档是"图文混合"的：扫描的验收报告、带流程图的制度文件、带产品照片的故障手册。纯文本 RAG（前面 12 篇）处理不了图里的信息——**图的入口要用 VLM 前置解析，把图变成文字描述或结构化数据，再进 RAG 检索**。

```text
原始图文文档
   ↓ ① 解析：VLM 把每页转成结构化文本
   │    文字进文本流，图片转成"图片说明"或"结构化描述"
   │    （例：一张缺陷照片 → [图片] 屋面防水层裂缝，位于西南角……）
   ↓ ② 切分入库（RAG 入库流水线）
   ↓ ③ 用户提问 → 检索 → 生成（带出处）
```

VLM 解析时给图片生成的**描述质量**，直接决定图里的信息能不能被检索到：

```python
def describe_image_for_index(image_path: str) -> str:
    """把图转成可检索的文字描述（供 RAG 索引）"""
    return vlm(
        image=image_path,
        prompt="""用结构化文字描述这张图，供后续检索使用：
1. 图类型（缺陷照片/流程图/表格截图/示意图）
2. 图中关键内容（缺陷：类型/位置/严重度；流程：环节和顺序）
3. 图中出现的文字（编号、标签）""",
    )
```

**方案要点：图片描述 = 图的"检索入口"**。描述写得详细，用户问"屋面裂缝的图"才能召回这张图；描述写成"这是一张图"就毫无检索价值。**VLM 前置解析是图文知识库能否工作的关键环节，值得用评测来打磨描述质量。**

## 组合方案的通用原则

从两个场景里提炼出图文协同的通用设计原则：

**原则一：按任务分模型，不按"先进"选模型。** 每一步问"这个子任务谁最擅长、最便宜"，而不是"哪家模型最先进"。检测找 CV、理解找 VLM、依据找 RAG、表达找 LLM——**用对模型比用贵模型重要。**

**原则二：中间结果必须结构化。** CV 输出缺陷框（坐标+类型+置信度）、VLM 输出判断（类型+严重度+置信度）、RAG 输出规范条款——**每一步的输出是下一步的输入，不结构化就无法衔接、无法评测。**

**原则三：置信度是"分流开关"。** 高置信走便宜路径、低置信升级贵模型（CV→VLM）、关键结论要人复核（VLM→人工）。**置信度机制让"成本-质量"可调**——要求高了多升级、预算紧了多走便宜路径。

**原则四：全程可观测可评测。** 每段模型调用都要记录（哪个模型、输入输出、置信度、耗时成本），组合方案才能调优——哪一段是瓶颈、哪一段出错最多，用数据说话。

## 小结

真实业务是图文混合的，多模态应用的正确形态是**组合而非单模型**：质检场景 = CV 检测 + VLM 精判 + RAG 查规范 + LLM 出报告；图文知识库 = VLM 前置解析（图片转描述）+ RAG 检索。四条设计原则：按任务分模型、中间结果结构化、置信度做分流开关、全程可观测可评测。**多模态落地的本质不是"上一个看图模型"，而是把视觉能力作为一段组件，缝进已有的 AI 应用架构里——它解决的是"信息入口"的问题，而信息进来之后，检索、评测、生成，还是那套已经验证过的工程。**
