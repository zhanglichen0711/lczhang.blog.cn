vLLM 原理：PagedAttention 与连续批处理

vLLM 吞吐碾压的两个核心机制：KV Cache 分页管理消除碎片，连续批处理让 GPU 满载。

#vLLM #PagedAttention
目录

vLLM 相对”裸跑”吞吐高 5~20 倍，靠两个核心机制：PagedAttention（KV Cache 分页管理）和连续批处理（token 粒度动态调度）。原理篇已经在推理优化版块讲过一个，这一篇把它们放回 vLLM 的实现视角，讲清”为什么是 vLLM 做到别人做不到的”。

传统 KV Cache 的浪费：碎片化

KV Cache 优化（KV Cache 篇）讲过要缓存中间结果，但朴素实现有个隐藏问题——连续内存分配：每个请求的 KV Cache 要一段连续显存，而请求长度是动态增长的：

显存利用率的浪费，直接等于并发能力的浪费。

PagedAttention：像虚拟内存一样管 KV

vLLM 的解法借鉴操作系统虚拟内存：把 KV Cache 切成固定大小的”页”（block），按需分配、不要求连续。

三个工程红利：

  1. 显存利用率接近满——同样的卡能服务多得多的并发；
  2. 块共享：多个请求共享同一段 prompt（多轮对话的历史、批量评测的公共前缀）时，KV 块可以复用（copy-on-write），省下大量重复存储；
  3. 调度灵活：内存按块精确计量，调度器知道”还能接多少请求”。

连续批处理：调度到 token 粒度

vLLM 的第二个机制是引擎级调度器（推理优化版块详述过原理）：每轮解码，动态把所有”此刻要算下一个 token”的请求拼成一个批。

配合 PagedAttention 的按块计量，调度器能精确回答”现在 KV 显存还能接几个新请求”——两者是”内存管理”和”任务调度”的绝配。

两个机制如何协同

**连续批处理管”谁上 GPU”，PagedAttention 管”上多少人显存不爆”**——一个求满载、一个守上限，共同支撑高吞吐。

为什么别的框架早期做不到

理解 vLLM 的贡献：KV Cache 分页这个想法”听起来简单”，但实现要动整个推理栈（注意力内核要支持非连续内存的 KV、调度器要精确计量）。早期 HF/朴素方案用连续内存图省事，换来 30~40% 的显存浪费和调度低效。vLLM 的价值是把这些系统级优化做成了开箱即用的引擎——这也是它在 2023 年一开源就统治自建推理的原因。

对使用者的意义

理解原理不是为了自己实现，而是为了用好：

  1. 长 prompt / 共享前缀场景：PagedAttention 的块共享 + 前缀缓存，让多轮对话和批量任务吞吐大增——尽量复用相同 system prompt；
  2. 并发压测才见真章：连续批处理的价值只在并发下显现（串行请求吃不到红利）；
  3. 显存参数的意义：gpu-memory-utilization 决定可分配 KV 块总量，直接影响并发上限（呼应参数篇）。

小结

vLLM 的两个引擎级机制：PagedAttention 用分页消除 KV 碎片（显存利用率近满、块可共享），连续批处理把调度细化到 token 步（GPU 永不空转）。一个管内存、一个管调度，配合成就 5~20 倍吞吐。原理透明之后，下一篇的性能调优就全是”在理解基础上的参数选择”。
