FastAPI 简介

为什么用类型注解写接口，FastAPI 如何成为 AI 应用的服务层。

#后端 #FastAPI
目录

把一个 RAG 问答系统真正交到用户手里，最后一道工序通常是：把检索和生成的逻辑包成一个后端服务，让网页、小程序、内部平台都能通过 HTTP 调用它。服务层用什么框架写，直接决定了这个接口层是顺手还是硌手。

我的选择是 FastAPI。这一篇先讲清楚它是什么、为什么适合做 AI 应用的服务层，后面的篇幅再逐层展开怎么用。

FastAPI 是什么

FastAPI 是一个基于 Python 3.6+ 类型注解的现代 Web 框架，2018 年发布。它站在两个成熟组件的肩膀上：Starlette 提供异步 Web 能力，Pydantic 提供数据校验与序列化。所以它一出生就同时具备「异步高性能」和「类型安全」两条腿。

在 Python 后端框架里，它和两个老前辈的定位差异很明显：

框架 特点 适合
Flask 轻量、自由，路由/模板/ORM 全自己拼 小服务、快速原型
Django 全家桶，自带 ORM、Admin、认证 内容型、管理后台为主的产品
FastAPI 类型驱动 + 原生异步 + 自动文档 API 服务、AI 应用接口层

选 FastAPI 不是因为它”新”，而是因为它解决的问题恰好是 AI 应用接口层最疼的那几个。

Python 的函数注解本来是可选的”注释”，FastAPI 把它变成了约束。看一个例子，左边是普通函数，右边是 FastAPI 路由：

区别在于：当声明了 q: str，FastAPI 就知道请求里应该有一个叫 q 的参数，会把它解析出来、校验类型、再传给函数。调用方传了个数字过来？框架直接返回 422 错误，根本不会让这个请求进到你的业务代码里。

这带来的连锁好处是：你不再需要手写参数解析和校验那一堆样板代码，函数签名本身就是接口文档。RAG 服务的查询接口参数（query、top_k、过滤条件、权限标识）一多，这种”声明式”写法的优势就非常明显。

自动生成 OpenAPI 文档

写了路由之后，启动服务打开 http://127.0.0.1:8000/docs，会看到一个可交互的 API 文档页面——每个接口的参数、类型、示例、响应结构都列好了，还能直接在页面上点”Try it out”发请求测试。

这个文档不是手写的，是框架根据你的类型注解自动生成的（OpenAPI 规范，也叫 Swagger）。前后端联调时，后端把文档链接甩过去，前端照着调就行，不用再维护一份”迟早过期”的接口说明。

原生异步：等待大模型时不阻塞

AI 服务的典型场景是调大模型接口，一次请求要等好几秒。如果框架是同步的，每个在等的请求都会占着一个线程，线程池很快耗尽，后面的人全部排队。

为什么说它适合做 AI 的服务层

抛开框架本身的特性，FastAPI 和 AI 应用的契合是生态层面的：

  1. Pydantic 结构化——大模型输出的 JSON 解析、请求参数强校验，用的就是同一个 Pydantic，心智不用切来切去。
  2. 流式支持成熟——StreamingResponse 和 WebSocket 是框架一等公民，LLM 流式输出直接透传。
  3. OpenAPI 即插即用——接口定义能直接给前端、给 Agent 当工具描述，Agent Card 或 MCP 工具清单里的输入 schema 几乎可以照搬。
  4. 依赖注入清晰——鉴权、数据库会话、权限过滤这类横切逻辑声明一次到处复用，RAG 服务里”按角色过滤可见文档”这种需求很好落地。

小结

FastAPI 的价值不是”写得更快”这一个点，而是让接口的契约显式化：类型注解驱动校验、文档、序列化三者合一，原生异步扛得住等待型的 AI 请求。理解了它为什么这样设计，后面的使用篇会顺很多。
