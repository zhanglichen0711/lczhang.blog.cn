少样本提示：用例子教会模型

一段好的描述不如三个对的比例子。示例是给模型看的'测试用例'，挑例子就是在定义任务。

#Prompt #Few-shot
目录

提示工程里有个反复被验证的经验：描述性指令再详细，也不如给模型看几个例子有效。 你花三百字解释”要提取条款编号、适用场景、违规后果”，模型可能还是输出五花八门；但你给它三个”输入→正确输出”的配对，它立刻就能照葫芦画瓢。这背后的原理还是那一条：模型是续写器，示例比抽象规则更贴近它学习语言的方式——它是从例子里学会模式的，不是从规则里。

为什么示例比描述有效

想一想我们教人做事的方式：光讲规则，对方总要问”举个例子？”；给了一个例子，理解立刻具体化。模型也是这样，而且更极端——它的训练数据就是海量的”文本对”，它对”照着这个样子来”的理解，远比对”按以下三点要求执行”的理解要深。

原因有两点：

  1. 示例隐含了描述说不清的信息。 比如输出格式，你说”输出 JSON”，模型可能给你嵌套 JSON、带注释的 JSON、甚至 JSON 外面裹一段解释。但你给一个”输入→纯 JSON 输出”的例子，格式就通过模仿被锁定了——格式这种信息，靠例子传递远比靠文字描述可靠。
  2. 示例约束了风格和边界。 描述说”简洁回答”，模型对”简洁”的理解因人因模型而异；但例子展示的”三行以内、直接给结论”，是模型能精确模仿的。

Few-shot 的基本写法

Few-shot 就是在提示里放几个”输入-输出”对，让模型模仿。看一个把用户问题分类到业务意图的例子：

模型看到三个例子的模式后，会把”幕墙开启扇的密封要求”归到”查规范”。这里的关键是：三个例子覆盖了任务的主要分支（三类各一个），模型就能学会”按例子里的映射规则来”。

挑例子的三条原则

例子不是随便挑的，挑例子其实是在定义任务——模型会从你的例子里反推”这个任务的规律是什么”，所以例子的质量直接决定任务被理解成什么样。

原则一：覆盖典型分支，不只给”完美答案”。 上面那个例子如果三个全是”查规范”，模型可能以为所有问题都是查规范。每个输出类别至少给一个代表例子，让模型看到完整的映射面。

原则二：包含”困难案例”和”边界案例”。 好的测试集要含边界题，好的示例也一样。如果你的分类有个容易混淆的边界（比如”查规范”和”查案例”的模糊地带），放一个边界例子，模型就知道模糊输入该归哪边。

原则三：例子要真实，不要编造极端完美的例子。 从真实数据里挑例子。如果你的真实输入经常带口语、错别字，例子就别全用书面语——例子和真实输入的分布越接近，模型在实际数据上的表现越好。 例子太”干净”而线上输入很”脏”，模型会水土不服。

Few-shot 的进阶：错误示范也有用

传统机器学习的训练里，正负样本都要有。提示里也可以给”反例”——一个典型的错误输出，并说明为什么错：

反例的价值在于把”边界”显式化。当任务存在容易混淆的类别时，一个标注了错误原因的反例，比三个正确例子更能教模型”别踩这个坑”。

示例数量：不是越多越好

Few-shot 确实比 Zero-shot（无示例）稳定，但示例不是越多越好：

  • 3~5 个精心挑选的例子通常就够，质量远大于数量；
  • 例子太多会撑长上下文，增加成本和延迟，还可能引入无关模式让模型困惑；
  • 超过一定数量后收益急剧递减——这时候该做的不是加例子，而是考虑微调或换任务设计。

判断例子数量是否合适的标准：每个例子是否都在教模型一个它自己想不到的新东西。 重复同类例子是浪费，边界例子和困难例子才是真正提升。

Few-shot 在工程里的真实形态

在真实项目里，few-shot 例子通常不硬编码在提示里，而是作为可配置数据维护：

这样设计的好处是：调分类行为变成改数据，而不是改 prompt 字符串。 当线上出现新类别的误分，把那条真实输入加入示例集，就是一次”用真实数据做的提示迭代”——这比反复修改描述性指令可靠得多。

小结

示例比描述更有效地约束模型的输出，因为模型天生从例子里学模式。挑例子的三条原则：覆盖典型分支、包含边界与困难案例、贴合真实输入分布。几个精心挑选的例子胜过几百字描述——但例子要作为数据管理，而不是埋在 prompt 里。
