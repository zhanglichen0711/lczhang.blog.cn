评测集设计：golden set 与坏案例归档

好的评测集是代表性样本而非全量穷举：典型题定基线、边界题探盲区、坏案例防回归。

#评测 #评测集
目录

评测集是 LLM 应用评测的地基——没有题，一切指标都是空谈。但”怎么出题”远没有看起来简单：出得太简单，评测集分数虚高，系统真上了线就露馅；出得太偏，评测集无法代表真实业务。这一篇讲评测集设计的方法论：好的评测集不是全量穷举，而是精心挑选的代表性样本——三类题各司其职。

评测集不是什么

先破除两个误区：

误区一：评测集 = 把所有可能的问题都列出来。 真实业务的问题空间近乎无限，穷举既不现实也没必要。而且评测集越大越难维护——每次业务变化都要同步改几十上百条题，改到后来没人愿意动它。

误区二：评测集 = 随便攒一些问题。 从线上日志随机抓 50 条就当评测集，很可能全是”简单题”——因为容易的问题占比天然高，而真正暴露系统缺陷的是那些边界题和疑难案例。随机抓取攒不出好评测集，设计才有。

好的评测集应该是：几十到几百条、覆盖各场景、包含关键边界的代表性样本。 它不追求”覆盖所有题”，追求”能代表所有题的类型”。

评测集的三类构成

一个合格的评测集，由三类题组成，各司其职：

第一类：典型题——定基线。 每类核心场景挑几条最有代表性的正常问题。它们定义了”系统日常表现如何”：

第二类：边界题——探盲区。 挑那些”容易混淆、容易出错”的问题。它们是最有价值的题——评测集的主要价值不是确认系统会什么，而是暴露系统不会什么：

第三类：坏案例——防回归。 线上曾经答错的问题（连同正确答案），每次发现就补进评测集。它们是评测集的”回归测试”，保证修过的 bug 不会复发（RAG 篇提过这个机制，这里强调它在评测集中的位置——坏案例是评测集里最珍贵的一类题，因为它们代表真实用户的真实痛点）。

golden set：评测集的”黄金标准”

评测集里最关键的一部分叫 golden set（黄金集）——那些有明确正确答案、评判标准无争议的题。它们的作用是给系统一个”客观锚点”：

golden set 为什么重要？因为它是评测集里唯一能客观判断对错的部分——关键词命中、是否拒答，都可以用规则自动判分，不需要人工或 LLM 打分。它承担两个职责：

  1. 快速回归：每次改动跑 golden set，秒级得到”有没有明显变坏”的信号；
  2. 校准其他评测：当 LLM-as-Judge 的评分和 golden set 的客观答案冲突时，说明打分标准需要校准。

设计原则：评测集必须有相当比例（建议三成以上）是 golden set 这类客观可判的题——否则整套评测都依赖主观打分，地基不稳。

坏案例归档：让评测集”生长”

评测集最容易被忽略的是持续维护。一个好评测集不是一次建完的，而是跟着系统一起生长的：

坏案例归档有两个层面的价值：对评测，它让评测集越来越贴近真实痛点；对工程，它本身是一份”系统缺陷地图”——统计坏案例的根因分布（多少是切分、多少是检索、多少是提示），能告诉你下一步该优化哪。坏案例不是失败记录，是优化路线图。

评测集的规模与维护节奏

规模：不必贪大。一个小型应用 50-100 条、中型 200-300 条足够驱动迭代。关键是结构合理（典型 + 边界 + 坏案例）+ golden set 占比够。宁可 100 条精心设计，不要 1000 条随手攒的。

维护节奏：

  • 每次业务新增场景 → 补典型题；
  • 每次线上发现坏案例 → 补回归题；
  • 每季度 → 审视一遍评测集，删掉过时题（业务变了）、补充新边界；
  • 评测集本身要版本化（和代码同仓库），改动可追溯。

小结

评测集设计三原则：代表性而非穷举（典型题定基线）、边界题探盲区（暴露系统不会什么）、坏案例防回归（线上问题持续回流）。golden set 是评测集的客观锚点，保证三成以上可客观判分。评测集是活的资产——跟着业务和坏案例生长，而不是一次性建完就归档。没有好评测集，后面所有评测方法（Judge、线上评测）都是建在沙地上。
