LLM 推理为什么慢：生成式解码的瓶颈

为什么生成 100 个词要好几秒：自回归解码的串行本质与三个性能瓶颈。

#LLM #推理优化
目录

训练一个大模型很贵，但真正每天花钱的是推理——每个线上请求都要模型跑一遍。LLM 推理有个明显体感：出第一个字慢、后续逐字输出。要优化它，得先理解”生成式解码为什么本质上就慢”。这一篇把瓶颈拆清楚，后面几篇的每一个优化手段都对着这些瓶颈来。

自回归：一个字一个字”想”

LLM 生成文本是自回归的：生成第 N+1 个词时，要把前 N 个词全部重新过一遍模型（因为要基于完整上下文预测下一个词）：

关键点：生成第 100 个词，模型要把 100 个词的前向传播完整算一遍。于是生成 N 个词的总计算量 ≈ 1+2+3+…+N 份单步计算——这就是推理”慢”的结构性根源。

一次推理的两个阶段

一次请求分两段，瓶颈完全不同：

阶段 做什么 特点
预填充（Prefill） 一次性处理整段输入提示 计算密集，可用矩阵并行，快
解码（Decode） 逐词生成输出 每步只算 1 个新词，内存带宽密集，慢

解码阶段慢的真相很反直觉：**每生成一个 token，瓶颈不是算力，而是”读权重”**。模型要把几十 GB 的权重从显存读一遍才能算出下一个词，读内存的速度（带宽）远慢于计算——GPU 大部分时间在”等数据”而不是”在计算”。这也解释了为什么小模型在消费级显卡上可能比大模型更快——权重小、读得快。

三个性能瓶颈

把”为什么慢”拆成三个可优化的瓶颈：

瓶颈一：串行生成

解码必须一步一步来，第 2 个词依赖第 1 个词的结果——无法像训练那样整体并行。单个请求的解码延迟被卡死在”步数 × 每步耗时”。

瓶颈二：重复计算（KV Cache 的前置问题）

没有缓存时，生成第 N 个词要把前 N 个词的注意力全部重算——前 N-1 词的注意力结果其实没变，纯属浪费。解法就是后面要讲的 KV Cache：把已算过的中间结果存下来复用。

瓶颈三：内存带宽受限

解码每一步都要读取全部模型权重，吞吐被显存带宽卡住（而非算力）。所以推理优化的核心思路之一是”让权重更小“（量化）和”一次多服务几个请求“（批处理，摊薄权重读取）。

为什么并发场景更糟

单请求已经很慢，多个并发请求若各跑各的，GPU 利用率更低：每个请求串行解码时都在”等权重”，GPU 算力大量闲置。推理引擎的核心价值就是把多个请求的串行解码”拼”成批量计算——这也是 vLLM 这类引擎存在的原因（后面专篇展开连续批处理）。

一张图记住推理优化的目标

优化手段都是对着”串行、重复计算、带宽瓶颈”这三个病根下药。

小结

LLM 推理慢的根源是自回归解码的串行本质 + 解码阶段受内存带宽限制。三个核心瓶颈：串行生成、重复计算（KV Cache 前身）、带宽受限。理解了瓶颈，后面的 KV Cache、批处理、投机解码、量化——每一招你都看得懂它到底在解哪个题。
