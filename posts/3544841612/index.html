数据隐私与脱敏合规

PII 进模型前先处理，权限边界在架构上划死，别指望模型守口如瓶。

#安全 #隐私 #脱敏
目录

注入和越狱防的是”模型被操纵”，但数据安全要防的是另一类问题——你自己的系统把不该给的东西泄露出去了：A 用户的数据被 B 用户检索到、内部文档被发给第三方模型、用户手机号出现在日志里。这些泄露往往不是模型”变坏了”，而是系统设计时没把数据边界划清楚。这篇讲 LLM 应用数据安全的三个层面：进模型前的脱敏、检索时的权限边界、以及合规视角的落地。

数据在 LLM 应用里的流动路径

先看清数据经过哪些环节，才知道在每个环节该设什么防线：

三个关键暴露点：② 检索环节可能跨用户泄露；③ 拼进 prompt 发给第三方模型（数据出境）；①⑤ 输入输出都可能含 PII 且会进日志。每个点对应一类防护。

权限边界：别指望模型”不泄露”，让数据根本到不了它面前

LLM 应用最容易犯的错是：把所有数据检索出来塞给模型，然后寄希望于 prompt 里写”不要泄露其他用户的数据”——这在安全上等于裸奔。模型没有可靠的机制区分”这个数据属于谁”。

正确原则是权限下推：在检索这层就用权限过滤把数据挡在门外，让模型根本看不到无权访问的数据。RAG 架构里，知识库文档按权限打标签，检索请求带上用户身份做过滤（前面 Milvus 篇的 expr 过滤就是干这个的）：

几个落地要点：

  • 权限模型越简单越安全：复杂的 ACL 容易配错。常见简化是”数据按租户/组织隔离 + 文档级可见性”两级；
  • 默认拒绝：没有显式授权就是不可见，别默认全放行；
  • 过滤在存储层，不在应用层：把全部数据查回来再在代码里过滤，等于把”用户 A 的数据”先拉到了服务内存——过滤要在查询条件里做，让存储层直接返回权限内的结果。

脱敏：PII 在进模型前先处理

即使权限过滤做好了，合法数据里仍可能混着个人敏感信息（PII）——手机号、身份证、地址、邮箱。这些信息不该原样发给第三方模型（数据出境风险），也不该留在日志里（泄露风险）。做法是进模型前脱敏，出模型后还原（或直接不还原）。

脱敏按敏感程度和业务需要分几档：

第一档：直接移除。与任务无关的 PII（比如用户闲聊里带出的身份证号）直接删掉再送模型。

第二档：替换占位符。与任务相关但不能外泄的，用占位符替换，处理完再映射回来：

第三档：匿名化（不还原）。用于统计/分析场景时，PII 换掉就不还原了——能还原的叫脱敏，不能还原的才叫匿名化，合规上匿名化数据不受个人数据法规管辖，是更彻底的方案。

统一收口：脱敏逻辑要在一处实现（独立的 sanitize 模块），在输入进入业务流、以及数据写入日志的两个入口统一调用——散落各处的脱敏迟早会漏。

数据出境与第三方：发给云端模型前问一句”该不该发”

调用第三方模型 API 时，数据会离开你的服务器。合规视角的决策树：

  1. 数据能不能出域？ 涉及用户隐私、商业机密、政务数据的，优先私有化部署模型，或选有数据协议的云厂商；能出域的，再往下走；
  2. 能不能少发？ 只发完成任务必需的最少内容——不需要全文，就发摘要；不需要原始文档，就发检索片段；
  3. 能不能脱敏后发？ 前面两步走完剩下的 PII 再脱敏一层。

企业环境常配”出域网关”统一管这件事：所有要发给外部模型的内容过网关，网关做脱敏、记录审计日志、按策略放行或拦截——让”数据能不能出去”由策略决定，而不是由开发者的习惯决定。

日志与训练：两个容易被忽略的泄露口

日志泄露：前面日志篇强调过”别把 PII 记进日志”。LLM 应用要格外注意——prompt、输出这些”业务数据”本身就常含 PII，如果全量打日志就是持续泄露。审计需要记录，但可以脱敏后记录：记录替换后的占位符版本，需要溯源时用密钥解映射（把映射表本身加密保存）。

数据被用于训练：调用第三方 API 时，默认假设数据可能被用于改进模型（各厂商政策不同）。涉及敏感数据的场景，要么选承诺不用于训练的厂商服务，要么用私有化部署——**读清楚服务协议的数据使用条款，别默认”不会用”**。

合规视角：几件必须做的事

不同地区法规不同（中国有《个人信息保护法》，欧美有 GDPR），具体条款要咨询法务，工程侧有几件事是共通的：

  • 数据清单：知道自己系统里有哪些 PII、存在哪、流向哪——这是合规的地基，没有清单一切免谈；
  • 最小化收集：能不收的 PII 就不收（比如不需要手机号就别让用户填）；
  • 留存期限：日志、对话记录设定保留期限，到期清理，别永久堆着；
  • 告知与授权：面向用户的产品，隐私政策说清楚”哪些数据会用于 AI 处理、是否发给第三方”；
  • 泄露响应：有流程能快速定位”某批数据泄露影响哪些用户”（这又回到可观测性和审计日志的价值）。

小结

数据安全三层防护：权限边界在存储层划死（过滤在查询条件里，数据到不了模型面前）；脱敏在进模型前处理 PII（占位符替换或匿名化，统一收口实现）；出境合规在调用第三方前把关（能不出就不出、能少发就少发、能脱敏就脱敏）。再补上日志脱敏和数据清单，LLM 应用的数据防线才算完整。前面的防线都在管”输入和过程”，最后一层防线在出口——模型输出的内容要经过校验才能发出去，下一篇讲护栏设计。
