Embedding 与向量检索：让检索理解语义

把文字变成向量，用距离衡量语义。选对 embedding 模型、度量方式与索引，是召回质量的地基。

#RAG #Embedding
目录

RAG 闭环的第二步”召回”里，最核心的技术是向量检索——而向量检索的地基是 Embedding：把一段文字变成一个向量（一串数字），让”语义相近”的文字在向量空间里”距离相近”。这篇讲清楚 Embedding 是什么、怎么选、怎么用对，以及为什么召回质量问题大多出在”embedding 没选对”而非”代码写错”。

Embedding：把文字变成”可计算相似度的向量”

传统的关键词检索（比如数据库的 LIKE）只能做字面匹配：搜”屋面漏水”，匹配不到写”屋顶渗水”的文档——字不同，但语义相同。Embedding 要解决的就是这个：让检索理解”意思”，而不是只认”字面”。

Embedding 模型把一段文字映射成一个高维向量（通常是几百到几千维）：

文字变成向量之后，”语义相似度”就变成了”向量距离”——可以用余弦相似度等度量计算。于是检索变成一个数学问题：把用户的查询也转成向量，然后在知识库里找离它最近的几个向量。

这就是”语义检索”的全部秘密：不是模型理解了你的话，而是 Embedding 把语义相近的文字映射到了相近的位置。

选 Embedding 模型的三个维度

Embedding 模型的选择直接影响召回质量，选型看三个维度：

维度一：语言与领域匹配。 中文业务用中文表现好的模型（如 bge-m3、text-embedding-v4 系列）；领域术语多（法律、医疗、技术规范）时，通用模型可能”看不懂”专有名词的语义，需要试领域数据的效果。

维度二：向量维度与效果平衡。 维度高（如 1024/2048）通常表达力强但存储和计算成本高；维度低检索快但可能损失精度。先看效果，再看成本——用你的真实语料测，而不是只看宣传。

维度三：检索任务的表现。 Embedding 模型分两类：通用语义模型和检索专用模型（专门为”query vs 文档”匹配训练）。检索场景优先选检索专用模型，它们对”查询”和”文档”两种文本的处理更贴合 RAG 需求。

选型不是一劳永逸：embedding 模型升级后，旧向量可能不兼容（维度/分布变了），需要重新向量化全库——这是换 embedding 模型的隐性成本，选型时要想到。

相似度度量：余弦就够了

向量算好之后，怎么衡量”多近”？主流选择是余弦相似度：

余弦相似度衡量的是”方向是否一致”而非”绝对距离”，对文本长度不敏感，适合语义比较。主流向量库（Milvus、pgvector、Redis 等）默认都支持余弦。工程上不必深究其他度量，除非有明确场景——大部分 RAG 用余弦就够，把精力留给更影响质量的地方。

向量索引：召回速度和质量的平衡

文档量大了之后，不能每次检索都全库暴力比对（O(N) 太慢），需要向量索引来加速。最常用的是 HNSW 这类近似最近邻（ANN）索引：

  • HNSW：召回质量高、速度快，是 Milvus 等库的默认主力索引，适合大多数场景；
  • IVF：先聚类再搜索，内存更省，但参数要调，质量略逊；
  • 暴力检索（FLAT）：小数据量（几万条内）完全够用，精确无损失，别过早优化。

工程上的关键认知：索引影响的是检索的速度和召回率，不是业务的正确性。 索引参数（如 HNSW 的 efConstruction/M）调的是”多快”和”召回多全”的权衡，调不出”语义理解对没对”——后者由 embedding 模型决定。

一句话：embedding 决定”能不能找对”，索引决定”找得多快”。 召回质量差，先怀疑 embedding 和切分，别急着调索引参数。

向量库选型与落地

向量检索需要一个能存向量、做 ANN 的存储——向量数据库。选型维度与经验：

维度 考量
数据规模与性能 百万级以下很多方案都够用；亿级才需要分布式向量库
过滤能力 是否支持标量过滤与向量检索混合（权限过滤刚需，系列第 7 篇）
运维成本 自建（Milvus）vs 云服务 vs 复用现有存储（Redis/ES 加向量能力）
生态 是否有官方 SDK、与你的技术栈契合度

这块我在 Milvus 系列里展开过：索引只是手段，先问清楚向量维度、度量方式、过滤字段是否和业务主键对齐。这里记住落地的三步：

常见的三个坑

坑一：query 和文档用了不同的 embedding。 查询向量必须和文档向量出自同一个 embedding 模型，否则向量空间不对齐，相似度毫无意义。换模型要全库重灌。

坑二：召回条数设太少。 top_k 设成 3，漏了相关文档也浑然不知。先宽召回（8~20 条）再过滤/重排，比”精确取几条”稳（最小闭环篇讲过）。

坑三：拿通用聊天模型当检索用。 聊天模型和 embedding 模型是两个东西。用聊天接口”生成式”判断相关性（让模型打分）不是向量检索——那是另一种方案（rerank/LLM 过滤），别混在一起。

小结

Embedding 把文字映射成向量，让检索从”字面匹配”升级为”语义匹配”。工程要点：embedding 选型看语言匹配、检索任务表现，换模型要重灌向量；相似度用余弦；索引选 HNSW 且明白它只影响速度与召回率；向量库选型看过滤能力和运维成本。最大的坑是 embedding 不对齐和”质量差就调索引”——召回质量的地基在 embedding 和切分，不在索引参数。
