Kubernetes 简介：容器编排解决什么问题

单机 Docker 管不过来时，K8s 用声明式控制让集群自我修复。

#Kubernetes #K8s
目录

Docker 系列一路走下来，单机部署的能力已经齐了：镜像、Compose、健康检查、优雅退出。但真实业务迟早会撞到单机的天花板——一台机器扛不住全部流量，需要多台机器组成集群；某个服务实例挂了要能自动补位；流量大了要能自动加副本。这些事 Docker Compose 管不了，因为它们本质是”编排”问题：不是管单个容器，而是管一群容器在一群机器上怎么调度、怎么自愈、怎么扩容。Kubernetes（K8s）就是干这个的——业界事实标准的容器编排系统。

单机 Docker 的四个力所不能及

先看清楚痛点，才知道 K8s 在解决什么：

1. 多机管理。 三台服务器各跑三个容器，服务要调度到哪台？某台机器挂了，上面的容器谁来接管？Compose 只认一台机器，跨机器它完全无能为力。

2. 故障自愈。 restart: unless-stopped 只能处理”进程退出”。机器宕机、容器被外部杀掉、依赖服务不可用——这些单机层面没有机制兜底，需要人工介入。

3. 弹性伸缩。 流量高峰来了想从 3 个副本扩到 10 个，单机只能靠人手动 docker run 一堆新容器再手工配负载均衡，扩缩容是噩梦。

4. 滚动发布。 新版本上线要”先起新的、确认健康、再摘旧的”，中间不能断服务。手搓这套流程极易出错。

K8s 把这些问题全部变成”描述期望状态，系统自动趋近”。

声明式：告诉它”要什么”，而不是”怎么做”

理解 K8s 最重要的一句话：你只描述想要的最终状态，K8s 负责把现状改造成那个状态。 这跟 Docker 的”命令式”操作形成鲜明对比。

命令式（Docker 风格）是”怎么做”的指令序列：run 这个镜像、删掉那个容器、重启服务——每一步都要你明确指示。

控制平面与工作节点

K8s 集群分两层角色：

  • 控制平面（Control Plane）：集群的大脑。kube-apiserver 是唯一入口（所有 kubectl 命令都打到它这里），etcd 存集群状态，调度器决定 Pod 放哪台机器，各类控制器负责把现状推向期望状态。
  • 工作节点（Node）：真正跑容器的地方。每个节点上有 kubelet（跟控制平面通信、管理本机容器）和 kube-proxy（处理网络转发）。

有个理解上的常见误区：**kubectl 不是”连到某台机器执行命令”**，而是跟集群的控制平面对话。你说”我要 3 个副本”，控制平面去调度，各节点的 kubelet 执行——你不关心 Pod 具体落在哪台机器上。

一切皆资源：用 API 对象描述系统

K8s 的哲学是”一切皆资源”。Deployment、Service、Pod、ConfigMap、Secret、Ingress……都是 API 资源，都可以用 YAML 描述、用 kubectl apply 提交。这意味着整个集群的期望状态就是一堆 YAML 文件，可以被版本管理、代码评审、自动同步——这就是后面讲 GitOps 的根基。

这套设计带来一个 AI 应用团队特别受用的能力：把整套 LLM 服务（API、向量库、模型推理、Redis）的部署描述沉淀成代码。环境怎么搭、副本几个、资源限额多少，全部可审阅、可复现。新环境（测试、预发、生产）clone 一份配置改改参数就能拉起。

小结

K8s 解决的问题是单机 Docker 够不到的：多机调度、故障自愈、弹性伸缩、滚动发布。它的核心思想是声明式——描述期望状态，让控制器自动趋近，系统因此有了自我修复能力。下一篇进入核心对象，从最小调度单元 Pod 和管副本的 Deployment 讲起，这是理解后面所有概念的地基。
