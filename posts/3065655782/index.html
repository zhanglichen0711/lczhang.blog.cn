MCP 会重演 HTTP 的故事吗

每个 Agent 一套私有工具协议，是 2025 年应用层最明显的重复劳动。统一协议的赢家往往是生态。

#MCP #工具生态
目录

把模型接到真实系统里的过程里，我花过最多时间的地方不是模型，是工具层：每个 Agent 框架一套工具调用协议，每个业务系统一种接入方式，每换一个框架就要重写一遍工具封装。2025 年做 AI 应用的人，很大一部分精力都耗在这种重复劳动上。

MCP 想解决的正是这个：给”模型怎么调用工具”定一个公共协议。

为什么说它可能重演 HTTP

HTTP 当年赢，不是因为它是技术最优雅的方案，而是因为它是”最低公共标准”：谁都能实现、够用、可扩展。MCP 走的是同一条路——一个很薄的协议（工具发现、调用、结果返回），不做重活，把复杂度留给两端。

协议类的东西有一个规律：价值不在协议本身，而在接入的生态规模。 HTTP 没有”HTTP 公司”赚钱，但整个 Web 都长在它上面。MCP 如果成立，赢家不是协议作者，而是那些”一次接入、处处可用”的工具和平台。

做工具封装这一年看到的信号

有几个迹象让我觉得这不是又一次炒作：

  • 主流 Agent 框架和客户端开始原生支持 MCP，不再各自发明工具格式；
  • 工具提供方（数据库、协作软件、开发平台）陆续出官方 MCP Server，意味着”为 MCP 适配”正在变成厂商的默认动作；
  • 应用侧开始出现”一次写好 MCP Server，多个 Agent 客户端复用”的真实收益——我们自己也把一批内部工具封装成 MCP，换框架不再需要重写接入层。

它不会重演 HTTP 的部分

也要清醒：HTTP 是纯技术协议，MCP 却绑定了”模型的行为”。协议可以标准化，但模型执行工具调用的可靠性、安全边界、权限模型这些，仍然各自为政。MCP 统一的是”怎么调用”，不是”能不能调用”——后者依然是应用层的责任。

结论

MCP 大概率不会成为某个公司的护城河，但会成为一个基础设施层的分水岭：早把工具封装成标准协议的人，在生态转向时会少一次重构。 协议的故事总是这样——单点价值很小，生态价值很大。值得押注的从来不是协议本身，而是站上协议之后能触达的生态。
