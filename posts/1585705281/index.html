Milvus 简介：向量数据库在 RAG 里的位置

RAG 为什么需要向量数据库、Milvus 与 ES/传统数据库的边界，以及它的核心概念地图。

#RAG #Milvus #向量数据库
目录

一个 RAG 知识库要回答”哪些文档和这个问题最相关”，靠的是把文本变成向量再做相似度搜索——“找到离问题向量最近的那些片段”。这个搜索如果放在 MySQL 里做（暴力算全部向量的距离），数据一到几十万条就扛不住了。于是有了专门干这事的存储：向量数据库。这一篇讲清楚它在 RAG 里的位置，以及 Milvus 凭什么是主流选择之一。

RAG 检索链路里它在哪

标准的 RAG 在线链路：

向量数据库负责”召回”这一环——它的性能决定了”几十万、上千万片段里，几十毫秒找出最相关的几十条”。这是它和 MySQL、Elasticsearch 分工的根本点：

存储 擅长 在 RAG 里的角色
MySQL 精确查询、事务、业务数据 存文档本身、切片记录、权限等元数据
Elasticsearch 关键词/全文检索、倒排索引 关键词兜底、日志等文本检索
Milvus 向量相似度搜索（百亿级毫秒） 语义召回的主战场

现实中它们常组合使用：MySQL 管业务状态，Milvus 管向量召回，ES/BM25 管精确词匹配——各自负责最擅长的那部分。

Milvus 是什么

Milvus 是开源的云原生向量数据库，由 Zilliz 团队发起，目前是 LF AI & Data 基金会项目。几个核心特征：

  1. 专为向量设计——支持多种 ANN 索引（HNSW、IVF、DiskANN 等），能在海量向量上做近似最近邻搜索（ANN），几千万条数据毫秒级召回；
  2. 不止存向量——每条数据可以带标量字段（文档 ID、标题、部门、权限），搜索时能按标量字段过滤（dept = "质量部"），这是做权限控制的关键；
  3. 原生支持混合检索——2.4 引入多向量，2.5 起内置 BM25 全文检索（Sparse-BM25），稠密向量 + 关键词可以一条链路打通（这正是 RAG 工程最需要的”语义 + 精确词”双路召回）；
  4. 部署灵活——单机 Standalone 到分布式集群，本地 Docker 就能起步。

核心概念地图（先混个脸熟）

后面十篇会逐个展开，先建立全景：

概念 一句话 对应关系
Collection（集合） 相当于关系数据库的”表” 一个知识库 = 一个或多个集合
Field（字段） 一行数据的列：主键、向量、标量 id、vector、title、dept
Vector（向量） 浮点数组，文本/图片的数学化表示 dim=768 表示 embedding 是 768 维
Index（索引） 加速搜索的数据结构（HNSW/IVF） 不加索引 = 全表暴力扫
Metric（度量） 向量间”距离”怎么算 内积 IP、余弦 COSINE、欧氏 L2
Segment（分段） 数据在底层按段存储，自动合并 类似 LSM 的 Segment
expr（过滤表达式） 搜索时对标量字段的过滤条件 dept == "质量部" 实现权限过滤

为什么它是 RAG 工程的”标配”之一

如果只是”能搜向量”，选项其实不少（FAISS、Qdrant、pgvector、Elasticsearch 的向量插件……）。Milvus 在企业级 RAG 场景胜出靠的是完整度：

  • 混合检索开箱即用：稠密语义 + BM25 关键词 + RRF 融合在同一套 API 里，不用自己拼两套系统再写融合逻辑；
  • 标量过滤能力强：权限、版本、时效过滤直接下推进检索（expr），这是企业知识库的硬需求；
  • 运维与生态成熟：官方 SDK（Python/Go/Java）、监控指标、与 LangChain/LlamaIndex 的集成、Zilliz Cloud 托管版。

对企业知识库这类”数据分部门隔离、要求权限过滤、需要混合检索保精度”的场景，Milvus 几乎是现成的答案。

小结

向量数据库是 RAG 召回层的引擎，Milvus 的价值在于把”海量向量搜索 + 标量过滤 + 混合检索”整合成一套简单 API。理解它”是表不是缓存、靠索引不靠暴力”的心智，后面的安装、建集、写数据、检索才有根基。
