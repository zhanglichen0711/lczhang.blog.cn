查询理解：意图分流与改写

不是所有问题都该检索：先分意图再路由。改写让用户口语对齐到文档术语，多路召回比单路稳。

#RAG #查询理解
目录

RAG 的召回质量，不止取决于知识库这边（切分、embedding），还取决于查询这边——用户的问题长什么样，直接决定检索能不能命中。很多 RAG 项目把精力全花在优化知识库，却忽略了查询理解：用户一句”屋面漏了咋整”，和你知识库里”屋面防水层渗漏处理”的表述隔着一条语义鸿沟。这一篇讲查询侧的两件事：意图分流（要不要检索）和查询改写（怎么检索更准）。

意图分流：不是所有问题都该检索

RAG 系统最常见的浪费，是把所有问题都丢进检索流程。但实际上用户的问题五花八门：

如果对”谢谢你”也做一次向量检索、再拼上下文调模型，结果就是：浪费 token 和时间，还可能检索出不相干内容干扰模型回复。意图分流就是在检索之前，先判断”这个问题要不要检索、走哪条处理路径”。

意图分流的收益不只是省成本——它保护了回答质量：闲聊问题不被检索噪音污染，无关问题不硬凑知识库答案。没有意图分流的 RAG，是拿所有问题去撞一个它不万能的知识库。

查询改写：把用户的话翻译成文档的语言

这是查询理解里最容易被低估的一步。用户在问”屋面漏了怎么处理”，你知识库的文档写的是”屋面防水层渗漏的维修与堵漏”。两者的字面和向量表达都不完全对齐——embedding 能缓解一部分语义鸿沟，但改写（query rewrite）能主动消除它。

改写的思路：把用户的自然口语，改写成知识库里更可能出现的专业表述，再拿改写后的 query 去检索。

多路召回：别把鸡蛋放一个篮子里

改写后的 query 也不一定完美。工程上更稳的做法是多路召回：同一问题生成多个检索变体，分别检索后合并结果：

为什么多路比单路稳？因为每一条检索路径都有自己的盲区：原句保留用户口语可能漏掉术语文档，改写版可能过度改写丢信息，关键词版能兜底专有名词。三路合起来，比任何单路都更可能覆盖”该命中的文档”。代价是多几次检索——在召回质量面前，这个代价通常值得。

一组实测经验

在规范问答这种”术语密集”的场景里，查询理解的收益排序大概是：

  1. 意图分流：挡掉无关查询，质量与成本双收益（最大）；
  2. 改写：口语→术语，命中率提升明显；
  3. 多路召回：锦上添花，对模糊问题尤其有效。

一个容易被忽略的细节：改写不是越”书面”越好。 改写得过度，可能把用户的限定条件改丢（比如”去年的规范”被改成”规范”，时效条件就丢了）。改写必须保留所有关键限定——它做的是”翻译”，不是”概括”。

小结

查询理解是召回质量的前置环节，两件事：意图分流决定”要不要检索、走哪条路径”，挡住无关查询、保护质量；查询改写把用户口语翻译成文档术语，配合多路召回提升命中率。判断标准很简单：用户问不中，别只怪知识库——先看查询侧有没有把用户的话”翻译”对。
