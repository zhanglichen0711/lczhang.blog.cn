Agent 可观测：让每一步都有迹可循

Agent 是黑盒循环，出问题最难定位。记录每轮的思考、行动、观察，故障才能归因到具体一步。

#Agent #可观测
目录

单次问答出问题，看一次调用的日志就能定位。Agent 出问题就麻烦得多——它是一个多轮循环，可能在第 3 步选错了工具、在第 5 步被一个错误结果带偏、在第 8 步陷入死循环。用户只看到”最后任务没完成”，中间发生了什么全是黑盒。Agent 可观测性的目标，就是把这个黑盒循环变成”每一步都能回放”的白盒——这是 Agent 能调试、能评测、能上生产的前提。

Agent 出问题的三种典型形态

先看 Agent 特有的故障模式（传统监控看不到的）：

形态一：错误累积。 单步错误本身不大，但 Agent 会基于错误结果继续往下走——第 2 步的错误被第 3 步当成事实，越滚越大，最后输出一个”基于错误推理的自信结论”。

形态二：循环空转。 Agent 在一个失败的工具上反复重试，或者来回切换两个工具（A 说需要 B，B 说需要 A），直到步数上限——钱烧了、时间耗了、任务没完成。

形态三：目标漂移。 长任务执行中，Agent 逐渐偏离最初目标，做着做着做成了另一件事——需要对比”计划 vs 实际”才能发现。

这三种故障的共同点：**单看某一次调用看不出问题，必须看整条”决策链”**——这就是 Agent 可观测和普通日志的本质区别：要记录的是”思考-行动-观察”的完整链条，而不只是请求和响应。

几个 Agent 专属的观测指标

除了常规的延迟/成本/错误率，Agent 还要看几个专属指标：

循环指标：

  • 步数分布（正常任务几步完成？异常任务是否经常打满上限）；
  • 同一工具重复调用次数（>2 次可能是循环或工具设计问题）；
  • 工具切换频率（来回切换可能是”决策摇摆”）。

决策指标：

  • 工具选择错误率（选了不该选的工具）；
  • 参数校验失败率（工具设计问题，说明参数描述不清）；
  • 工具执行失败后的恢复方式（重试成功？换方案？还是死循环）。

目标指标：

  • 计划 vs 实际执行偏差（长任务是否跑偏）；
  • 提前终止率（Agent 自己觉得做完了 vs 用户觉得没做完）。

这些指标可以算成聚合看板（如”平均步数””循环发生率”），但更重要的是每个异常都要能点开看原始轨迹——指标告诉你”有问题”，轨迹告诉你”问题在哪一步”。

循环检测：自动发现”空转”

Agent 空转是最高发的故障之一，值得单独做检测。两个简单有效的检测：

检测到循环或卡住时，正确的处理不是等步数上限自然耗尽（浪费），而是主动干预：终止任务、切换策略（换个工具/换个说法）、或升级给人工（human-in-the-loop，LangGraph 篇详述）。

排查方法论：从轨迹定位根因

有了完整轨迹，Agent 故障排查就有章法了。一个实用的定位顺序：

归因的经验法则（Agent 故障里的高频真相）：大多数 Agent 故障不是”模型不够聪明”，而是工具边界不清、错误没有恢复路径、或循环没有护栏。 先怀疑这三类工程问题，再怀疑模型能力。

可观测如何反哺评测

轨迹不只是排查用的，它是 Agent 评测的基础（呼应评测系列）：

  • 评测要跑真实任务，而真实任务的”过程质量”（步数、工具错误、循环）只能从轨迹里拿；
  • 线上差评 → 调出轨迹 → 定位到第几步出错 → 该案例成为评测集回归题——Agent 的评测回流，靠的就是轨迹完整性；
  • 对比新旧版本：换了模型后 Agent 平均步数是涨是跌、循环率是否上升——这些只有轨迹可观测才能回答。

小结

Agent 可观测的核心是记录”思考-行动-观察”的完整轨迹，把黑盒循环变成可回放的决策链。要记录每一步的工具选择、参数、结果、重复情况；监控循环指标（步数、重复调用、工具错误）和异常（循环空转、卡死），检测到异常要主动干预而非等自然耗尽。排查时先怀疑工程问题（工具边界、错误恢复、护栏），再怀疑模型。轨迹是 Agent 调试的第一现场，也是评测与回流的数据基础——没有轨迹的 Agent，出了问题只能靠猜。
