RAG 混合检索与 rerank

关键词 + 向量双路召回，再用重排模型精挑，别只调 embedding。

#RAG #混合检索 #rerank
目录

纯向量检索有个反直觉的短板：它擅长”意思相近”，却常常漏掉”字面精确”的东西。搜「RAGAS 评测标准」，向量可能把 RAGAS 这个专有名词模糊掉，召回一堆泛泛的 RAG 评测文章，反而找不到真正写着 RAGAS 的那一篇。原因在于向量检索的匹配粒度是”语义向量”——它对专有名词、编号、精确说法不敏感，而这些恰恰是规范、技术文档里最重要的检索线索。

所以成熟的 RAG 不会只靠向量，而是「关键词 + 向量」双路召回，再用 rerank 精排。这三步决定了最终喂给模型的是不是”对”的片段。

一、两种召回互补

维度 BM25 关键词检索 向量语义检索
擅长 精确词匹配（编号、型号、专名） 语义相近（同义改写、口语化）
短板 同义词、换说法就找不到 精确字符串、低频专名
匹配单位 词项 token 语义向量

关键词检索补向量漏掉的”精确”，向量补关键词漏掉的”同义”。两者单独用都不够稳，合起来才完整。 规范文本尤其典型：既有条款编号（”4.2.1”这种必须精确命中）、又有口语化问法（需要语义兜底），双路召回几乎是刚需。

二、融合用 RRF，别硬加权

把两路结果合成一个列表，最常见的做法是给分数加权：

问题是两路分数的量纲和分布根本不一样（BM25 是词频统计，向量是余弦值），加权系数 alpha/beta 很难调出稳定最优——不同 query 的最优权重还不同。

更稳的融合是 RRF（Reciprocal Rank Fusion，倒数排名融合）：不看分数绝对值，只看排名，两路结果按排名给分相加：

RRF 的好处：不需要调权重系数——它假设”两路都排前面的，大概率真的相关”。这是工程上最省心也最稳的融合方案，Milvus 等向量库也直接内置了混合检索 + RRF。

三、rerank：让真正的”重排模型”精挑

双路召回 + RRF 之后，拿到的还是一个”粗排”结果——top 20 里可能只有 5 条真正有用。如果直接把这 20 条全塞给模型，上下文又长又噪。这时候需要 rerank（重排）：用一个专门的重排模型，对候选片段做”query 与文档相关性”的精细打分，把真正相关的提到前面，不相关的沉底或剔除。

rerank 与 embedding 的区别是关键：

  • embedding：把 query 和文档分别编码成向量，算的是”预先压缩后的相似度”——信息有损；
  • rerank：把 query 和文档拼接在一起输入模型，做的是”细粒度交叉匹配”——信息无损，更准但更慢。

所以工程上的标准姿势是分两段：向量/关键词先粗召回（快、召回全），rerank 再精排（准、取前几）：

为什么第一段要取宽？因为 rerank 再准，也只能在召回到的候选里排——如果第一段就把真相关文档漏了，rerank 也救不回来。召回保全面，重排保精准，各司其职。

四、rerank 的取舍：是不是第一天就得上

rerank 不是免费的：多一次模型调用 = 多几十到几百毫秒延迟，自建 rerank 还要维护一个模型。什么时候值得上？

  • 知识库大、候选杂时，rerank 收益明显——候选里噪音多，需要精排压噪；
  • top_k 里的噪音会干扰回答（比如前 5 条里混 2 条无关，模型就可能被带偏），rerank 能显著改善；
  • 早期小库、问题简单时，可以先不上——宽召回 + 严格生成提示（只依据资料）也能顶一阵。

我的建议：先把闭环跑通，再按线上质量决定是否加 rerank——它解决的是”候选里噪音多”的问题，不是”召回全不全”的问题。召回不全先回去查切分和 embedding，别用 rerank 掩盖上游问题。

每一步都解决一个明确的问题，每步之间都用你的评测集验证（评测集怎么建，系列里有专篇）。检索优化不是堆组件，是缺什么补什么。

小结

纯向量检索漏”精确”，纯关键词检索漏”同义”，混合检索让两者互补；融合用 RRF（按排名，不调权重）比硬加权稳；rerank 做第二段精排，用拼接式的交叉匹配把真正相关的提到前面。工程顺序：先粗召回保全面、再重排保精准，rerank 在候选噪音多时才值得上。检索质量的提升路径是”先补召回、再压噪音”，别只调 embedding，也别一上来就堆 rerank。
