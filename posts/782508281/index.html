什么是微调：从预训练到领域模型

通用模型不懂你的行业？微调把通用能力适配到领域：原理、代价与适用场景。

#微调 #大模型
目录

BERT 篇已经见过”预训练 + 微调”的雏形。到了大模型时代，微调（Fine-tuning）的含义更具体：一个在通用语料上训练好的 LLM（DeepSeek、Qwen……）很聪明，但不懂你的行业黑话、不按你的格式输出。微调就是用你的领域数据，让模型在保持通用能力的同时，学会你的规矩。这一篇讲清它是什么、什么时候该用、什么时候不该用。

预训练模型缺少什么

通用大模型很强，但落到垂直场景有三个短板：

  1. 领域知识缺失：不知道”GB50204””蜂窝麻面””质量门禁”意味着什么；
  2. 输出格式不对：你要求它输出固定的 JSON/固定字段，它自由发挥；
  3. 风格与语气：需要它像个”质量专家”回答问题，而不是通用聊天。

微调 = 用少量高质量领域数据在这些短板上”补课”。

三种”让模型懂领域”的方式

面对”模型不懂业务”，先别急着微调——有三条路，成本递增：

方式 做法 成本 什么时候用
提示工程 把背景/规则写进 system prompt 零 规则能说清、信息不超上下文
RAG 检索增强 把知识放库里，回答时检索进来 中（要维护库） 知识更新频繁、要可溯源
微调 用数据改模型权重 高（要算力+数据） 格式/风格/领域表达要”刻进”模型

决策铁律：先提示工程 → 再 RAG → 最后才微调。微调是三种里最贵、最不可逆的，别拿它当第一选择。

微调真正擅长的场景

RAG 和提示词都解决不了时才轮到微调：

  • 格式刚性：输出必须严格遵循 schema/模板，提示词经常”飘”；
  • 风格/角色固化：要让模型永远像”规范问答专家”，不解释、不闲聊；
  • 领域表达：术语用法、缩略语、回答口径要统一；
  • 模型行为：让它学会”不知道就说不知道”或特定交互流程。

反模式：以为微调能”灌入新知识”——那是 RAG 的活。微调学的是”表达方式”，不是”事实库”；事实靠检索喂，方式靠微调定。

微调的成本账

微调一个 7B 模型，成本要算清三笔：

  1. 数据：高质量样本通常要几千条起（数据质量 > 数量，脏数据会把模型教坏）；
  2. 算力：全参微调 7B 要几十 GB 显存；用 LoRA（后面专篇）一张消费级显卡也能跑；
  3. 评估与回滚：微调可能”灾难性遗忘”（学会领域、忘了通用），必须留评估集和原模型做对比。

每次微调都要回答：多花的这笔钱，换来了提示词/RAG 给不了的东西吗？ 答不上来就别微调。

微调的类型一览

按改动范围从大到小：

类型 改什么 算力需求
全参微调（Full FT） 所有参数 最高
LoRA/QLoRA 高效微调 只训少量低秩增量 低（单卡可跑）
指令微调（SFT） 教模型按指令/格式回答 中
对齐（RLHF/DPO） 让回答符合人类偏好 高

后几篇逐个展开：先讲策略（全参 vs 部分冻结），再讲 LoRA 怎么”以小博大”，然后是 SFT 数据怎么造、RLHF/DPO 怎么对齐、最后怎么评估微调效果。

小结

微调 = **用领域数据给通用模型”补课”**，解决的是格式、风格、领域表达，不是知识缺失。选型顺序记牢：提示工程 → RAG → 微调，微调是最后手段。理解”微调改的是表达、不是事实”，你就能在正确的时候用正确的方法——这也避免了很多团队”花了大力气微调，效果还不如加两行提示词”的尴尬。

微调的价值与边界清楚了，下一篇讲策略：全参微调、部分冻结与 LoRA，改动多大、代价多重。
