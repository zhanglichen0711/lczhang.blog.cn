MySQL 笔记：约束、联表和分析函数怎么接到知识库

DDL / DML / DQL 背再多也不如先想清楚：文档、切片、权限和引用主键分别放哪。

#RAG #MySQL
目录

数据库课会把 SQL 分成 DDL、DML、DQL，再补约束、多表和函数。知识库项目里，MySQL 很少用来存向量，但几乎一定用来存「事实和权限」。

先分清三层对象

  1. 库和表：文档库、切片库、用户/权限库。字符集一开始就用 utf8mb4，避免规范文本里的符号和生僻字。
  2. 行：一篇文档、一个 chunk、一次问答日志。
  3. 约束：主键决定你能不能回表引用；唯一约束避免同一文件被导入两次；外键能建就建，至少也要在应用层保证 chunk.doc_id 对得上。

主键、非空、唯一、默认值看起来像语法练习，上线后对应的是：

  • 同一 doc_id 不能插两条「当前版本」
  • source、version、permission 不允许空
  • 删除文档时，切片是级联删还是先标记 deleted

单表查询是日常

WHERE / LIKE / IN / BETWEEN、去重、别名、表达式，足够支撑后台「按专业、章节、时效筛文档」。模糊检索不要指望 LIKE '%规范%' 扛住全站搜索，那是 Milvus 的事；MySQL 负责精确过滤和回表。

多表查询才是引用链

交叉连接只用来理解笛卡尔积。真正用的是「有条件的连接」：

  • 切片 join 文档元数据，才能在回答里写出标准号和生效日期
  • 自连接适合章节树：父节点是规范名，子节点是条文
  • 子查询适合「先找出最新版本号，再取该版本切片」

权限过滤也是联表，而不是把所有人能看的文本都塞进向量库。

函数：为展示服务，不为检索服务

数值、字符串、日期、CASE WHEN 适合做报表和清洗。行转列 / 列转行是面试常客，在业务里更常见于「把多标签展平」或「把每日调用量摊成宽表」。

不要用一长串字符串函数代替切分器。切分是 Python 的工作；MySQL 只保存切分结果和元数据。

和 Redis / Milvus 的边界

问题 放哪
谁在什么版本下有权看这篇文档 MySQL
同一 query 的 embedding 是否刚算过 Redis
语义上最相近的 20 条切片 Milvus
回答里要展示的标准号、页码、原文 MySQL 回表

向量库不是数据库替代品。主键先对齐，hybrid search 才有意义。
