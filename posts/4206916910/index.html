规划与反思：让 Agent 学会拆解任务

长任务最怕跑偏。先规划再执行让步骤可控，反思让结果可修正——但两者都有边界，别盲目加。

#Agent #规划
目录

ReAct 是 Agent 的”标准大脑”——走一步看一步。但真实任务往往很长：调研一个课题、整理一份报告、批量处理一批数据，如果 Agent 每一步都临时决定，很容易跑偏——做着做着忘了最初目标，或者在某条岔路上越走越远。规划（Planning）让长任务可控：先想清楚要做哪几步，再动手。 而反思（Reflection）补的是另一类缺陷：做完的质量问题。 这篇把”规划”和”反思”两个机制讲透——它们怎么落地、各自的边界在哪。

规划的本质：把”自由发挥”变成”有步骤地执行”

ReAct 的自由循环适合任务路径不确定的场景；但很多任务其实是”路径可预知”的——只是步骤多。规划的价值是把这些可预知的步骤显式化：

  • 先让模型产出任务清单（步骤 1/2/3…）；
  • 再逐步执行，每步可以单独验证；
  • 执行过程中可对照计划检查”有没有跑偏”。

它的工程意义不只是”更有序”，而是三个可量化收益：

  1. 可控：长任务拆成小步后，每步可单独评测、单独重试，出问题能定位到”第几步”；
  2. 可恢复：任务中断后，从失败的步骤重跑，而不是从头再来；
  3. 可审计：计划和实际执行对比，能看出 Agent 是否忠实执行、哪里偏离。

工程上的三个关键设计：

1. 计划要”可执行”而非”口号”。 差的计划是”调研三家厂商”（太粗，执行时还是要自由发挥）；好的计划是”用 web_search 查厂商 A 的 GPU 型号和价格 → 查厂商 B → …”。计划里的每一步，执行阶段要能直接对应到工具调用。

2. 执行中允许”计划修订”。 现实里第 2 步可能发现第 3 步的前提变了。好的实现允许执行中插入”重新规划”——发现计划不成立时，让模型先更新计划再继续，而不是死板执行完一个错误计划。

3. 规划也要设上限。 计划步骤过多说明任务拆得太碎（每步都有开销），过少说明没拆到位。一般一个任务 3-8 步为宜；计划本身失败（模型拆不出合理步骤）要能降级回 ReAct。

反思的本质：第二双眼睛

反思是让模型”自己检查自己的工作”。它的价值在于抓住第一遍生成时遗漏的错误——很多错误在生成当下看不见，但回头看能发现（漏了条件、逻辑矛盾、格式不对）。

反思的两种实现层次：

层次一：单轮反思（生成 → 检查 → 修正）。 模式篇给过：生成草稿，用审视视角检查，根据问题修正。适合”错误容易被发现”的任务（代码、SQL、结构化输出）。

层次二：持续反思（循环中每一步都带检查）。 在 ReAct 循环里，模型每次行动后不仅观察结果，还反思”这一步对吗？要不要回退？”——这就是 Agent 的”元认知”，能减少错误累积：

反思的边界：不是所有任务都值得

反思不是免费的——每次反思都是一次额外模型调用（延迟 + 成本）。而且反思的效果有前提：模型得能看出自己的错。两个判断标准：

工程判断：能不能用”规则”替代反思？ 很多”反思”能做的事，规则做起来更便宜更可靠——JSON 格式错误用解析器校验、SQL 语法用编译器检查、缺字段用 schema 验证。先上规则，规则覆盖不了的再用反思。 反思是”规则之外的最后一道柔性检查”，不是第一选择。

小结

规划让长任务可控（拆成可执行、可验证、可恢复的步骤），反思让结果可修正（生成后自查）。工程要点：计划要能直接映射到工具调用、执行中允许修订计划；反思要分层次（单轮 vs 循环中）、能用规则替代就别用模型反思。两者都有成本与边界——规划适合路径可预知的长任务，反思适合”错误能被自己发现”的任务。给 Agent 加”计划”和”反思”，是给它装了方向盘和后视镜——但别让它因此开得更野，上限和护栏一个都不能少。
